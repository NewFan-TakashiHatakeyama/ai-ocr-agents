# ADR-0008: 本文ベースの帳票分類は「1 ページ目の表題部」だけを信号にする

- 状態: Accepted
- 日付: 2026-09-12

## 背景

帳票分類（⑦）の信号は「アップロード時の doc_type 宣言」と「ファイル名の語彙一致」
だけだった（ADR-0006 決定 5 で「本文内容ベースの分類は別チケット」とした残課題）。
実際のファイル名（`0001.pdf`、`scan_20260831.pdf`）では何も推定できず、抽出を終えて
本文が手元にあるのに種別の提案が付かない。

本文を信号にする案は一度、敵対的レビュー（2026-08-17）で退けている。当時は抽出
**値**を渡していて、請求書の備考が「見積書No.Q-1に基づく」を引用しただけで
quotation が勝ち、正当な run を `process.classify` の halt で止めた。値は
「自種別の語はほぼ現れず、他種別の語は常態的に現れる」**構造的に偏った信号**であり、
重みを調整して救える性質のものではない。この判断は維持する。

一方、run ごとの OCR span は `run_spans`（migration 0008、読取領域ヒントの土台）に
座標付きで永続化されるようになった。位置が分かるなら、本文のうち**種別が印字されている
場所だけ**を信号にできる。

## 決定

### 1. 信号は「1 ページ目・上端 25%」に中心がある span の原文に限る

帳票の種別（「請求書」「御見積書」「納品書」）は表題として 1 ページ目の上端に印字され、
明細・備考（他種別の語が出る場所）はその下にある。bbox の中心が
`page_height × 0.25` 以下の span を読み順（行を上から、行内は左から）に並べ、
空白で連結する。上限は 40 span / 600 文字。

切り出しは純関数 `newfan_workflow.title_zone_text` に置き、gateway
（`POST /documents/{id}/classify`）と orchestrator（`process.classify`）が
**同じ関数で同じ文字列**を作る。抽出値は引き続き渡さない。

### 2. 重みは変えない（ファイル名 ×3、表題部 ×1、領域 3 で飽和）

`classify_text` の重みと飽和はそのまま。帰結を実スコアで固定する:

| ファイル名 | 表題部 | 結果 | 確信度 |
|---|---|---|---|
| 手がかり無し | 「請求書」 | invoice | 0.667 |
| 手がかり無し | 「請求書」＋明細に見積語 ×3（表題部の外） | invoice | 0.667（本文全体なら quotation 0.75 で反転していた） |
| 「請求書」 | 「御見積書」 | invoice | 0.75（表題無しなら 1.0） |
| 「請求書」 | 「御見積書」「見積金額」 | invoice | 0.6 |
| 「請求書」 | 見積語 3 領域 | invoice（同点、ファイル名側） | 0.5 |

表題部の 1 領域は 1.0、飽和で 3.0＝ファイル名 1 語。つまり**表題はファイル名の
1 語を上回れない**（最大で同点）。ファイル名と表題が食い違うとき、表題は相手の
確信度を下げる（ゲート閾値 0.75 は 2 領域で割る）が、種別を反転させない。
同点はファイル名に一致した候補を先にする（候補の並び順に依存しない）。

これは意図した非対称である。ファイル名は人が付けた名前、表題部は OCR であり、
表題部にも「見積No」のような他種別の参照は入り得る（発注書の右上に見積番号）。
反転させたいなら人がファイル名か取込時の種別で言う、が今の運用。

### 3. ゲートの閾値 0.75 はそのまま

`process.classify` が内容分類でスキーマ種別を上書きするのは確信度 0.75 以上のとき
だけ（従来どおり）。表題部だけの信号は 1 領域で 0.667 なので、ファイル名の手がかりが
無い帳票では**ゲートを上書きしない**（2 領域以上＝「御請求書」＋「請求金額」で 0.833）。
gateway のサジェストには閾値を掛けない（UI が確信度を併記し、利用者が選び直せる）。

### 4. 寸法不明のページは信号にしない

`pages.height` は DDL で nullable。寸法が無ければ「上端」を決められないので空を返し、
従来どおりファイル名だけで分類する（除外領域の適用と同じ fail-open）。run が無い・
`run_spans` の行が無い（0008 より前の run、失敗 run）場合も同じ。

## 影響

- `POST /documents/{id}/classify` は、最新 run の 1 ページ目に span があれば
  表題部を信号に加える。`method` は表題部の証拠が寄与したとき `"filename+title"`、
  `reason` は「〜がファイル名に一致、〜が表題部に一致」と出どころを分けて出す。
  run が無い帳票（ExtractStart の初回）は従来と同一の応答。
- `process.classify` は `title_text`（抽出完了 notify の enrich で
  `load_extract_result` が `run_spans` から取る）を信号に加える。node output に
  `method` を残す。ファイル名が空でも表題部だけで走る。
- KIE プロンプトは変えない。抽出結果・正規化・確信度ゲートも変わらない。
- `classify_text` の text 引数は「本文全体」ではなく「表題部」を渡す契約になる。

## やらないこと

- 発見 label とスキーマ label の照合（ADR-0006 決定 5 の当初案）。label は値と同じく
  帳票の**内容**であり、同じ偏りを持つ。
- LLM による分類。決定論で十分に説明可能で、コストも掛からない。
- 表題部の領域を帳票ごとに学習すること。25% 固定で始め、誤検知が実測されたら
  ADR を改める。
