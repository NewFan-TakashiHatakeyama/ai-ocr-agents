# ADR-0004: HTTPS 化を保留し、ALB を HTTP のまま検証用途に限定する

- 状態: Accepted
- 日付: 2026-07-16

## 背景

§11 は通信の暗号化を求めており、terraform 側の HTTPS 配線は完成している。
`acm_certificate_arn` を渡すと、

- 443 リスナ（ACM 証明書）が生えて `/v1/*` と `/healthz` の振り分けが 443 にも付く
- 80 リスナが 443 へリダイレクトする既定アクションに切り替わる

つまり**証明書 ARN を 1 つ渡せば HTTPS になる**状態で、実装上の残作業は無い。

残っているのは証明書を発行する**ドメインが無い**こと。この AWS アカウント
（654654601240）の Route53 にあるゾーンは `graphsuite.jp` と `fastemergence.com` で、
どちらも AI-OCR とは別サービスのもの。ACM の証明書もその 2 つのサブドメイン向けしか
発行されていない。

ドメインの選定はサービスの命名に関わる事業判断で、コード側では決められない。

## 決定

当面 HTTP のままとし、ALB は**検証用途に限定する**。

## 影響

ALB はインターネットに公開されており、HTTP のままだと

- JWT が平文で流れる。経路上で盗まれればテナントのデータを読める
- レスポンス（抽出結果＝顧客の帳票内容）も平文で流れる

**顧客の実データを載せる前に必ず HTTPS 化すること。** 今の状態で本番運用に入っては
いけない。認証フロー自体（トークンの投入・検証・localStorage 保持）は実装・検証済みで、
足りないのは輸送路の暗号化だけ。

## 解除の手順

ドメインが決まったら:

1. Route53 にゾーンを用意（既存ゾーンのサブドメインでも可。例 `ai-ocr.example.jp`）
2. ACM で証明書を発行し DNS 検証を通す（ap-northeast-1。ALB はリージョン内の証明書が要る）
3. `deploy/terraform/env/production.tfvars` に `acm_certificate_arn = "arn:aws:acm:..."`
4. `scripts/aws_env.sh up`

`web` イメージは `NEXT_PUBLIC_API_BASE` をビルド時に焼き込むため、
**HTTPS 化と同時に再ビルドが要る**（実行時 env では変わらない）。`aws_env.sh push` は
ECR に同タグがあるとスキップするので、`image_tag` を上げること。

## 検討した代替案

- **`graphsuite.jp` のサブドメインを使う**: 既存ゾーンがあり今すぐ自動化できるが、
  別サービスのドメインに AI-OCR を相乗りさせることになる。
- **AI-OCR 専用ドメインを取得**: サービスの独立性は保てるが、ドメイン取得は費用が
  発生する購入操作で、利用者自身が行う必要がある。

いずれも保留。判断が出た時点でこの ADR を更新する。
