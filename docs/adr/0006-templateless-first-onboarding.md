# ADR-0006: 帳票登録はテンプレートレス先行（抽出→テンプレート化）に順序を反転する

- 状態: Accepted
- 日付: 2026-08-22

## 背景

従来の帳票登録フロー（①取込〜⑩有効化）は、実装上「③スキーマ登録が先、①取込が後」を
UI が強制していた:

- チャットに画像を貼る → アップロード → `/documents/{id}` へ誘導
- 未抽出の帳票画面（ExtractStart）は**スキーマ選択が必須**で、未選択だと
  「抽出を開始」ボタンが押せない
- スキーマが 1 つも無いテナントでは選択肢が「（スキーマ未登録）」のみ＝**行き止まり**
- スキーマが有っても、推定が付かない帳票は**先頭スキーマへ強制割当**され、
  無関係な定義（例: 請求書スキーマで納品書を抽出）で誤抽出が走っていた

これは利用実態と逆である。新しい帳票種を初めて取り込む時点では、
**どんな項目がその帳票にあるか自体がまだ分かっていない**。空欄から項目名を
発明させるより、実物から抽出された値を見ながら「残す項目」を選ばせる方が、
定義の質も導入の速度も上がる。プロダクトの標榜（テンプレートレス AI-OCR）とも
これで一致する。永続層は元々 schema_id を nullable にしており
（`pg_persistence.EMPTY_SCHEMA` の注記「テンプレートレス既定」）、
UI と KIE プロンプトだけが順序を逆に強制していた。

## 決定

**「まず取り込んで抽出 → 値を見てからテンプレート化」を既定の導線にする。**

1. **スキーマ選択を任意にする**（ExtractStart）。既定は
   「ユーザー選択 > 自動分類の推定 > スキーマなし（自動発見）」。
   先頭スキーマへの強制割当は廃止する。
2. **KIE プロンプトに自動発見モードを追加する**。スキーマの fields が空のとき、
   LLM は帳票に実在する「見出し語＋値」の組を自ら発見して抽出する
   （name は snake_case、label に見出し原文、span 根拠の契約は通常時と同一）。
3. **発見された label を `extraction_fields.label`（migration 0006）へ永続化する**。
   スキーマ指定の抽出は従来どおり field_schemas から label を引き、行の label は
   スキーマレス時のフォールバックとしてのみ使う。
4. **結果 API（GET /documents/{id}/result）に `schema_id` を追加する**。
   null＝スキーマレス抽出であり、UI はこれで「テンプレート化」導線を出し分ける。
5. **検証画面にテンプレート化ダイアログを追加する**。抽出結果の項目一覧から
   残す項目を選び（値が取れなかった項目は既定で除外）、label / name / 型
   （値の見た目から初期推測）を調整して `PUT /schemas`（create=true, admin）で
   スキーマ v1 を作る。以後の同種帳票は分類（⑦）がこのスキーマを提案する
   — ただし現状の分類は「アップロード時の doc_type 宣言」か「ファイル名の語彙一致」
   だけが信号であり、チャット貼り付け（doc_type 無指定）では提案が付かないことが
   多い。その場合も自動発見で抽出は成立し、抽出画面のプルダウンから作成済み
   スキーマを選べる。**本文内容ベースの分類（発見 label とスキーマ label の照合）は
   別チケット**とし、それまではテンプレート化の成功メッセージで
   「次回はファイル名に種別を含めるか、種別を指定して取り込む」ことを案内する。

## 影響

- **既存のスキーマ指定フローは不変**。スキーマがあるテナントでは分類の提案が
  従来どおり既定になり、抽出結果・正規化・確信度ゲートの動作も変わらない。
- **スキーマレス抽出の正規化・ゲートは保守的**。型情報が無いので
  deterministic_normalize は string 扱い、critical 閾値は付かない（standard 閾値 +
  grounding 必須はそのまま効く）。値の型による検証はテンプレート化後の
  次回抽出から効き始める。これは意図的な段階設計である。
- **プロンプトバンドル 2026.07-1 を上書き更新した**。スキーマ指定時の指示文は
  変えていない（自動発見の節は「fields が空の場合」に限定）。ゴールデン回帰
  （スキーマ指定で走る）で無影響を確認する。バンドルの版管理を厳密に運用する
  段階になったら新版ディレクトリを切ること。
- **migration 0006** は nullable 列の追記のみ。migrate → サービス更新の通常順序で
  安全（旧コードは列を無視、新コードは migrate 後に起動する）。
- テンプレート化は admin 限定（PUT /schemas の既存権限）。reviewer にはバナーで
  案内のみ出す。

## やらないこと

- **抽出の自動開始**（アップロードと同時に抽出）: LLM コストが掛かる操作は
  明示クリックに残す。ワークフロー（⑤⑥自動取込）では従来どおり自動で走る。
- **テンプレート化直後の自動再抽出**: 作成したスキーマでの取り直しは利用者の
  判断（既存の再抽出導線）に委ねる。
- **明細（tables）のテンプレート化**: v1 はヘッダ項目（fields）のみ。
  line_items の列定義化は別チケット。

## 追補（2026-09-06）: 領域指定テンプレート化の保証範囲

テンプレート化のプレビューで読取領域（include）と除外領域（exclude）を指定できる
ようにした（詳細設計 `docs/design/region-template-editor.md`）。テンプレートレスの
原則は維持する。**矩形を一切触らずに保存した場合、生成されるスキーマは領域機能を
導入する前と完全に同一**であり、抽出のプロンプトも 1 バイト変わらない。

### 除外領域が保証すること

指定した領域に重なる内容を、以下から除外する。

- OCR の span（面積の過半が領域に入るもの）
- テーブルセルの値と span 参照（セル自体は残す。列がずれると別項目に見えるため）
- 除外領域を持つページの `layout_markdown`
- 上記に由来する抽出結果（fields / tables）

### 保証しないこと

正直に書いておく。以下は v1 では消えない。

1. `LayoutBlock.content` とグラフの checkpoint への残存（スクラブしない）
2. マスクが発動しなかった表の `structure_html`
3. セル被覆率が 0.5 未満のときの pred_html 経由のテキスト混入
4. 自社ホストの視覚モデル（structure-svc / vl-svc）が画像として領域を見ること
5. 領域を設定する前に実行済みの run のデータ
6. 原本および前処理後 PNG のストレージ上の残存
7. `pages.width` / `height` が未登録のページ（寸法不明では領域を画素へ射影できず、
   誤った位置を決定論削除する方が危険なので**適用しない**。件数は run の
   `metrics.region.skipped_pages_no_dims` に記録する）

なお `layout_markdown` の除外は**ページ単位**である。markdown は座標を持たず部分
マスクが構造的に不可能なため、除外領域を持つページの markdown を丸ごと落とす
（落としたページは `metrics.region.markdown_dropped_pages` に残す）。

画像を外部 LLM へ送る経路はコード上存在しない（kie / llm_correct はテキストのみ）。
VL 由来の span は grounding 上限 0.7 で常にレビューを通る（DD-09）。

### 適用範囲

- **除外領域は doc_type（スキーマ版）単位で決定論的に適用される。** 同一 doc_type を
  共有する別レイアウトの取引先帳票にも同じ座標が当たるため、その位置にある実データが
  除外され得る。v1 は保存時の警告・検証画面のオーバーレイ・「除外が起きた run で
  必須項目が空」の集約所見という 3 つの検知線に倒す。取引先／レイアウト単位への
  スコープ化は v2。
- **ワークフローの `process.extract` は `schema_id`（版 id）固定**であり、新版の除外
  設定は既存ワークフローに自動適用されない。lint の L012（warning）が「最新版では
  ありません」と知らせるので、extract ノードのスキーマを選び直して再有効化する。

### 読取領域（include）の位置づけ

読取領域は **hint であって hard crop ではない**。領域の外で値が見つかっても抽出して
よく、領域はどの段でも値を捨てる根拠にならない。位置ガードは「設定と違う場所で
検出した」ことを観測するだけで、確信度にも値にも触らない。既定は shadow
（metrics とログのみ）で、誤検知率を実測してから `REGION_GUARD_ENFORCE` で有効化する。

### 追補（2026-09-06）: 取込時の種別指定と、テンプレート化からの書き戻し

このドキュメントは「次回はファイル名に種別を含めるか、種別を指定して取り込む」と
案内していたが、**その「種別を指定して取り込む」操作が画面に存在しなかった**。
`POST /documents` は前から `doc_type` を受け、classify の `declared` 経路
（confidence 1.0）も実装済みだったのに、web のアップロード導線が渡していなかった
ためである。残る唯一の信号はファイル名で、実際のファイル名（`0001.pdf` 等）では
何も推定できず、2 通目以降も必ず自動発見に落ちていた。

配線した内容:

- 一覧のアップロード欄に種別セレクトを置く。**既定は「未指定（自動発見）」**で、
  候補が 0 件のテナントでは描画しない。未指定時のリクエストは従来と同一。
  候補は `GET /doc-types`（viewer 可）から取る ── `GET /schemas` は admin 限定で、
  アップロードは uploader で通るため、そちらを候補源にすると権限の低い人には
  選択肢が空になる。
- テンプレート化に成功したとき、その帳票自身の `documents.doc_type` を
  `PATCH /documents/{id}`（admin）で確定する。**領域編集では行わない**
  （同じ `PUT /schemas` が飛ぶため、領域を直すだけで取込時に指定した種別を
  無言で上書きしてしまう）。

**行き止まりは作っていない。** 種別は任意で、未指定でも従来どおり取り込める。
抽出の開始も明示クリックのまま（種別が決まっても自動では走らせない）。
チャット貼り付け経路は無変更で、doc_type 無指定の許容経路として残す。
