# ADR-0007: 住所の値の慣例を正規化器（address_jp）で 1 つに決め、正解データも同じ形で持つ

- 状態: Accepted
- 日付: 2026-09-12

## 背景

読取領域ヒントの第 3 回計測（`docs/design/region-measurement-2026-09-12.md`）は
6 つのゲートをすべて通したが、項目別に見ると住所だけが**悪化**していた:

| S1（21 枚 × 5 試行） | 対照のみ正解 | 介入のみ正解 | p（McNemar） |
|---|---|---|---|
| issuer_name / customer_name | 4 | **35** | < 1e-6 |
| issuer_address / customer_address | **18** | 5 | 0.011 |
| total_amount / document_no / document_date | 4 | 8 | 0.39 |

介入アームの住所は `followed`（候補の中から取った）なのに外れる: issuer_address が
followed 55 のうち不正解 30、customer_address が followed 31 のうち不正解 17、partial 12 は
すべて不正解。実機で値を見ると、外れ方の大半は**値の慣例**の食い違いだった:

- 「981-3205 仙台市泉区紫山3-1-4」── 郵便番号を付けている（正解は付けない）
- 「本社 981-3205 仙台市泉区紫山3-1-4」── 見出し語まで含めている
- 「東京都品川区北品川5-10-20」── 建物名を落としている（これは慣例ではなく本当の取りこぼし）

正解値の位置から起こした矩形は余白を持つので、隣の郵便番号の span が候補に混じる
（sample7 の customer_address の候補は「596-0006」「大阪府岸和田市」「春木若松町1026-56」）。
候補に従って郵便番号まで含めるか、逆に複数行の一部を落とすかで、正解の慣例から外れる。

ヒントの側でこれを直そうとした 2 つの版はどちらも別の揺れを生んだ。住所にヒントを渡さない版
（`address_field`、結果 (c)）では、ヒントを持たなくなった住所が今度は郵便番号を付け足す方向に
外れ（sample6 ← sample の issuer_address が 5/5 → 0/5）、説明文を中立にした版（結果 (d)）でも
依然 0/5 だった。**住所の成否は、ヒントの節の文言のわずかな違いで別の帳票が裏返る。**
計測の判定は「ヒントの機構ではなく住所の正規化の仕様（郵便番号・社屋名を値に含めるかを決め、
正規化器で揃える）を次にやる。ヒント側はいじらない」で確定した。

一方、これまでスキーマの住所項目は `string` 型で、正規化は NFKC と空白の畳み込みだけだった。
LLM が郵便番号を付けるかどうかはプロンプトの揺れに任せきりで、値の慣例をプロダクトのどこも
決めていなかった。正解データ（`golden/data/samples_ground_truth.json`）は 2 人のラベラーの
慣例（郵便番号なし・都道府県から建物名/階まで・見出し語なし）で揃っていたが、それが仕様と
して書かれた場所も無かった。

## 決定

### 1. 住所の型 `address_jp` を足し、値の慣例を正規化器で決める

`FieldType.ADDRESS_JP = "address_jp"` を追加し、`newfan_normalizers.builtin.norm_address_jp`
を登録する。値の慣例は次のとおり:

> **郵便番号なし・見出し語なし・都道府県〜建物名/階まで・番地の区切りは "-"・空白は半角英数字の
> 間にあるものだけ 1 つ残す。**

規則（順に適用）:

1. NFKC（全角英数字・全角ハイフン U+FF0D・全角空白を揃える）
2. 先頭の見出し語（住所／所在地／本社／本店／支社／支店／営業所／事業所／Address、
   区切りの `:` `：` は任意）と、先頭・末尾の郵便番号（`〒` は任意、`\d{3}\s*-?\s*\d{4}`
   ── ハイフンの周りの空白とハイフン落ちを許す、`〒` だけのものも）を、**剥がれなくなるまで**
   剥がす。「本社 981-3205 仙台市…」は見出し語の後ろに郵便番号が続くので、1 回ずつでは
   足りない。見出し語は**後ろに住所の本文か区切りが続くものだけ**剥がす（区切り／空白／
   `〒`／数字／末尾か、都道府県名か、3 文字までの市区町村郡名）。区切りを要求しないと
   「本社工場 愛知県…」「本社ビル 東京都…」「支店名: 東京都…」のような長い複合語の先頭
   2〜3 文字だけを剥がして「工場愛知県…」「名:東京都…」を作り、見出し語付きのままより悪い
3. 空白（全角含む）は、**両隣が半角英数字のものだけ 1 つの半角空白に畳み**、それ以外は除く。
   無条件に除くと「丸の内1-1-1 3F」（番地の直後の階数）が「丸の内1-1-13F」に、英字の住所
   「A-123 Sample.BLD」が「A-123Sample.BLD」に化けて別の住所になる（`string` 型の頃は 1 つの
   空白に畳んでいたので、これは後退になる）。日本語の住所の空白（「東京都 品川区」
   「9-9-9 ファッションビル」）は語の境界を担わないので除いてよい
4. 数字と数字の間のハイフン類（‐ ‑ ‒ – — ― − ー）を `-` に揃える。**数字に挟まれたものだけ**
   ── 長音「ー」は「タワー」「ビルディング」の一部でもあるので、無条件には置換しない
5. 何も残らなければ `None`

**建物名・階は削らない。** 正解の慣例がそうであり、「東京都品川区北品川5-10-20」のように
建物名が落ちた抽出値は慣例の問題ではなく本当の取りこぼしなので、正規化で隠してはならない
（隠すと計測が取りこぼしを見なくなる）。

値の形を変えるだけで導出はしないので `type_converted=False`（grounding の 0.85 に落とさない）、
`confidence_cap` も付けない。

結果は**不動点**（もう一度通しても変わらない）でなければならない。正解データの検査
（決定 2）と計測の採点（決定 3。プロダクトの `value_normalized` にもう一度通す）がそれを
前提にしていて、崩れるとプロダクトの出力と計測のキーが食い違う。郵便番号の中の空白を
許すのはこのため ── 許さないと「〒100 0001 東京都…」は 1 回目で `〒` だけが剥がれ、
2 回目で初めて `100 0001` が剥がれる。

郵便番号の末尾側は、本文と空白か `〒` で切れているものだけを落とす。「…町123-4567」のように
番地が 3 桁+4 桁で終わる住所を郵便番号と誤認して削らないための番人。先頭側は住所が 7 桁の
数字で始まることは無いので、区切りを要求しない（「141-0001東京都…」も剥がす）。

### 2. 正解データは正規形で持つ

`golden/data/samples_ground_truth.json` の住所は `norm_address_jp` の**不動点**にする
（`golden/scripts/check_gold_addresses.py` が検査し、`--fix` で揃える）。ラベラーの慣例
（郵便番号なし・建物名まで・見出し語なし）はそのままで、変わるのは全角英数字と
日本語の間の空白だけ（英字住所 sample30 の「A-123 Sample.BLD」の空白は残る）。
`golden/data/*.jsonl` の正解値はもともと「正規化後の表現で保持する」約束
（`newfan_golden.dataset` の冒頭）なので、これはその約束を住所にも適用しただけである。

### 3. 計測は両側を同じ正規化にかけてから比べる

`newfan_golden.region_ab` は住所の項目（名前が `_address` で終わるもの）を `address_jp` 型で
スキーマに載せ、採点では**抽出値と正解の両方**を `norm_address_jp` に通してから `norm_key`
で比べる。プロダクトの正規化と正解の慣例を同じ土俵に乗せるためで、正解側にも通すのは
「正解データの修正漏れ」で計測が歪まないための保険。

### 4. 住所らしい項目は既定で `address_jp`

dev のシード（`scripts/serve_gateway_dev.py`、`golden/data/schemas.json`）の住所項目を
`address_jp` にする。テンプレート化の画面とスキーマ管理画面には「住所(日本)」として並ぶ
（型の選択肢とラベルは `web/lib/fieldTypes.ts` の `TYPE_OPTIONS` に 1 か所で持ち、両画面が
それを使う）。
値の見た目からの型推測（`web/lib/fieldTypes.ts`）は `string` のままにする ── 都道府県名で
始まる社名（「東京都民銀行」）の誤推測が、そのまま保存されて次回の正規化に効いてしまう
（迷ったら `string` に倒す、という同ファイルの原則）。

## 影響

- **ヒントの機構は変えない。** `region_hint.py` とプロンプトは 1 バイトも触らない（計測の判定）。
  `address_jp` は `TYPED_FIELD_TYPES` に入れないので、読取領域ヒントの `type_mismatch` 判定では
  従来どおり `string` と同じ扱い（候補を型で落とさない）。
- **既存のスキーマは不変。** `string` 型のままの住所項目は従来どおり NFKC と空白の畳み込み
  だけ。`address_jp` に切り替えたテナントから、次回の抽出で新しい慣例が効き始める。
- **展開の順序: 先に orchestrator-worker と gateway を、このコミットを含むイメージにしてから、
  シード（`scripts/aws_env.sh seed-schemas`）や画面で `address_jp` を選ぶこと。**
  orchestrator は保存されたスキーマを `FieldSchema`（`type: FieldType`）で検証するので、
  `address_jp` を知らないイメージの worker に `address_jp` のスキーマが届くと、その doc_type
  の抽出は**すべて** pydantic の ValidationError → failed（E9001）になり、メッセージは
  再配信を繰り返す。gateway は `put_schema` で `FieldType` に無い型を E1003 で拒むので、
  gateway だけ新しく worker が古い、という組み合わせでも保存時に気づけるが、**逆
  （gateway が古い）は素通りする** ── 順序を守るしかない。
- **KIE のプロンプトは不変。** 型はスキーマ JSON に載るだけで、領域なしのプロンプトの
  スナップショット（G5）に影響しない。
- **計測の数字は変わり得る。** 「郵便番号を付けた」「本社を付けた」外れは正規化で消えるので、
  次の計測では住所の 対照のみ 18 / 介入のみ 5 は縮む見込み。ただし「建物名を落とした」外れは
  残る（残すのが正しい）。第 3 回の数字は取り直さない。
- 正解データの修正は全角英数字と空白だけ（`check_gold_addresses.py` の出力をコミットログに
  残す）。派生フィクスチャ（`region_ab_s*.jsonl` / `*_goldspec.json`）は
  `build_region_fixtures.py` で作り直す。位置探索（`region_from_gold`）は `norm_key` で比べる
  ので、領域の起こし方は変わらない。

## やらないこと

- **郵便番号の `〒` を `T` と誤読した値（「T222-0001 仙台市…」）の救済。** OCR の誤読の補正は
  正規化器の責務ではない（日付の正規化器が `T222-0001` を大正の日付と読まないよう番人を置いた
  のと同じ向き）。実測で頻出するなら別途。
- **都道府県名の補完**（「仙台市泉区紫山3-1-4」に「宮城県」を足す）や住所の分解（都道府県／
  市区町村／番地／建物）。慣例を揃えるだけで、住所の意味解析はしない。
- **建物名の有無の同一視。** 正解が建物名まで持つ以上、落とした値は不正解でよい。
- **ヒントの説明文で住所の慣例を教えること。** 第 3 回の (b)〜(d) で、説明文の例示が
  別の帳票を裏返すことを見た。慣例は決定論の側（正規化器）で持つ。
