# 実測記録（第 3 回）: 反証可能な読取領域ヒント

2026-09-12。実スタック（実 PaddleOCR + 実 Gemini 2.5 Flash、ローカル compose）。
設計は `region-field-add-and-hint-v2.md`（第 2 版）。判定は同 §3 の G1〜G6。

## 第 2 回から何を変えたか

第 2 回の失敗は「領域が 1 行ずれると、ヒント無しなら正解していた値が壊れる
（sample8 の customer_name 3/3 → 0/3、返った値は隣の行の『大熊邸』）」だった。
ヒントが座標だけなので、モデルにはそこに何があっても従う以外の選択肢が無かった。

今回のヒントは**矩形を渡さない**。渡すのは:

| 渡すもの | 中身 | 目的 |
|---|---|---|
| `candidates` | 領域に掛かる span の id と原文（中心が矩形内、または重なり 30% 以上。重なり面積順で最大 12 件） | モデルが照合するのは座標ではなく span |
| `example_value` | テンプレート元の帳票で、その位置にあった span の原文（最大 200 字） | 「前回ここには『株式会社千曲川ホーム』があった」と伝える |
| `example_present` | 例示値が候補の中にあるか（正規化して比較） | 同じ雛形かどうかの手がかり |

さらに、渡す**前**に落とす（`metrics.region.hints.dropped` に理由を残す）:

| 理由 | いつ |
|---|---|
| `page_out_of_range` / `page_unprojectable` | テンプレートのページがこの帳票に無い／寸法が取れない |
| `no_spans_in_region` | その位置に文字が無い |
| `overlaps_exclude` | 除外領域と重なる |
| `type_mismatch` | 候補のどれも項目の型（金額・日付など）として解釈できない |
| `kind_conflict` | 例示値と候補の**種類**（会社／人名／建物／住所／金額／日付／番号）が食い違う |

渡した**後**は、モデルが返した `span_ids` と候補の集合演算で `followed` / `partial` /
`rejected` / `no_evidence` を付ける（モデルの自己申告ではない）。

設計の原則は**非対称性**: ヒントを誤って落としても対照の挙動に戻るだけで、誤って
渡すと正解を壊す。迷ったら落とす。

### 効いたこと

**テンプレートの転用（S2）が有意になった。** 第 2 回は 5 枚中 4 枚で改善したが p = 0.33
だった。今回は 5 枚すべてで改善し（+1 / +7 / +1 / +9 / +1）、p < 0.001。項目別では
total_amount 16 → 23、issuer_name 5 → 10、customer_address 5 → 9。

**「1 行ずれ」は守れた（G3）。** 第 2 回で 3/3 → 0/3 に壊れた sample8 の customer_name は、
例示値「株式会社千曲川ホーム」と候補「大熊邸」の種類が合わないと判定され、5 試行すべて
渡す前に落ちた（`kind_conflict`）。対照と同じ 5/5。**ヒントを反証可能にする**という
設計の狙いは、この直接の再現ケースで成立した。

**間違ったテンプレートを当てても、全体では害にならない（S3）。** 65 の領域つき項目 × 5 試行
のうち、渡す前に落としたのが 170（文字が無い 130、種類が合わない 40）、渡した 125 のうち
モデルが従わなかった（rejected）のが 69。従ったのは 41 で、そのほとんどは
別雛形でもたまたま同じ位置にある項目（日付・番号）だった。McNemar は 11 / 11 で完全な引き分け。

### 効かなかったこと ── 3 つのゲートが落ちた理由

**1. sample27 ← sample29 の −4 は、ヒントを持たない項目で起きた。**
この帳票で落ちたのは issuer_address（対照 5/5 → 介入 1/5）だが、issuer_address の
ヒントは `no_spans_in_region` で**渡す前に落ちている**。つまりモデルが受け取った
issuer_address の定義は対照と同一で、違うのはプロンプト末尾のヒント説明文と、他の
2 項目（customer_name・document_no）に付いた `region_hint` だけである。

実機で確かめると、介入アームは issuer_address を「東京都品川区北品川5-10-20」（span 1 つ）と
返し、対照は「東京都品川区北品川5-10-20 サンプルビル2F」（span 2 つ）と返す。同じ帳票を
4 回回して介入は 1 回しか 2 行目を含めなかった。**ヒントの説明文が、ヒントの無い項目の
読み方（複数 span をまとめるか）まで変えていた** ── 波及である。

**2. S1 が有意にならなかったのも同じ現象と整合する。** 介入だけ外した 7 対のうち 5 対が
住所（customer_address 3、issuer_address 2）で、いずれも `followed`（候補の中から取った）
なのに不正解 ── 候補の一部だけを取って住所を切り詰めている。第 2 回の介入（全 span に
bbox）ではこの切り詰めは起きていない。

**3. G4 の −1 は 218 対のノイズの範囲だが、ゲートは「0 以上」を要求している。**
落とした／捨てた項目の正解率が対照と同じなら差は 0 を中心に散らばるので、
このゲートは効果が無くても半分の確率で落ちる。**ゲートの設計が悪い**（第 2 版の自分の
設計）。ただし、同じデータで閾値を緩めるのは過適合なので、ここでは落ちたまま記録する。

### 判定 (a): 既定 off のまま。ただし原因は特定できた

失敗の原因は「ヒントが正解を壊す」（第 2 回）ではなく、**「ヒントの説明文が、ヒントの
無い項目にまで波及する」**である。反証可能にする機構そのものは S2・G3・S3 で狙いどおりに
働いた。

住所の介入アームの内訳は、issuer_address が followed 55（正解 25・不正解 30）、
customer_address が followed 31（正解 14・不正解 17）・partial 12（すべて不正解）。
**候補の中から取っているのに外れる。** 正解値の位置から起こした矩形は余白を持つので、
隣の郵便番号の span が候補に混じる（sample7 の customer_address の候補は
「596-0006」「大阪府岸和田市」「春木若松町1026-56」）。候補に従って郵便番号まで含めるか、
逆に複数行の一部を落とすかで、正解の慣例（郵便番号を含めず建物名は含める）から外れる。
sample7 は対照が 3 span を連結して正解するのに対し、介入は 5 試行中 5 回外した
（値は帳票を消しているため残っていない。実機で回し直すと正解することもある）。

第 2 回でも住所は S1・S2 を通して一度も改善せず、設計 §4.4 は「同じデータで『住所だけ
外す』と決めるのは過適合。第 3 回で再度見る」としていた。別データ（第 3 回、5 試行）でも
同じ向きで、今度は有意に悪い。そこで**住所にはヒントを渡さない**版（`address_field`）を
試した ── 結果は (c) / (d) のとおりで、**採らなかった**。

## 結果 (c): 住所にヒントを渡さない版で S3 を回し直す → 説明文の例示が裏目に出た

`address_field` を入れて S3 の介入アームを回し直すと、**ヒントを持たなくなった住所が
今度は逆方向に外れた**: sample6 ← sample の issuer_address が 対照 5/5 → (b) 3/5 → (c) **0/5**、
sample2 ← sample13 が 3/5 → 4/5 → **0/5**。実機で値を見ると「981-3205 仙台市泉区紫山3-1-4」──
郵便番号を付けている（正解の慣例は郵便番号を含めない）。

原因は (b) で足した説明文そのものだった。「値が複数の span にまたがるとき（住所と建物名の
2 行、姓と名など）はすべて含めよ」は、切り詰めを止める代わりに、**例に挙げた住所だけ**
普段は含めない郵便番号まで付け足す方向へ働いた。(b) では住所にヒント（候補）があったので
候補に従って隠れていたが、ヒントを外した途端に表に出た。

**項目の種類を例に挙げると、その種類の読み方だけが変わる。** 説明文は「切り詰めるな」と
「付け足すな」を対にし、値の範囲は本文の指示 1〜5 で決めると書き直した（種類の例は
挙げない）。S3 の残りと S2 / S1 は回さずに打ち切り、(d) へ。

## 結果 (d): 説明文を中立にしても、ヒントの無い住所は揺れる

(c) の説明文を「切り詰めるな・付け足すな」の対にして種類を挙げない版で S3 を回し直した。
sample6 ← sample の issuer_address は依然 **0/5**。実機で対照と介入を交互に回すと、対照は
「仙台市泉区紫山3-1-4」（2/3 正解）、介入は「本社 981-3205 仙台市泉区紫山3-1-4」（0/2）──
**同じ 1 つの span の原文をそのまま返す**ようになる。ヒントの節が「span の原文」を強調する
ため、ヒントの無い項目でもモデルが原文に忠実になり、正解の慣例（郵便番号と「本社」を含め
ない）から外れる。sample4 ← sample19 では 1 試行だけ 7 項目すべて外す出力もあった。

つまり **住所の成否は、ヒントの節の文言のわずかな違いで別の帳票が裏返る**:

| 版 | 説明文 | ヒントの無い住所で起きたこと | どの帳票 |
|---|---|---|---|
| (a) | 設計どおり | 2 行目（建物名）を落とす | sample27 |
| (b) | ＋「複数の span はすべて含めよ（住所と建物名…）」 | 起きない（住所にはヒントがあり候補に従う） | — |
| (c) | (b) ＋ 住所にヒントを渡さない | 郵便番号を付け足す | sample6, sample2 |
| (d) | (c) の説明文を中立に | span の原文をそのまま（「本社」「郵便番号」付き） | sample6, sample2 |

住所は「郵便番号・建物名・社屋名のどこまでを値とするか」の慣例が細く、ヒントの節の存在
そのものがモデルの忠実度を動かす。(c) と (d) は S3 の 1〜2 帳票で純減 −3〜−5 になり G2 を
落とす。残りのアームは回さずに打ち切った。

## 判定: (b) を出す（既定 on）。住所は仕様の問題として残す

**出荷するのは (b) の状態**（説明文の適用範囲を明示した版、住所にもヒントを渡す）。
6 つのゲートをすべて通したのは (b) だけである（S1 は 5 試行）。

| ゲート | (b) | 根拠 |
|---|---|---|
| G1 | ✅ | S1（21 × 5）26 / 48 / p = 0.014 |
| G2 | ✅ | S3 12 / 12 / p = 1.0、帳票ごとの純減は −2 まで |
| G3 | ✅ | sample8 customer_name を 5/5 `kind_conflict` で守った |
| G4 | ✅ | 落とした／捨てた 238 対で +4 |
| G5 | ✅ | 領域なしプロンプトはスナップショットとバイト一致 |
| G6 | ✅ | 介入プロンプトは第 2 回の介入より 4,400〜4,800 字短い |

第 2 回で出せなかった理由 3 つは、それぞれこう解消した:

1. **ずれた領域が正解を壊す** → 例示値と候補の種類判定で渡す前に落とす（G3 で直接再現、
   S3 で 40 件が `kind_conflict`）。渡したヒントの半分以上をモデルが捨てる（S3 で 68 / 125）。
2. **領域はずれる** → ずれても対照と同じ正解率に留まる（S3 で 12 / 12）。
3. **壊れたことに誰も気づけない** → 従った／捨てた／落とした理由と、例示値・候補の原文を
   検証画面に参考表示する（`metrics.region.hints`）。

**住所の扱い（残す問題）。** (b) の S1 で住所は 対照のみ 18 / 介入のみ 5（p = 0.011）と悪い。
ただし外れ方の多くは「郵便番号や『本社』を含めるか」という**値の慣例**の問題で、S1 の
候補には郵便番号の span が矩形の余白に入りやすい。S2（転用）では住所は 0 / 2 で悪化して
いない。住所にヒントを渡さない版は (c) / (d) のとおり別の揺れを生むので採らない。
次にやるべきは、ヒントの機構ではなく**住所の正規化の仕様**（郵便番号・社屋名を値に含めるか
を決め、正規化器で揃える）である（設計 §4.4 は据え置き、根拠を更新）。

**計測の限界（正直に書く）。**

- (b) 以降は対照アームを (a) の行から再利用した（`--resume`）。設計の手順は 2 アームを
  交互に回して時間帯の揺れを散らす前提だったので、(b) の S3 / S2 と S1 の試行 0〜1 は
  対照と介入の時刻が離れている（S1 の試行 2〜4 は両アームを交互に回した）。実機で同じ
  帳票を交互に回すと対照も 1/3 で外す（sample6）程度には揺れる。第 4 回からは
  `region_ab` がこの使い方（片方のアームの丸ごと再利用）を止める（「再実行の手順」）。
- S1 の 5 試行への延長は結果を見てから決めた（2 試行で p = 0.21）。1 回だけ・5 試行固定と
  先に決めて回し、それ以上は足していない。
- G4 の閾値「0 以上」は効果が無くても半分の確率で落ちる設計だった（設計 §3 に注記）。
  今回は +4 で通ったが、次回から「有意に悪くならない」に改める（`eval_gates_v2.py` を
  改めた。落とした／捨てた対の McNemar で判定する。第 4 回から適用）。
- LLM 側の失敗（JSON 契約違反 / 要素 null / fields 配列だけ）で対が欠けたものは、
  修正して埋めた（`kie.py` / `adapter.py` の 3 件。ヒント機能とは無関係の既存の欠陥）。


## 再実行の手順

第 3 回は手順をその場のシェルで組んで回した（(a)〜(d) と延長で 5 本）。第 4 回からは
`golden/scripts/run_region_arms.sh` で **3 アームを同じ手順で** 回す。手順の要点は
スクリプトの頭に書いてある: アームごとに「領域を起こす（出力があれば飛ばす）→ 位置依存
項目と合わせる（S1 は例示値を落とす）→ `region_ab` で対照と介入を**同じ試行で交互に**回す」。
交互に回すのが手順そのもの（時間帯の揺れを両条件へ散らす）。

```bash
# 1. 正解データからフィクスチャを組み立てる（S1 / S2 / S3、例示値つき）
uv run python golden/scripts/build_region_fixtures.py

# 2. worker のヒントが有効なことを確認する（既定 on。REGION_KIE_HINTS を off にしていないこと。
#    対照アームはフラグの影響を受けない）
docker compose --env-file .env -f deploy/compose.yaml up -d --no-deps orchestrator-worker

# 3. 3 アームを回す（S3 → S2 → S1。S3 / S2 は 5 試行、S1 は --trials-s1、既定 5）。
#    --out は計測ごとに新しくする（第 4 回なら out/phase4、第 5 回なら out/phase5）
golden/scripts/run_region_arms.sh --api http://localhost:8000/v1 --token "$JWT" \
  --out out/phase4 [--trials-s1 5] [--structure http://localhost:8081]

# 4. ゲートを判定する
uv run python golden/scripts/eval_gates_v2.py \
  --s1 out/phase4/s1_ab.json --s2 out/phase4/s2_ab.json --s3 out/phase4/s3_ab.json \
  --md out/phase4/gates.md
```

**今回（第 3 回）の出力は次回の `--resume` に渡せない。** ADR-0007 で住所の採点規則が
変わり（郵便番号・見出し語を落としてから比べる）、出力 JSON に採点規則の印 `scoring` が
入るようになった。印が無い今回の出力から欠けた対だけ埋めると 1 つの McNemar 表に 2 つの
規則が混ざるので、`region_ab` は拒む。次回は全件を回し直す。
**対が欠けたとき（LLM 側の失敗で捨てた試行）** は、同じ `--out` でスクリプトをもう一度
回す。`<arm>_ab.json` があれば `region_ab --resume` に渡して**欠けた (帳票, 試行, アーム)
だけ**を埋める（元は `<arm>_ab_prefill.json` に残る）。
**対が欠けたとき（LLM 側の失敗で捨てた試行）や試行数を延ばすとき** は、同じ `--out` に
**`--resume` を付けて**スクリプトをもう一度回す。欠けた対のあるアームだけ `<arm>_ab.json` を
`region_ab --resume` に渡して**欠けた (帳票, 試行, アーム) だけ**を埋める（元は
`<arm>_ab_prefill.json` に残る）。欠けた対の無いアームは回さず、出力も書き直さない。

**前回の出力がある `--out` に `--resume` なしで回すと止まる**（exit 2）。完全な出力を
`region_ab --resume` に渡すと 1 件も抽出せずに同じ行を書き直し、前回の結果が新しい計測に
化ける（mtime だけ新しくなる。出力にはどの worker / プロンプトで回したかが残らないので、
後から見分けられない）。worker やプロンプトを変えて測り直すときは**別の `--out`** にする。

**片方のアームを丸ごと再利用してはいけない。** 第 3 回の (b) は対照アームを (a) から
再利用して介入だけ回し直した（上記「計測の限界」）。これは対照と介入の時刻が離れ、
時間帯の交絡が入る。第 4 回からは `region_ab` が、`--resume` の出力にある帳票の片方の
アームが 1 行も無いとき**止める**（`--allow-arm-reuse` を付けたときだけ通し、出力に
`resume_arm_reuse: true` と帳票ごとの再利用したアームが残って `eval_gates_v2` が先頭に
「⚠ 片方のアームを再利用した計測（時間帯の交絡あり）: S3（対照 12 帳票）」のように出す。
この印は、その出力を `--resume` に渡した実行にも引き継がれる ── 欠けた対の埋め直しや
試行の延長で消えることはない）。プロンプトを変えて介入だけ見直したいときも、
**両アームを回し直す**（別の `--out` にする）。
