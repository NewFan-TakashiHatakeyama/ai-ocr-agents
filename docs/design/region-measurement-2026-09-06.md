# 実測記録: 読取領域ヒント（Phase 4）と位置ガード（Phase 5）

2026-09-06。実スタック（実 PaddleOCR + 実 Gemini 2.5 Flash、ローカル compose）で計測した。

設計の約束は次の 2 つで、**どちらも「実測で示せたら出す」**という形になっている。

- Phase 4: 「fixture ベースの精度計測（region 有無での field 正解率比較）を通過した場合のみ出荷」
- Phase 5: 「shadow 実測に基づき許容パラメータを確定し、誤 mismatch 率が許容水準であることを確認してから有効化」

## 結論（先に）

| | 判定 | 既定 |
|---|---|---|
| Phase 4 読取領域ヒント | **出荷しない** | `REGION_KIE_HINTS` = off |
| Phase 5 位置ガード有効化 | **有効化しない**（機構は検証済み） | `REGION_GUARD_ENFORCE` = off |

実装と計測ツールは入れた。フラグを立てれば動く。**どちらも「良くなる」ことを示せなかった**ので、
設計の約束どおり既定は off のままにする。

---

## Phase 4: 読取領域を KIE のヒントとして渡す

### 何を測ったか

同じ帳票・同じ項目定義で、**`region` の有無だけ**が違う 2 版のスキーマを作り、対照（領域なし）と
介入（領域あり）を**交互に**回した。交互にするのは、時間帯によるモデル側の揺れを両条件へ
均等に散らすため。ツールは `golden/src/newfan_golden/region_ab.py`。

fixture は `golden/data/region_ab.jsonl`。中核は **sample2.png の発行元 vs 宛先**で、
どちらも会社名、語彙では区別できず、紙面上の左右でしか決まらない（請求書として最も普通の形）。
設計が要求する「位置でしか特定できない項目」はこれに当たる。

### 結果（試行 5 回／アーム）

| | 全体 exact match |
|---|---|
| 対照（領域なし） | **0.864** |
| 介入（領域あり） | **0.780** |

項目ごと（`◆` は位置依存）:

| 項目 | 対照 | 介入 |
|---|---|---|
| ◆ issuer_name（発行元・右） | 3/4 | **5/5** |
| ◆ customer_name（宛先・左） | 1/4 | **2/5** |
| ◆ issuer_address | 3/4 | **1/5** |
| ◆ customer_address | 3/4 | **1/5** |
| ◆ addressee_name（見積書） | 5/5 | 5/5 |
| ◆ quote_total_amount | 5/5 | 5/5 |
| invoice_no | 4/4 | 5/5 |
| total_amount | 4/4 | 5/5 |

### 読み取り

- **会社名（issuer_name / customer_name）は改善方向**に動いた。狙った効果は出ている。
- **住所（issuer_address / customer_address）は悪化**した。左右の会社名ブロックは近接して
  いるため、住所行の矩形が隣ブロックを巻き込みやすい。ヒントが誤誘導になったと読める。
- 見積書（sample.png）は対照でも全問正解で、**改善の余地がない**（天井）。
- 全体では悪化。

### 判定: 出荷しない

「改善が確認できた場合のみ出荷」という条件を満たしていない。項目によって上下が割れており、
全体では下がっている。したがって `REGION_KIE_HINTS` は既定 off のままとする。

### この計測で言えないこと（正直に）

- **有効な文書が実質 1 件**しかない。sample.png は天井で情報を持たず、判断はすべて
  sample2.png 1 枚に乗っている。ここから母集団の傾向は言えない。
- **試行 5 回はノイズに対して少なすぎる**。対照アームの invoice は 2/6 〜 6/6 まで振れており、
  この分散の中で ±1〜2 件の差は区別できない。「悪化した」も強くは言えない（「改善は示せない」
  までしか言えない）。
- 住所の悪化が「ヒントの本質的な害」なのか「私が引いた矩形が雑だった」のかを分離していない。
  矩形は実検出位置に 2% のゆとりを足しただけで、人が引く矩形より機械的である。
- 対照アームには **span の bbox が載っていない**。介入アームは「矩形の注入」と「全 span への
  座標付与」の 2 つを同時に受けており、差がどちらに由来するかを分離していない。

### 出荷するなら次に何が要るか

1. **評価データを増やす**。位置でしか区別できない項目を含む帳票が最低でも 10 枚は要る。
   いまの 2 枚では何回回しても解像度が上がらない。
2. 「矩形の注入」と「span への座標付与」を**別々のアーム**で測る（`kie_extract` に
   span 座標だけを載せる経路を足す）。
3. 住所のような**近接ブロックの項目**を別建てで見る。会社名は効いて住所は効かない、という
   のが本当なら、ヒントを出す項目を絞るという設計もあり得る。

## Phase 5: 位置ずれ検知の本番有効化

### 何を測ったか

ツールは `golden/src/newfan_golden/region_guard_shadow.py`。誤検知率だけでは足りない
（誤検知 0 でも検知力 0 なら有効化する意味が無い）ので、3 つのアームを回す。

| アーム | 領域の置き方 | 何を測るか |
|---|---|---|
| aligned | 実検出位置から生成（正しい） | **誤検知**。ここで出る mismatch は全て偽陽性 |
| shifted_all | 全項目を縦に 12% ずらす | 「別レイアウトの帳票が来た」ケース |
| shifted_one | **1 項目だけ**ずらす | 有効化して初めて挙動が変わる経路（per-field レビュー） |

### 結果（各アーム 6 run / 判定対象 30 項目）

| アーム | mismatch | 率 | doc レベル「別レイアウト」判定 |
|---|---|---|---|
| aligned | 0 / 30 | **0.00** | 0 / 6 |
| shifted_all | 30 / 30 | **1.00** | **6 / 6** |
| shifted_one | 6 / 30 | 0.20 | 0 / 6 |

### 読み取り: 機構は設計どおりに動いている

- **正しい領域では 1 件も誤検知しない。**
- **全項目がずれると 100% 検知し、同時に doc レベルで「別レイアウト」と判定して
  per-field のレビューを抑止する。** これは設計の意図どおり（取引先 B の帳票を
  全件レビュー化させないための判断）。
- **1 項目だけずれた場合は、その 1 項目にだけ所見が付き、doc レベル判定は働かない。**
  有効化したときに実際に増えるのはこの経路で、狙いどおりに動いている
  （設計 C33 が要求した「n≤2 のスキーマで per-field レビューが出ること」も、
  この経路が生きていることで満たされる）。

### 判定: それでも有効化しない

機構は検証できたが、**許容パラメータを決める材料が無い**。

このテストの `aligned` 領域は**実際の検出位置から機械的に生成**しており、人が UI で
手描きした矩形より遥かに正確である。したがって誤検知 0.00 は「実運用での誤検知率」を
まったく予測しない。実利用者の矩形は数十 px ずれるし、スキャンの傾きや別紙面の
差もそこに乗る。

許容パラメータ（`REGION_GUARD_PAD_PAGE_RATIO=0.05` / `REGION_GUARD_PAD_SIDE_RATIO=0.50` /
`REGION_GUARD_MIN_FIELDS_FOR_LAYOUT=3`）をこの規模のデータで動かすと過適合になる。
**実運用で領域付きの帳票が貯まってから**、shadow が書き続けている
`metrics.region.mismatch_fields` を集計して決めるのが正しい順序。
shadow のまま出荷しているのはそのためで、集計に必要な数字は既に永続化されている。

### 有効化の判断に必要なもの

1. 実運用で**人が引いた矩形**を持つ run を、doc_type をまたいで数十件。
2. その中で「正常な帳票なのに mismatch が付いた」割合（＝運用上の誤検知率）。
   これが数 % を超えるならレビュー工数が増えるだけなので、まず許容幅を広げる。
3. 逆に、**本当に別レイアウトだった帳票**で `layout_mismatch` が立っているかの確認。

## 実測値

計測の生データは以下に出力される（リポジトリには入れない。顧客データではないが、
環境依存の数字を正としてコミットすると次回の実測を歪めるため）。

- Phase 4: `newfan_golden.region_ab --out <path>`
- Phase 5: `newfan_golden.region_guard_shadow --out <path>`

再実行の手順:

```bash
# worker 側でヒントを有効にしてから A/B を回す（対照アームはフラグの影響を受けない）
REGION_KIE_HINTS=1 docker compose --env-file .env -f deploy/compose.yaml up -d --no-deps orchestrator-worker
PYTHONPATH=golden/src python -m newfan_golden.region_ab \
  --gold golden/data/region_ab.jsonl --regions golden/data/region_ab_regions.json \
  --api http://localhost:8000/v1 --token "$JWT" --trials 5 --out out/region_ab.json

# 位置ガードは shadow のままで測れる（ヒントの有無と独立）
PYTHONPATH=golden/src python -m newfan_golden.region_guard_shadow \
  --gold golden/data/region_ab.jsonl --regions golden/data/region_ab_regions.json \
  --api http://localhost:8000/v1 --token "$JWT" --trials 3 --out out/guard_shadow.json
```
