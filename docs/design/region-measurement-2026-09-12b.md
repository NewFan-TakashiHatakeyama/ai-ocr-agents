# 実測記録（第 4 回）: 住所の慣例・手順・候補の並び順

2026-09-12（夕方〜）。実スタック（実 PaddleOCR + 実 Gemini 2.5 Flash、ローカル compose）。
設計は `region-field-add-and-hint-v2.md`、判定は同 §3 の G1〜G6（G4 は本回から新定義）。

## 第 3 回から変えたこと

| # | 変更 | どこ |
|---|---|---|
| A1 | **住所の正規化仕様**を決めた（ADR-0007）。型 `address_jp` を足し、郵便番号・見出し語を落として都道府県〜建物名/階まで、空白なし・番地の区切りは `-` に揃える。正解データも同じ形に直し、採点は両アームともこの正規化を通す | `packages/normalizers`、`golden/`、seed |

| A3 | **交互実行の手順を守る**。`--resume` は欠けた対の補充だけに使い、片方のアームの丸ごと再利用は `region_ab` が止める（第 3 回 (b) は対照を再利用していた）。3 アームを 1 本で回す `golden/scripts/run_region_arms.sh` | `golden/` |

A4 の効果を分けて見るため、2 サイクル回す: **サイクル 1 = A1〜A3**（候補は面積順のまま）、
**サイクル 2 = A1〜A4 ＋ 丸写しの取り直し**。どちらも 3 アームを両アーム交互に全件回す
（S1 21 × 5、S2 5 × 5、S3 12 × 5 = 380 抽出／サイクル）。

## 手順で踏んだこと（正直に書く）

- **サイクル 1 の最初の実行は捨てた。** 計測ランナーはアームごとに新しい python を起動し、
  `golden/src` をその時点の作業ツリーから読む。計測中にメインの checkout で別ブランチへ
  切り替えたため、S3 が旧採点規則（住所の正規化なし・`scoring` 印なし）で走った。
  以後、計測中はメインの checkout を触らず、他の作業は `git worktree` に出した。
  捨てた S3（両アーム交互・旧採点）は第 3 回 (b) の再現実験として残す（下記）。
- サイクル 1 の S3 で介入アームの 2 試行が**全項目外れ**（6/6・5/5 が 0）だった。丸写しの
  空抽出である（対照には無い）。これが 2 帳票の純減 −5・−6 の正体で、修正はサイクル 2 から。

## 第 3 回 (b) の再現実験（両アーム交互、旧採点規則）

第 3 回 (b) の S3 は「対照と完全に引き分け（12 / 12）」だったが、対照を (a) から再利用して
いた。両アームを交互に回し直すと **対照のみ 25 / 介入のみ 14（p = 0.108）**、帳票ごとの純減は
最大 −8。引き分けは再現しなかった。**対照の再利用は楽観に振れる**（時間帯の交絡）。
これが A3 の根拠。

### 住所は「悪化」から「改善」に転じた（A1 の効果）

第 3 回の S1 で住所は 対照のみ 18 / 介入のみ 5（p = 0.011）と悪かった。ADR-0007 の正規化を
両アームに掛けると、S1 の issuer_address は 42 → 47、customer_address は 40 → 50 と
**介入が上回る**。S2 の customer_address は 15 → 25。第 3 回で「住所だけ外す」を採らなかった
判断（実測記録 §判定）は正しく、悪化の正体は郵便番号・社屋名を値に含めるかの慣例だった。

S1 全体は 8 / 72 で、第 3 回（26 / 48）より差が開いた。対照 0.711 → 介入 0.808。

### S3（間違ったテンプレート）は引き分けにならない

両アームを交互に回すと、S3 は 対照のみ 25 / 介入のみ 16 で介入がやや悪い（p = 0.21、有意では
ない）。第 3 回 (b) の「12 / 12」は対照再利用の楽観だった。内訳:

- 介入アームの 2 試行（sample16 ← sample19 の試行 0、sample13 ← sample2 の試行 4）が
  **全項目外れ**。run の値は残っていないが、対照に 1 件も無く、ヒント付きスキーマの丸写し
  （value の無い配列を空の抽出として通す）が原因である。この 2 試行で純減 −5 と −6 が出る。
  サイクル 2 から E3002 で取り直す。
- それを除いた害は、渡したヒントをモデルが捨てた（rejected 63 / 125）あとに別の場所を取る
  ことと、ヒントの無い項目への波及で、issuer_name（40 → 33）に集中する。

### A4（読み順で渡す）は採らない

サイクル間は対応の無い比較だが、S1 は介入だけ正解の対が 72 → 57 に減り、対照だけ正解が
8 → 12 に増え、S3 は 25 / 16 → 27 / 13 と悪化側に動いた。改善の兆しが無く、読み順に
並べ替えたことで**大きな枠では本命が後ろに来る**（設計 §2.5 R17 が読み順を退けた理由）。
候補は従来どおり重なり面積順のまま（revert）。

### 全項目外れの正体は「丸写し」だけではなかった

サイクル 2 でも介入アームの 2 試行が全項目外れになった。実機で同じ帳票（sample4 ← sample19）
を 4 回回すと、1 回は **fields が空の「成功」**（value=null の項目すら無い）が返った。
丸写しの取り直しだけでは足りない。スキーマに項目があるのに fields が空の出力は契約違反
（出力スキーマは「見つからなければ value=null」を要求する）として E3002 で取り直すように
した（自動発見では 0 件も正当なので対象外）。**両方の取り直しを入れた worker で S3 だけ
回し直す**（サイクル 3、下記）。

## 再実行の手順

```bash
# worker はヒント既定 on。プロンプト／コードを変えたら build → up で入れ替える
docker compose --env-file .env -f deploy/compose.yaml build orchestrator-worker
docker compose --env-file .env -f deploy/compose.yaml up -d --no-deps orchestrator-worker

# 3 アームを両アーム交互に全件（S1 は 5 試行）。計測中はメインの checkout を触らない

  --out golden/out/phase4r4/c2 --trials-s1 5

# 欠けた対の補充だけ（片方のアームの丸ごと再利用は止まる）

# ゲート判定
uv run python golden/scripts/eval_gates_v2.py \
  --s1 golden/out/phase4r4/c2/s1_ab.json --s2 .../s2_ab.json --s3 .../s3_ab.json --md .../gates.md
```
