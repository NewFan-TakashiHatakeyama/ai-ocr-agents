## 0. 最初に — 調査の焦点をどこに置くか

「Dify のようなドラッグ&ドロップでワークフローを組めるか」が出発点の問いですが、
**D&D エディタ自体は、この機能の中で最も不確実性が低い部分**です。

| 要素 | 不確実性 | 理由 |
|---|---|---|
| D&D エディタ（SCR-07） | **低** | React Flow 等の成熟した既製品がある。Dify も n8n も Flowise もこれで作られている（要確認 → Q3） |
| **実行エンジン** | **高** | 数日単位の HITL 待ち・マルチテナント・ECS の使い捨てタスク・"使う時だけ up" 運用を同時に満たす必要がある |
| **既製エンジンの流用可否** | **高** | ライセンスとマルチテナントの制約次第で、作るか借りるかが根本から変わる |
| **DB 書込みの安全性（DD-12）** | **中** | 顧客の基幹 DB へ書く。設計は決まっているが実現手段の検証が要る |

したがって調査の主眼は **「エディタをどう作るか」ではなく「エンジンを作るか借りるか」**
に置いてください。ここの判断が、工数を 1 桁変える可能性があります。

## 1. 我々の制約（ここが他社事例と違う。調査時に必ず当てはめてください）

既製品の評価をする際、以下に照らして「使えるか」を判断してください。
一般的な「良い/悪い」ではなく、**この制約下で成立するか**が知りたいことです。

| # | 制約 | 出所 | 効いてくる場面 |
|---|---|---|---|
| C1 | **マルチテナント SaaS**。1 インスタンスに複数顧客。PostgreSQL の RLS でテナント分離（`ENABLE`+`FORCE`、アプリは非所有ロールで接続） | §7.3 | 既製エンジンが自前の DB スキーマを持つ場合、RLS をどう効かせるか。効かないなら顧客ごとにインスタンス分離が要る＝コスト構造が変わる |

| C3 | **「使う時だけ up、終わったら destroy」** の運用。稼働 $0.766/h、月 4 回 × 8h で約 $28 | 利用者の明示要件 | **常駐が必要なコンポーネントは運用と根本的に相性が悪い**（→ Q6） |

| C8 | Web は Next.js 15（App Router, standalone 出力） | 実装済み | エディタの埋め込み先 |

### Q1【最優先】既製ワークフローエンジンを組み込めるか — ライセンス

**知りたいこと**

Dify / n8n / Windmill / Flowise / Temporal / Prefect / Argo Workflows / Kestra 等について、
**「マルチテナント SaaS の一機能として組み込んで顧客に提供する」ことがライセンス上可能か。**

**なぜ効くか**

C1（マルチテナント SaaS）に直撃します。OSS でも「自社利用は可、第三者へのサービス提供は不可」
という条項を持つものがあります（n8n の Sustainable Use License、Dify のライセンス追加条項など。
**これは伝聞であり、一次情報での確認が必要です**）。ここが NG なら、その候補は
検討の土俵に上がりません。**技術評価より先に、これを潰してください。**

**何をもって答えとするか**

- 候補ごとに、**ライセンス原文の該当条項の引用**（URL とリビジョン付き）
- 「マルチテナント SaaS への組込み」が可否どちらか、および**根拠となる条文**
- 商用ライセンスがある場合、その価格体系（テナント数課金か、収益シェアか）
- 判断に迷う場合は「法務確認が要る」と明記（自己判断で白黒つけない）

**期待する成果物**: 候補 × 可否 × 根拠条文 の表。NG の候補は以降の調査から除外。

---

### Q2【最優先】既製エンジンは我々のマルチテナント分離に載るか

**知りたいこと**

Q1 を通過した候補について:

1. エンジン自身が持つ DB スキーマは何か。我々の PostgreSQL に同居させられるか
2. **テナント分離をどう実現するか**。エンジン側に tenant の概念があるか、無いなら
   RLS（`current_setting('app.tenant_id')`）を効かせられるか
3. 効かないなら、テナントごとにインスタンスを分ける以外の手はあるか

**なぜ効くか**

我々は本セッションで、RLS が**所有者バイパスで完全に無効化されていた**のを実測で
見つけて直したところです。既製エンジンが自前の接続プールで所有者ロールを使うなら、
同じ穴が開きます。「エンジンを入れたらテナント分離が壊れた」は最悪の結末です。

**何をもって答えとするか**

- エンジンが発行する SQL が、接続ロールとして何を使うか（設定可能か）
- **実際に 2 テナントのデータを入れて、片方から他方が見えないことを実測した結果**
  （ドキュメントの記述ではなく、実行して確かめた出力）
- 無理な場合、インスタンス分離時の 1 テナントあたりコスト（C3 の $28/月 に対して何倍か）

### Q3 D&D エディタの実現手段

**知りたいこと**

1. Dify / n8n の**エディタ部分だけ**を切り出して使えるか（できないなら、何を使っているか）
2. React Flow（現 xyflow）のライセンス・機能・Next.js 15 App Router との相性
3. **ノード設定フォームをどう作っているか**。ノード種別ごとに手書きか、
   JSON Schema からフォームを自動生成しているか
4. 大規模グラフ（ノード 50+）での描画性能

**なぜ効くか**

我々のノードカタログは 13 種で、それぞれ config が違います（`docs/design/16-agent-workflow.md` §4.2）。
**13 種 × 設定フォームを手書きすると、UI の工数がエンジン本体を超えます。**
スキーマ駆動でフォームを生成できるなら、pydantic モデル → JSON Schema → フォームの
経路が使えて、config の定義が 1 箇所で済みます。ここは工数を大きく左右します。

**何をもって答えとするか**

- 3 の答えが最重要。**Dify / n8n が実際にどうしているか、ソースを読んだ上での報告**
- React Flow のライセンス（原文）と、商用利用時の制約
- 「Next.js 15 App Router + React Flow で、ノードを D&D して JSON を吐く」最小の
  動くコード（PoC）。**動いた画面のスクリーンショットと、吐いた JSON**

### Q4【重要】永続的な実行エンジンをどう作るか — LangGraph で足りるか

**知りたいこと**

我々は既に LangGraph 1.2.9 + PostgresSaver を抽出グラフ（§4）で使っています。
**ワークフロー層も LangGraph で作れるか。**

1. LangGraph 1.x の durable execution / interrupt は、**数日単位の待機**に耐えるか
   （checkpointer に置いたまま何日も放置して resume できるか）
2. **グラフ構造を実行時に組み立てられるか**。我々の graph_json は DB に入っていて
   テナントごとに違う。LangGraph は静的にグラフを定義する前提に見えるが、
   動的構築（`StateGraph` を毎回組む）は現実的か。その際のコストは
3. LangGraph の checkpointer は、抽出グラフのものと**同じテーブルを共有してしまわないか**
   （DD-11 の観点で、レイヤが混ざるのは避けたい）
4. 代替: Temporal / Prefect / Restate 等の durable execution。C2/C3/C4 に載るか

**なぜ効くか**

設計書 §6.2 では「1 メッセージ = 1 ノードの継続渡しを自前で書く」としています。
これは確実に動きますが、**リトライ・冪等・並列・タイムアウトを全部自分で書く**ことになります。
LangGraph か Temporal で代替できるなら、そこが丸ごと減ります。

逆に、Temporal は**常駐サーバが要る**ため C3（使う時だけ up）と衝突します。
LangGraph は既に入っているので追加コストがゼロです。**まず LangGraph で足りるかを見てください。**

**何をもって答えとするか**

- 1 について: **実際に checkpoint を保存して、プロセスを落として、数日後（または
  時刻を操作して）resume できることを実測した結果**
- 2 について: DB から読んだ JSON で StateGraph を毎回構築する PoC と、その所要時間
- 4 について: 常駐が要るか / ECS Fargate に乗るか / down→up でデータが消えないか

### Q5 HITL の待機を既存事例はどう扱っているか

**知りたいこと**

Dify / n8n / Temporal / LangGraph が、**人間の承認待ち（数日）**をどうモデル化しているか。

**なぜ効くか**

C5。我々の設計では `workflow_runs.status='waiting_hitl'` で DB に永続化し、
`document.confirmed` イベントで再開します（§8）。これは自前実装です。
既存エンジンに「人間タスク」の概念があるなら、そちらに乗れます。

**何をもって答えとするか**

- 各エンジンの HITL 機構の有無と、その永続化方式
- 待機中に**エンジンのプロセスが落ちても再開できるか**（実測）
- 待機中の run が**リソースを食い続けないか**（ワーカーを占有しないか）

### Q6【運用の根幹】常駐が要る機能と「使う時だけ up」は両立するか

**知りたいこと**

`source.folder_watch`（S3 を 60 秒間隔で監視）には常駐ワーカーが要ります。
しかし本環境の運用は「使う時だけ up、終わったら destroy（月 4 回 × 8h = 約 $28）」です。
**「S3 にファイルを置いたら自動で処理される」機能は、環境が落ちている間は動きません。**

選択肢:

1. watcher を常駐させる（月 +$9 程度。ただし**環境全体を落とせなくなる**＝月 $606 に戻る）
2. **S3 イベント通知 → EventBridge → ECS RunTask** で、ファイルが置かれた時だけ起動
3. EventBridge Scheduler で定期起動（cron 相当）
4. ワークフローは「使う時に手動で流す」に限定し、自動トリガーを諦める

**なぜ効くか**

**これは技術ではなく事業判断に直結します。** 利用者は $606/月 を「完全にコストオーバー」と
明言しており、$28/月 の運用に合意しています。自動化層が常駐を要求するなら、
その前提が崩れます。

**何をもって答えとするか**

- 2 について: S3 イベント → ECS タスク起動の**実測レイテンシとコスト**。
  RDS/ElastiCache が落ちている状態から起動して処理完了までに何分かかるか
  （＝RDS の起動に 15-20 分かかるなら、この案は「即時処理」を名乗れない）
- 各案の月額コスト試算（月 4 回 × 8h の利用パターンで）
- 「自動トリガーは常時稼働の環境でのみ提供する（有料オプション）」が
  成立するか、という**プロダクト側の選択肢の提示**

### Q7 DD-12（顧客 DB への書込み）の実現手段

**知りたいこと**

1. 既製エンジンの DB 書込みノードは、**任意 SQL を許していないか**。許しているなら
   我々の制約（INSERT/UPSERT 限定、allowed_tables 限定、行数上限）を後付けできるか
2. 顧客 DB への接続情報を、どこにどう保持しているか（DB 平文なら我々の §16.5 に反する）
3. テーブル名・列名は識別子でバインドできない。SQL インジェクションを防ぐ実装パターン

**なぜ効くか**

C7。汎用エンジンの「何でも書ける DB ノード」は、そのままでは DD-12 に反します。
**制約を後付けできない設計なら、その候補は使えません。**

**何をもって答えとするか**

- 候補ごとの DB ノードの実装（ソースの該当箇所）
- 制約を注入できる拡張点があるか（プラグイン/フック）

### Q8 Dify / n8n の graph_json 設計を読む

**知りたいこと**

我々の `graph_json`（§4.1）と比べて、実績のある設計が何を持っているか。特に:

1. **版管理**をどうしているか（実行中の run が定義変更の影響を受けない仕組み）
2. **条件分岐の式**をどう表現しているか。任意式を eval しているか、限定文法か
3. ノード間のデータ受け渡し（変数参照の記法）
4. サブグラフ / 再利用の仕組み

**なぜ効くか**

我々は条件式を**限定文法**にしています（§4.3。`eval` も汎用式言語も入れない）。
これは lint とテストを可能にするための判断ですが、**実際の利用者が「and/or が使えない」で
困らないか**は事例から学べます。

**何をもって答えとするか**

- 2 が最重要。**実際の式の例を 10 個以上**（実運用のワークフローから）。
  単項比較で足りているのか、複合条件が普通に使われているのか

## 4. 報告してほしい形

### 4.1 必須

- **判断を変える情報だけ**を書いてください。「Dify は人気がある」は判断を変えません。
  「Dify のライセンスは第 X 条でマルチテナント SaaS への組込みを禁じている」は変えます。
- **一次情報を引用**してください（ライセンス原文、ソースコードの該当行、実行ログ）。
  ブログ記事の要約は、その元を辿ってください。
- **実測した結果**と**ドキュメントの記述**を区別してください。両者はよく食い違います
  （我々は本プロジェクトで、公式が GPU を要求する VL パイプラインが実は CPU で動くこと、
  最新の paddlepaddle 3.3.1 が壊れていること、RLS が書いてあるのに効いていないことを、
  全て実測で発見しています）。
- **分からなかったことは「分からなかった」と書いてください。** 推測を結論として
  報告されると、それを前提に設計してから破綻します。

### 4.2 最終的に答えてほしい問い

> **作るか、借りるか。借りるなら何を、どこまで。**

この 1 行に対する推奨と、その根拠。判断が Q1（ライセンス）と Q2（マルチテナント）と
Q6（常駐と運用）で決まるなら、そう書いてください。

### 4.3 期待する成果物

1. Q1 の可否表（候補 × 可否 × 根拠条文）
2. Q2 の実測結果（2 テナントの分離を試した出力）
3. Q3 の PoC（動く D&D → JSON。スクリーンショット付き）
4. Q4 の実測結果（LangGraph の長時間 resume、動的グラフ構築）
5. Q6 のコスト試算（案 1〜4 × 月額）

## 5. 優先度と打ち切り基準

**Q1 → Q2 → Q6 → Q4 の順に着手してください。**

- **Q1 で全候補が NG なら**: 自前実装が確定。Q2/Q3/Q7 の既製品調査は不要になり、
  Q4（LangGraph で足りるか）と Q8（設計の参考）に資源を集中してください。
- **Q6 で「常駐は許容できない」と分かったら**: `source.folder_watch` は設計から外れ、
  トリガーは manual / schedule に縮小します。調査範囲もそこまで縮みます。
- **Q3 は後回しで構いません。** エディタは D&D ライブラリが確実に存在するので、
  「できない」という結論にはまずなりません。工数見積りのためだけに要ります。

時間が限られる場合、**Q1・Q2・Q6 の 3 つだけ**でも判断できます。
Q3 に時間を使って Q1 が終わらない、が最悪の配分です。
