# 設計: 画像からの項目追加と、反証可能な読取領域ヒント

2026-09-11。第 1 版に敵対的レビュー（§7）を当てて書き直した第 2 版。

## 0. なぜ今これか

利用者の工程はこうである。

```
AI が項目を自動発見 → 人が「要らない項目を外す」「足りない項目を足す」
  → テンプレート登録 → 同種の帳票を大量に流す
```

現状の到達点（2026-09-11 時点、main）:

| 工程 | 状態 | 何が欠けているか |
|---|---|---|
| 要らない項目を外す | できる | — （テンプレート化画面の「残す」チェック、スキーマ管理画面の削除） |
| **足りない項目を足す** | **半分** | 名前と型はスキーマ管理画面で足せるが、**「紙面のここにある」と教える手段が無い**。テンプレート化画面のドラッグは既存の行にしか紐づかない |
| テンプレート登録 | できる | — |
| 大量に流す | できる | フォルダ監視で自動取込〜後段まで流れる（複数同時アップロードと一括再処理は別件） |

「足りない項目を足す」が半分なのは、2 つの欠落が重なっているからである。

1. **UI**: 領域から新しい項目を作れない（行を選ばずに引くとエラー）。
2. **ランタイム**: 読取領域は既定では抽出結果を変えない（Phase 4 は off）。
   位置を教えられたとしても、AI はそれを使わない。

1 だけ作っても「引けるが効かない」で終わり、2 だけ直しても「効くが AI が見つけた
項目にしか領域を付けられない」で終わる。**セットでないと価値が出ない**ので 1 つの
設計にする。

2 を既定 on にできなかった理由は再計測（2026-09-07）で確定している。機構は効く
（S1: p = 0.007）が、**領域が 1 行ずれると正解を壊し**（sample8: customer_name 3/3 → 0/3、
返った値は隣の行の「大熊邸」）、**位置ガードはそれを検知できない**（領域の中から
取った値なので一致と見なす）。いまのヒントは座標だけで、モデルはそこに何があっても
従う。だから本設計の 2 は「ヒントを渡すかどうか」ではなく **「ヒントを反証可能にする」**
ことを目標にする。

### 第 1 版から変えたこと（要点）

第 1 版を自分で攻撃したら（§7）、**設計の安全装置が、設計の動機になった失敗を
カバーしていなかった**。決定論のガードは「候補 0 件」「型の不一致」だけで、
sample8（会社名の項目に建物名が入る）は文字列項目なのでどちらにも掛からず、
モデルの判断（＝ソフトな指示）だけに頼っていた。第 2 版では:

- **種類の衝突を決定論で落とす**（会社名の項目に住所・建物名・金額が来たら渡さない）。
  誤って落としても「ヒント無し」に戻るだけで対照より悪くならない、という非対称性が
  この安全装置の根拠。
- **例示値の出どころを正す。** 第 1 版は正規化後の値を使っており「正規化しない」と
  矛盾していた。しかも手描きの領域（Part 1 が作る本命のケース）では枠の下の文字を
  知る手段が無く、例示値が欠けるか**古い値を引きずる**。span の永続化を必須にする。
- **モデルの自己申告をやめる。** 「従った／捨てた」は span_ids と候補の共通部分から
  決定論で求まる。プロンプトの出力形式を変えず、申告漏れの心配も無い。
- **別雛形のテンプレートを当てる計測（S3）を出荷ゲートに足す。** 「間違ったヒントは
  害になるか」を直接測る。前回は sample8 の 1 件しか無かったが、目視で「別雛形」と
  判定した 6 組をそのまま使える。
- **「行を選ばずに引くと新規」という見えない状態に頼らない。** 明示的なモードにする。

## 1. 画像からの項目追加（Part 1）

### 1.1 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| D1 | **「＋ 領域から項目を追加」ボタンで一回限りの描画モードに入り、次のドラッグが新しい項目になる** | 第 1 版の「行を選ばずに引くと新規」は、選択の有無が画面から見えず（解除は Esc だけ、案内も無い）、背景クリックは意図的に行選択を残す作りなので、誤操作で行が増える。明示的なモードなら「いま何を引いているか」が常に見える |
| D2 | 「＋ 項目を追加」ボタンも置く（領域なしで行だけ足す） | 領域を引く前に名前を決めたい人、位置が決まらない項目（自由記述など）のため |
| D3 | 新規作成モード・編集モードの**両方**で追加できる | 「足りない」と気づくのは 2 通目以降の検証画面（＝編集モード）が多い |
| D4 | 編集モードでの**削除は引き続きスキーマ管理画面**で行う。ただし画面に「削除はスキーマ管理画面で」と**その画面へのリンク**を置く | 削除はワークフローの `map_fields`・学習メモリのキーに波及する。いまの save() は `base` 持ちの行を `include=false` でも版から落とさない（意図的）。この契約は変えないが、行き止まりにはしない |
| D5 | 新規項目は **`name` と `label` の両方が必須**。命名規則（英字始まりの英数字・アンダースコア）と重複検査を適用 | `label` は KIE がその項目を探す**唯一の語彙の手掛かり**。空だと `name`（例: `due_date`）が代用され、日本語帳票では探せない |
| D6 | ゴースト（AI が見つけた位置）に **AI が読んだ原文（`source_quote`）** を表示する | 再計測で、AI が取り違えた項目はゴーストの位置も取り違えていた。正規化後の値ではなく原文を見せる ── 「何をどこから読んだか」が分かるのは原文だけ |
| D7 | 新規行の型の選択肢から `table` を除く | 列定義の無い表項目ができる。既存の表項目は従来どおり読み取り専用 |
| D8 | 領域に **`origin`（`ghost` / `manual`）と `created_at`** を持たせる | AI の位置をクリックで採ったか手で引いたかで、例示値の信頼度も計測の切り口も変わる。**後から付けると既存の領域が全部 unknown になる**ので今付ける |
| D9 | 予約名（`__pages__`・`__region__`・先頭 `__`）は**サーバで**拒否する | UI の命名規則は英字始まりなので通らないが、チャット経路は `SchemaFieldDef(**field)` で任意の名前を通す。レビュー項目の集約名と衝突する。検査は Pg / InMemory 両方の `put_schema` が呼ぶ共通関数に置く（ルータに置くとチャット経路が素通り） |

### 1.2 画面の振る舞い

**領域から新規項目を作る**（D1）

1. 一覧の下の「＋ 領域から項目を追加」を押す。画像の上に帯が出る:
   「新しい項目の位置をドラッグしてください（Esc で中止）」。
2. ドラッグを終えると一覧の末尾に行が増える: 表示名・項目名は空、型は `string`、
   「残す」は on、領域はいま引いた矩形（`origin: manual`）。モードは自動で抜け、
   行が選択状態になり、**表示名の入力欄にフォーカス**が移る。
3. 名前を入れて保存する。空のまま保存しようとすると、その行を指して止める。

このモードに入っていないときの挙動は現状のまま（行を選んでいれば紐づけ、選んで
いなければ「行を選んでください」）。**暗黙に新規項目を作る経路は作らない。**
モード中はゴースト（破線）を出さない ── ゴーストの上では pointerdown が矩形描画を
始めないので「次のドラッグが新しい項目」が崩れる。Esc はモードを抜けるだけで、
ドラッグ中の矩形は捨てない（pointerup は通常経路に落ちる）。

**「＋ 項目を追加」**（D2）

一覧の末尾に空行を足す。領域は無し（あとで行を選んで引く）。

**新規行の削除**

新規行（`base` 無し・保存前）には「×」を付け、行ごと消せる（領域も一緒に消す）。
新規行の「残す」チェックを外す操作は**「×」と同じ意味**（版に載らない）なので、
新規行ではチェックボックスを出さず「×」だけにする。編集モードで既存行のチェックが
「領域を付けるか」の意味なのと混ざらないようにするため。

**ゴースト**（D6）

`title` とホバー時のラベルに `読み取り: <source_quote>` を添える。40 字で切る。
`source_quote` が無い（根拠 span 無し）項目はゴースト自体を出さない ── 座標が
無いので出しようがない（現状どおり）。

### 1.3 データの流れ

`DraftRow` に `isNew: boolean` を足す。save() の生成規則は変えない:

```ts
.filter((d) => d.include || d.base)   // 既存契約のまま
.map((d) => d.base
  ? { ...d.base, name, label, type: d.type, region }
  : { name, label, type: d.type, required: false, critical: false, region })
```

新規行は `base` 無しなので 2 つ目の分岐に落ち、`region` 付きの新しい項目として
PUT /schemas に載る。サーバ側の変更は D9 の予約名検査だけ。

`issue()` の検査に足すもの:

- 新規行の `name` または `label` が空 → 「項目名と表示名を入力してください（行 N）」
- 新規行の `name` の重複・命名規則 → 既存の検査に乗せ、**違反した行が新規行なら
  「（N 行目）」を添える**（既存行の文言は変えない。§1.6-3 と §1.3 の食い違いを
  こちらで解消）
- 新規行で領域が無い → **保存を止めない**（D2）。保存後のトーストで「領域が無い項目は
  AI が語彙から探します」と伝える

### 1.4 純粋関数の切り出しとテスト

`TemplatizePreview.tsx` は 787 行で、実機で潰した不具合が 10 件を超える領域なのに
自動テストが無い。Part 1 でさらに分岐が増える。**保存 body の生成と検査を純粋関数に
切り出し、そこにだけ単体テストを付ける**:

```
web/lib/templatize.ts
  buildSaveBody(drafts, regions, preserved, mode) -> { fields, excludeRegions, sourcePageCount }
  validateDrafts(drafts, regions, docType) -> string | null
  resolveGhosts(fields, drafts, regionByRow, page) -> CanvasGhost[]
```

DOM に触らないので vitest だけで動く。導入は `vitest` の devDependency と
`npm run test`、CI の web ジョブに 1 ステップ。React コンポーネントのテストは
入れない（この 3 関数が壊れやすさの本体）。

### 1.5 文言

Part 1 を単独で出す期間（Part 2 が off の間）、新規項目に領域を引いても抽出は
変わらない。**その状態で「ここにある」と引かせるのは誠実ではない**ので:

- Part 1 単独の期間: 新規行に「この項目は AI が語彙から探します。位置のヒントが
  抽出に使われるのは今後の版からです」と添える。
- Part 2 が既定 on になったら、この画面の説明文を「読取領域は、この位置に何があるかの
  ヒントとして抽出 AI に渡されます」に差し替える（**同じコミットで**）。
- **on にした直後、off の期間に引かれた領域が初めてヒントとして使われ始める。**
  作者はヒントの意味で検証していない。D8 の `created_at` で「有効化前に引かれた領域」を
  識別し、検証画面の参考表示（§2.8）で区別して見せる。
- 境界となる時点は orchestrator の定数 `REGION_HINTS_ACTIVATED_AT`（コードで既定 on に
  した 2026-09-12T00:00:00Z）。実際に on になった時点は環境ごとにずれ得る（キルスイッチで
  止めていた期間・デプロイ日）ので、環境変数 `REGION_HINTS_ACTIVATED_AT`（ISO 8601、Z か
  オフセット付き）で上書きできる。tz の無い値（日付だけ等）は UTC 00:00 とみなす（JST の
  0 時ではない。JST の時点は `+09:00` を付けて書く。terraform の `region_hints_activated_at`
  は時刻と tz まで必須で、日付だけは plan で弾く）。解釈できない値は定数に倒して warning を
  出す。検証画面の文言には日付を書かない（上書きした環境で嘘になる）。

### 1.6 受け入れ条件（Part 1）

1. 「＋ 領域から項目を追加」→ ドラッグ → 名前入力 → 保存で、GET /schemas/{doc_type} の
   fields に **region 付き（origin: manual）**でその項目が返る。
2. 編集モードでも 1 が成り立ち、既存の項目・領域・除外領域は 1 ビットも変わらない
   （既存の「触っていない矩形は origin を返す」保全が壊れない。`buildSaveBody` の
   スナップショットで固定）。
3. `name` / `label` が空、重複、命名規則違反の新規行は保存が止まり、どの行かが分かる。
4. 新規行の「×」で領域も消える（孤立した include 領域を残さない）。
5. ゴーストに `source_quote` が出る。
6. 予約名は API 直叩き・チャット経由でも E1003 で拒否される。

## 2. 反証可能な読取領域ヒント（Part 2）

### 2.1 いまのヒントの何が足りないか

いま KIE に渡るのは `region_px: {page, bbox}` だけである。モデルの側から見ると
「この矩形の中を優先せよ」としか言われておらず、**矩形の中身が項目の種類と合っている
かを判断する材料が無い**。sample8 では矩形の中に「大熊邸」（建物名）があり、項目は
customer_name。座標だけ見れば「宛先はここ」なので従った。

プロンプトには「ヒントは絶対条件ではない」と書いてあるが、**何をもって外れと判断
するかが書かれていない**ので、指示として機能していない。

さらに、いまの介入アームは**全 span に bbox を付ける**（`_spans_for_prompt(with_bbox=True)`）。
プロンプトが膨らむうえ、前回の実測記録が自ら書いたとおり「矩形の注入」と「全 span への
座標付与」の効果を分離できていない。

### 2.2 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| D10 | 領域に **`example_value`（テンプレート元でその位置にあった**原文**）** を持たせる | 「前回ここには『株式会社千曲川ホーム』があった」があれば、「大熊邸」を見たときに種類が違うと判断できる |
| D11 | 例示値の出どころは **span の原文**に限る。ゴーストクリック → その項目の `source_quote`、手描き → **枠の下の span の連結**（§2.3）。正規化後の値は使わない。**矩形を引き直したら必ず取り直す**（古い値を引きずらない） | 第 1 版は正規化後の値（`d.sample`）を使っており「正規化しない」と矛盾していた。手描きの枠に古い例示値が付くと、位置と例示が食い違う最悪のヒントになる |
| D12 | **span を run ごとに永続化し、取得 API を作る**（第 1 版 §3.1 を本体に含める） | D11 の「枠の下の文字」はこれが無いと取れない。加えて、新規項目に領域を引いたとき「この枠に何が書いてあるか」がその場で見える（いまは保存→再抽出で初めて分かる） |
| D13 | ヒントは矩形ではなく **矩形の中にある span の候補列（id と原文）** として渡す。**全 span への bbox 付与はやめる** | モデルが実際に選ぶのは span である。候補を名指しすれば座標は要らない。プロンプトが縮み、A/B の交絡も消える |
| D14 | **渡す前に決定論で落とす**: (a) 候補 0 件、(b) 型付き項目で候補の**連結**が型に合わない、(c) **例示値と候補の「種類」が衝突する**（§2.5） | (a)(b) は自明な誤ヒント。(c) が sample8 を落とす。落とした事実と理由は metrics に残す |
| D15 | 「従った／捨てた」は**モデルに申告させず、span_ids と候補の共通部分から決定論で求める** | 第 1 版の自己申告は、本体テンプレートの出力例に無いキーを付録で要求する形になり、従わない可能性が高い。集合演算なら申告漏れも嘘も無い |
| D16 | プロンプトに **「捨てる基準」を明記**する。空間的な語（「近く」）は使わない | 座標を渡さないので「近く」は意味を持たない。判断材料は候補の原文と例示値の**種類** |
| D17 | 検証画面に「位置ヒントを使用」「ヒントを捨てた（理由）」を**参考表示**（レビュー件数には触らない） | 位置ガードが検知できない失敗を人が見て気づける場所。捨てた理由はテンプレート作者への手掛かり（「この帳票ではその位置に何も無い」＝レイアウトが違う） |
| D18 | 表記揺れの正規化関数を **1 つに統合**する | いま `golden/metrics._norm`・`golden/region_ab._norm`・`golden/region_from_gold.key` の 3 つが同じ目的で別々に存在する。例示値の照合で 4 つ目を書く前に `newfan_schemas.textnorm` に寄せる |
| D19 | 出荷は**再計測のゲート**（§3）を通してから。既定 on の条件を先に決める | 前回と同じ |

### 2.3 保存契約: `RegionRect` の拡張

```python
class RegionRect(BaseModel):
    page: ...
    rect: ...
    label: Optional[str] = None
    # --- 以下、読取領域のみ（除外領域では未使用） ---
    # テンプレート元の帳票で、この領域にあった span の原文。KIE に「前回ここには
    # 何があったか」を伝える。正規化しない（紙面の見た目に近いほど照合しやすい）。
    # 印字可能文字のみ・200 字で切る（label の消毒と同じ規則）。
    example_value: Optional[str] = None
    # 領域の出どころ。ghost = AI が見つけた位置をクリックで採った / manual = 手描き。
    origin: Optional[Literal["ghost", "manual"]] = None
    created_at: Optional[str] = None  # ISO 8601。有効化前に引かれた領域を識別する
```

- fields JSONB の中なので**マイグレーション不要**。既存の領域は 3 つとも `None`。
- `RegionRect` は gateway の DTO からも参照されている（`SchemaFieldDto.region`）ので
  モデルに足せば往復する。**必ず往復テストを足す**（pydantic v2 の既定 `extra="ignore"`
  は DTO 側の漏れを黙って落とす。§4.2 で一度踏んでいる）。
- web の `RegionRect` 型に同じ 3 つを足す。`isUntouched` の保全は 3 つごと保全する。
  web の `PreviewRegion` 側は `originKind` / `createdAt` / `exampleValue`（`origin` は既に
  「読み込んだ原本の RegionRect」の意味で使われているため）。保存 body 上のキーは上記のとおり。
- **保存時に、手描き領域の例示値の取得がまだ終わっていなければ待って埋める**（取得前に
  保存すると `example_value` が欠け、その項目だけ `kind_conflict` が効かない）。
- 「例示値を消す」は矩形を再正規化せず、原本の RegionRect に `example_value: null` を
  乗せて返す（丸め往復を起こさない）。
- 消毒: `example_value` は kie.py が `label` に課しているのと同じ規則（印字可能文字のみ・
  上限で打ち切り）。LLM プロンプトに入る文字列なので、無検疫で通さない。

**例示値の出どころ（D11）**

| 領域の作り方 | `example_value` | `origin` |
|---|---|---|
| ゴーストをクリック | その項目の `source_quote`（AI が根拠にした span の原文） | `ghost` |
| 手描き（既存行・新規行とも） | 枠の下の span の原文を読み順で連結（§2.4 の取得 API） | `manual` |
| 枠を引き直した | **取り直す**。取れなければ `None`（前の値は捨てる） | 引き直した方法に従う |
| 編集モードで触っていない | 保存値をそのまま返す（保全） | 保存値のまま |

**データの分類が変わることに注意。** これまで `field_schemas` は項目の定義だけを
持っていたが、`example_value` は**帳票の値（取引先名・担当者の個人名など）**である。

- RLS の中に留まるので漏れはしない。
- スキーマ管理画面にも表示する（何がヒントに使われているかを人が見られる状態にする）。
- **保持期間が帳票より長い。** `put_schema` は常に新版 INSERT で旧版を残すため、
  例示値はスキーマの版が残る限り残る。`DELETE /documents` は帳票と学習例を消すが
  スキーマの例示値は消さない（帳票との紐付けが無い）。これを受け入れる代わりに、
  編集モードに**「例示値を消す」**を置き、個人名が気になる場合に作者が外せるようにする。
  種類判定（§2.5）で `person` と判定された例示値には、保存時に「個人名が例示値に
  入ります」と一言出す。

### 2.4 span の永続化と取得 API（D12）

- テーブル `run_spans(run_id, page_no, spans JSONB)`、migration 0008、RLS + FORCE。
  1 ページ数百 span × 100 バイト ≒ 数十 KB／ページ。
- `save_result` で `state["spans"]`（除外領域の適用**後**）を書く。needs_review → confirmed
  の再保存で消えないこと、再配信で二重に増えないことを §5 の Pg テストで固定する
  （`metrics.region` で踏んだのと同じ形の穴）。
- `GET /documents/{id}/spans?page=n`（viewer 可）→ `[{span_id, text, bbox}]`。
  テンプレート化画面は、枠を引いた／選んだときにこれを引いて「枠に含まれる文字」を
  表示し、`example_value` に入れる。
- structure-svc に都度問い合わせる案は採らない（ページあたり数秒〜数十秒。矩形を引く
  たびに待たせるのは操作にならない）。

### 2.5 ランタイム: 候補の解決と事前ガード（D13・D14）

`_schema_for_prompt(schema, pages, spans)`（llm_nodes.py）。ヒント有効時のみ。

```python
px = _region_px(region, pages)                       # 既存: 正規化→画素、ページ解決、範囲外は落とす
if px is None: continue
cands = [s for s in spans if s.page == px["page"] and _inside(s.bbox, px["bbox"])]
cands = _rank(cands, px["bbox"])[:HINT_MAX_CANDIDATES]
reason = _prevalidate(field, cands, region.get("example_value"))
if reason:
    dropped[name] = reason                            # metrics へ
    continue
stripped["region_hint"] = {
    "candidates": [{"span_id": s.span_id, "text": s.text} for s in cands],
    "example_value": ev,
    # 候補 1 つずつと、読み順で連結したものの両方と比べる（手描きの例示値は連結。D11）
    "example_present": ev is not None and (any(norm(s.text) == norm(ev) for s in cands)
                                          or norm(ev) in norm("".join(s.text for s in cands))),
}
```

**候補の判定 `_inside`** ── 除外領域の `_covered`（span の 50% 以上が矩形内）は
**流用しない**。除外は「消しすぎ」が危険なので厳しめが正しいが、ヒントは逆で
「拾い漏れ」が危険（人が手で引いた枠は文字の一部にしか掛からないことが普通で、
0 件になるとヒントごと落ちる）。**span の中心点が矩形内**、または重なりが span 面積の
30% 以上、のどちらかで採る。定数は `HINT_SPAN_RATIO = 0.3` として除外と分ける。

**候補の順位 `_rank`** ── 読み順ではなく**矩形との重なりが大きい順**。読み順で
先頭 N 件に切ると、大きな枠で本命が後ろに来たとき落ちる。`HINT_MAX_CANDIDATES = 12`。
切った件数は metrics に残す。**「重なりで選び、読み順で渡す」は第 4 回計測で試して
採らなかった**（S1 8 / 72 → 12 / 57、S3 25 / 16 → 27 / 13。改善せず、S3 は悪化側。
実測記録 `region-measurement-2026-09-12b.md`）。

**事前ガード `_prevalidate`**（落とす理由を返す。順に評価）:

| 理由 | 条件 | 何を防ぐか |
|---|---|---|
| `placeholder_example` | 例示値が**記入例語**（値ではなく記入欄の説明）。4 つの規則を順に当てる: (1) 値にも見出しにも現れない強い印（「住所1」「ビル名等」「都道府県」「登録できます」「記入例」「例）」「YYYY/MM/DD」「{{name}}」「@example.com」「Lorem ipsum」）を含む、(2) 見出し語・透かし語（「会社名」「氏名」「住所」「様」「株式会社」「サンプル」「見本」…）と助詞・記号を除いて何も残らない（「得意先の会社名」「自社名(ロゴや社判も登録できます)」「テスト株式会社」。「会社名 株式会社山田」「TEL 03-1234-5678」「テストー株式会社」は値が残るので通す。数字は消さない）、(3) 法人格・敬称・住所の単位字・元号と年月日・通貨・数字・区切りを剥がして伏せ字だけ（「〇〇株式会社」「〒○○○-○○○○」「令和○年○月○日」。「高田馬場XX-X-XX」「東京都○○区○○1-2-3」は固有の実文字が残るので通す。X は残りが X と伏せ字だけ（「03-XXXX-XXXX」）のときだけ伏せ字）、(4) 数字が 4 桁以上あってすべて 0（「〒000-0000」「¥000,000」）。テンプレート側の欠陥なので**最初に**評価する（候補 0 件でも no_spans ではなくこの理由。metrics でテンプレート単位に数えられる）。採らないと決めた語: 「ロゴ」（株式会社ロゴスコーポレーション）、「商事」「ABC」「Acme」「123 Main St」「N/A」「-」「No.」（実在しうる）。第 5 回の敵対的検証（独立に作った 463 件の held-out）で実値の誤検知 0 | **sample2 ← sample13**（第 4 回 S3、−6）: 記入例の帳票から作ったテンプレートは種類判定が unknown で `kind_conflict` が効かず、別雛形の候補にそのまま従った。落としても対照に戻るだけ（第 5 回計測で確認） |
| `no_spans_in_region` | 候補 0 件 | この帳票ではその位置に何も無い（レイアウト違い） |
| `overlaps_exclude` | 候補 0 件で、かつ矩形が適用済み除外領域と重なる | 作者が矛盾した領域を引いた。`no_spans` と区別して伝える |
| `type_mismatch` | 型付き項目（`money_jpy` / `date` / `number` / `tax_rate_jp` / `jp_invoice_reg_no` / `jp_bank_account`）で、候補の**連結**にも各候補にもその型として解釈できるものが無い。**数値系は数字を 1 つも含まなければ解釈不能**（正規化器が `.` 入りを素通しするため）。**日付に文脈年は渡さない**（年省略は落ちる側に倒す） | 金額項目の位置に数字が無い。**連結を見る**のは日付が「令和」「5年」「5月」「1日」に割れるため（単体で見ると全部落ちる） |
| `kind_conflict` | 例示値と候補の「種類」が衝突する（下表） | **sample8**（会社名の項目に建物名） |

型の解釈は決定論正規化のパーサをそのまま使う（新しく書かない）。

**種類判定（`kind_conflict`）** ── 小さな規則ベースの分類器。順に当てて最初に
当たった種類にする:

| 種類 | 手掛かり |
|---|---|
| `amount` | 数字と通貨記号／桁区切り（¥・￥・円・,）で構成 |
| `date` | 年月日・令和/平成・`yyyy/mm/dd` 型 |
| `id` | 英数字とハイフンのみ、または `T` + 13 桁 |
| `company` | 株式会社・有限会社・合同会社・(株)・㈱・Co.・Inc・Ltd・Corp・LLC を含む |
| `address` | 都道府県・市区郡町村・丁目・番地・号 を含む（`company` より後に評価。社名に「町」が入る例があるため） |
| `building` | 邸・ビル・マンション・ハイツ・荘・館 で終わる |
| `person` | 上のどれでもなく、**漢字 1〜4 ＋ 空白 ＋ 漢字 1〜3**、または末尾が「様」。空白の無い漢字語（発行日・合計金額・山田工務店）は `unknown`（見出し語・屋号を人名にしない。第 2 回レビュー） |
| `unknown` | 上のどれでもない |

候補は **1 span ずつ**と**読み順で連結したもの**の両方を分類する（type_mismatch と同じ理由:
日付は「令和」「5年」「5月」「1日」に割れる。第 2 回レビュー）。

衝突とみなす組（例示値の種類 → 候補の種類）: `company` → `address` / `building` / `amount` / `date` / `id`、
`person` → `address` / `building` / `amount` / `date` / `id`、`amount` → `amount` 以外、
`date` → `date` 以外。**`company` ↔ `person`、`unknown` を含む組は衝突にしない**
（区別が難しく、誤って落とすと効き目を失う側に倒れる）。候補の種類は、候補の中に
例示値と同じ種類のものが 1 つでもあれば衝突なし。

**この安全装置が「妥協なし」で入れられる根拠は非対称性にある。** 誤って落としても
その項目は**ヒント無し＝対照アームの挙動**に戻るだけで、対照より悪くはならない。
誤って通した場合の害（正解を壊す）とは釣り合わない。したがって分類器は保守的で
よく、精度はゲート（§3）で「落とした件数と、その項目の正解率」として測る。

**metrics** ── KIE ノードが `metrics.region.hints` に書く:

```
{"given": ["issuer_name", ...],
 "dropped": {"customer_name": "kind_conflict"},
 "truncated": {"issuer_address": 3},
 "outcomes": {"issuer_name": "followed", "total_amount": "rejected"}}
```

書き方は `_merge_region_metrics`（ocr_nodes.py）と同じ規則: `metrics` は reducer 無しの
LastValue チャネルなので既存の `region`（`excluded_*` 等）を読んでから返す。
**`hints` は run ごとに書き直す**（再配信で前回の値を残さない ── `mismatch_fields` で
踏んだのと同じ）。

**除外領域との関係** ── 候補は除外適用後の span から選ぶので、除外と重なる読取領域は
自然に候補 0 件になる。`overlaps_exclude` はその理由を作者に伝えるためだけにある。

**表項目** ── `columns` 持ちには `region_hint` を付けない（既存の分岐を維持）。

`region_px` キーは `region_hint` に置き換える。kie.py の `_has_region_hint` は
`region_hint` を見る。`_spans_for_prompt(with_bbox=...)` は**廃止**（D13）。
**領域を持たない field には何も足さない**ので、`snapshots/kie_prompt_no_region.txt`
はバイト一致のまま。

### 2.7 プロンプト（`kie_region_hint.yaml`）

差し替え後の骨子:

```
# region_hint（読取領域のヒント）がある場合
region_hint は「同じ種類の帳票で、前回その項目がこの位置にあった」という情報である。
- candidates: この帳票でその位置にある span（id と原文）。**まずここから探せ。**
- example_value: 前回その位置にあった原文（無ければ null）。
- example_present: 同じ原文がこの帳票の同じ位置にもある（true なら強い根拠）。

**ヒントを捨てる基準**（次のいずれかなら candidates を使わず、文脈と語彙で決めよ）:
- candidates の原文が項目の種類と合わない（会社名の項目なのに候補が住所・建物名・
  日付・数量など）
- example_value がある場合、候補の種類が example_value と合わない
  （会社名 vs 建物名、金額 vs 番号 など）
- 別の場所に、見出し（「合計」「請求先」など）付きで同じ種類の値がある

ヒントを捨てても value=null にしてはならない。捨てた場合は文脈から探せ。
span_ids は実在する span を指すこと（指示 2 の根拠契約が優先）。

**この節は region_hint のある項目にだけ適用する。** region_hint の無い項目は、
ヒントが無いときとまったく同じに指示 1〜5 で抽出せよ。ヒントの有無にかかわらず、
値にどの span を含めるかは指示 1〜5 のとおりに決め、この節を理由に値を切り詰めたり
（一部の span だけにする）、付け足したり（普段は含めない span を加える）してはならない。
```

出力形式への追加は無い。最後の段落は第 3 回計測で足した ── ヒントの説明文が、ヒントの
**無い**項目の読み方まで変えていた（波及。S3 の sample27 で issuer_address が対照 5/5 →
介入 1/5）。**項目の種類を例に挙げてはならない**: 「住所と建物名の 2 行はすべて含めよ」と
書いた版では、ヒントの無い住所に郵便番号まで付けて外した（実測記録 §結果 (a)〜(c)）。

### 2.9 位置ガード（Phase 5）との関係

ヒントに従った項目は、構造上、必ず領域の中で見つかる。したがって**ヒント on の run では
位置ガードの mismatch 率が下がる**が、それはガードが良くなったのではなくヒントが
選ばせただけである。Phase 5 が「実運用データを貯めて許容パラメータを決める」ために
使う mismatch 集計は、**`outcomes` が `none` / `rejected` の項目に限る**か、ヒント off の
run に限ること。`metrics.region.hints.outcomes` を項目ごとに残すのはこのため。

### 2.10 フラグの意味の反転

既定 on にするときは `region_hints_enabled()` を「未設定 → on、`0` / `false` / `off` → off」
に変える。いまの実装は `("1","true","yes","on")` に入るときだけ on なので、既定を
コードで反転するだけでは explicit off が効かない。compose / ECS のタスク定義に
キルスイッチとしての書き方を残す。

## 3. 出荷ゲート（D19）

`golden/src/newfan_golden/region_ab.py` で **3 つのアーム**を回す。

| アーム | 何を測るか | 領域の出どころ | 例示値 | 枚数 × 試行 |
|---|---|---|---|---|
| **S1** | 機構が効くか（2026-09-07 との比較用） | その帳票自身の正解位置 | **入れない** | 21 × 2 |
| **S2** | 同じ雛形への転用 | 同じ雛形の別の帳票 | 元帳票の span 原文 | 5 × 5 |
| **S3** | **間違ったテンプレートの害** | **別雛形**と判定した帳票 | 元帳票の span 原文 | 12 × 5 |

- S1 に例示値を入れないのは、同じ帳票の例示値は必ず `example_present: true` になり
  答えを教えるのと同じになるため。2026-09-07 の S1 と同じ条件で「効き目を失って
  いない」ことだけを見る。
- S3 の 12 件は、目視で「別雛形」と判定した 6 組（sample12/17、sample16/19、sample2/13、
  sample27/29、sample6/sample、sample4/19）の両方向。**これが「ヒントを反証可能にした」
  ことの直接の検証**で、前回は sample8 の 1 件しか無かった。
- 例示値はフィクスチャ生成時に `region_from_gold.py` が見つけた span の原文を使う
  （正解値ではなく原文。実運用と同じ）。

既定 on にする条件（**すべて**満たすこと）:

| # | 条件 | 根拠 |
|---|---|---|
| G1 | S1 の McNemar が「介入が有意に良い」（p < 0.05） | 効き目を失っていない |
| G2 | **S3 で介入が有意に悪くならない**（McNemar で「介入が有意に悪い」にならない）、かつ帳票ごとの純減（介入 − 対照、5 試行合計）が **−2 以上** | 間違ったテンプレートを当てても対照と同程度に留まる。3 試行で「下回る帳票ゼロ」を要求すると LLM の揺れで落ちる／通るが決まるので、5 試行と純減の幅で見る |
| G3 | sample8（S2）の customer_name が対照以上、または `outcomes` が `none`（`kind_conflict` で落とした）か `rejected` が 5 試行中 4 以上 | 「1 行ずれ」の直接の再現ケース |
| G4 | S3 で落とした／捨てたヒントの項目について、同じ試行の対照と対にした McNemar が**「介入が有意に悪い」にならない**（落としたことで悪くなっていない。生の正解数の差も根拠に残す）。第 3 回までは「差が 0 以上」（下記の注記） | 分類器の誤検知が害になっていない（非対称性の実測） |
| G5 | 領域を持たないスキーマのプロンプトがバイト一致（既存スナップショット） | 領域を使っていないテナントの挙動不変 |
| G6 | 介入アームのプロンプト長が、現行の介入（全 span bbox 付き）より短い | 費用が増えていない |

費用: 84 + 50 + 120 ≒ 254 抽出。前回の実績（大判で数分）から 3〜4 時間。

off のまま、結果を実測記録（第 3 回）に残す。

## 4. やらないこと

1. **編集モードでの項目削除** — D4。スキーマ管理画面へのリンクは置く。
2. **明細（表）への読取領域** — 従来どおり非対応（行数が可変）。
3. **ヒント付きと無しの二重抽出で照合** — 失敗の検知としては最も確実だが LLM 費用が
   倍になる。D14〜D17 で足りるかを S3 で見てから。
4. **住所項目だけヒントを外す** — 前回の計測で住所は一度も改善しなかったが、同じ
   データで決めると過適合。第 3 回の計測で再度見る（S1/S2/S3 の項目別を残す）。
   **→ 第 3 回で試して、採らなかった。** S1（5 試行）で住所は 対照のみ 18 / 介入のみ 5
   （p = 0.011）と悪いが、外れ方の多くは「郵便番号・社屋名を値に含めるか」の慣例の
   問題で、住所にヒントを渡さない版は逆にヒントの無い住所で郵便番号や「本社」を付けて
   外した（S3 で純減 −3〜−5、G2 不通過）。次は機構ではなく**住所の正規化の仕様**
   （郵便番号・社屋名の扱いを決めて正規化器で揃える）。実測記録 (c)(d)。
5. **`example_value` の自動更新** — 再抽出の結果でスキーマの例示値を書き換えるのは
   「スキーマが勝手に変わる」ので採らない。人が編集モードで保存したときだけ更新。
6. **ヒントを捨てた項目の確信度を下げる** — レビュー件数が増える。まず参考表示で
   人が見て、S3 の「捨てた項目の正解率」で必要かを判断する。
7. **テナント／スキーマ単位の on/off** — 既定 on ＋ 環境変数のキルスイッチで始める。
   必要なら `FieldSchema` にフラグを足す（小さい）。
8. **複数ファイルの同時アップロード・一括再処理** — 工程の後半だが本設計の外。
