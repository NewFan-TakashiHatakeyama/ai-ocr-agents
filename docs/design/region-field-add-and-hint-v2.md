# 設計: 画像からの項目追加と、反証可能な読取領域ヒント

2026-09-11。

## 0. なぜ今これか

利用者の工程はこうである。

```
AI が項目を自動発見 → 人が「要らない項目を外す」「足りない項目を足す」
  → テンプレート登録 → 同種の帳票を大量に流す
```

現状の到達点（2026-09-11 時点、main）:

| 工程 | 状態 | 何が欠けているか |
|---|---|---|
| 要らない項目を外す | できる | — （テンプレート化画面の「残す」チェック、スキーマ管理画面の削除） |
| **足りない項目を足す** | **半分** | 名前と型はスキーマ管理画面で足せるが、**「紙面のここにある」と教える手段が無い**。テンプレート化画面のドラッグは既存の行にしか紐づかない |
| テンプレート登録 | できる | — |
| 大量に流す | できる | フォルダ監視で自動取込〜後段まで流れる（複数同時アップロードと一括再処理は別件） |

「足りない項目を足す」が半分なのは、2 つの欠落が重なっているからである。

1. **UI**: 領域から新しい項目を作れない（行を選ばずに引くとエラー）。
2. **ランタイム**: 読取領域は既定では抽出結果を変えない（Phase 4 は off）。
   位置を教えられたとしても、AI はそれを使わない。

1 だけ作っても「引けるが効かない」で終わり、2 だけ直しても「効くが AI が見つけた
項目にしか領域を付けられない」で終わる。**セットでないと価値が出ない**ので 1 つの
設計にする。

2 を既定 on にできなかった理由は再計測（2026-09-07）で確定している。機構は効く
（S1: p = 0.007）が、**領域が 1 行ずれると正解を壊し**（sample8: customer_name 3/3 → 0/3、
返った値は隣の行の「大熊邸」）、**位置ガードはそれを検知できない**（領域の中から
取った値なので一致と見なす）。いまのヒントは座標だけで、モデルはそこに何があっても
従う。だから本設計の 2 は「ヒントを渡すかどうか」ではなく **「ヒントを反証可能にする」**
ことを目標にする。

## 1. 画像からの項目追加（Part 1）

### 1.1 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| D1 | テンプレート化画面で、**行を選ばずに読取領域を引くと新しい項目が生まれる** | 「AI が見つけなかった項目」は一覧に無い。いまの「行を選んでください」エラーは、この一番自然な操作を拒否している |
| D2 | 「＋ 項目を追加」ボタンも置く（領域なしで行だけ足す） | 領域を引く前に名前を決めたい人、位置が決まらない項目（自由記述など）のため。スキーマ管理画面と同じ操作を同じ場所でできるようにする |
| D3 | 新規作成モード・編集モードの**両方**で追加できる | 「足りない」と気づくのは 2 通目以降の検証画面（＝編集モード）が多い。ここで足せないと、スキーマ管理画面へ行って名前だけ足し、また戻って領域を引く、という往復になる |
| D4 | 編集モードでの**削除は引き続きスキーマ管理画面**で行う | 項目の削除はワークフローの `map_fields`・学習メモリのキーに波及する。いまの save() は `base` 持ちの行を `include=false` でも版から落とさない（意図的）。この契約は変えない |
| D5 | 新規項目の `name` は必須。既存の命名規則（新しく付けた名前にだけ課す）と重複チェックを適用 | 「表示名だけ入れて name が空」で保存されると、schema_fields_payload が壊れる／後続の照合が効かない |
| D6 | ゴースト（AI が見つけた位置）に**その値**も表示する | 再計測で、AI が取り違えた項目はゴーストの位置も取り違えていた。値が見えれば「これは違う」と気づける。クリックで確定する前に |

### 1.2 画面の振る舞い

**新規項目を画像から作る**（D1）

1. トグルが「読取領域」で、右の一覧の行を何も選んでいない状態でドラッグする。
2. 一覧の末尾に行が増える: 表示名・項目名は空、型は `string`、「残す」は on、
   領域はいま引いた矩形。行が選択状態になり、**表示名の入力欄にフォーカス**が移る。
3. 名前を入れて保存する。名前が空のまま保存しようとすると、その行を指して止める。

ドラッグの手触りは既存の行と同じ（`MIN_DRAG_PX` 未満は無視、`Delete` で領域解除）。

**「＋ 項目を追加」**（D2）

一覧の末尾に空行を足す。領域は無し（あとで行を選んで引く）。

**新規行の削除**

新規行（`base` 無し・保存前）には「×」を付け、行ごと消せる。既存行は従来どおり。

**ゴーストの値**（D6）

ゴーストの `title` と、ホバー時のラベルに `今回の値: ...` を添える。長い値は 40 字で
切る。

### 1.3 データの流れ

`DraftRow` に `isNew: boolean` を足す。save() の生成規則は変えない:

```ts
.filter((d) => d.include || d.base)   // 既存契約のまま
.map((d) => d.base
  ? { ...d.base, name, label, type: d.type, region }
  : { name, label, type: d.type, required: false, critical: false, region })
```

新規行は `base` 無しなので 2 つ目の分岐に落ち、`region` 付きの新しい項目として
PUT /schemas に載る。**サーバ側の変更は不要**（PUT は任意の項目列を受ける）。

`issue()` の検査に足すもの:

- 新規行の `name` が空 → 「項目名を入力してください（行: 表示名）」
- 新規行の `name` が既存行または他の新規行と重複 → 既存の重複検査に乗せる
- 新規行で領域が無い → **保存を止めない**（D2 の「領域なしで足す」を許す。
  ただし保存後のトーストで「領域が無い項目は AI が語彙から探します」と伝える）

### 1.4 文言

この画面の読取領域の説明は現在こうなっている:

> 読取領域は抽出結果を変えません。指定しておくと、項目が想定と違う位置で見つかった
> ことの検知に使われ、その結果は検証画面に参考として表示されます。

Part 1 だけを先に出す場合、新規項目に領域を引いても抽出は変わらない。**その状態で
「ここにある」と引かせるのは、Phase 4 off の期間中は誠実ではない**。よって:

- Part 1 を単独で出す場合: 新規行に「この項目は AI が語彙から探します。位置のヒントが
  抽出に使われるのは今後の版からです」と添える。
- Part 2 が既定 on になったら、この画面の説明文を「読取領域は、この位置に何があるかの
  ヒントとして抽出 AI に渡されます」に差し替える（**同じコミットで**）。

### 1.5 受け入れ条件（Part 1）

1. 行を選ばずに読取領域を引くと新規行ができ、名前を入れて保存すると
   GET /schemas/{doc_type} の fields に **region 付きで**その項目が返る。
2. 編集モードでも 1 が成り立ち、既存の項目・領域・除外領域は 1 ビットも変わらない
   （既存の「触っていない矩形は origin を返す」保全が新規行の追加で壊れない）。
3. 名前が空／重複／命名規則違反の新規行は保存が止まり、どの行かが分かる。
4. 新規行を「×」で消すと、その領域も消える（孤立した include 領域を残さない ──
   既存の `orphan` 検査が拾うが、そもそも作らない）。
5. ゴーストに値が出る。値が無い項目（null）は従来どおり位置だけ。

## 2. 反証可能な読取領域ヒント（Part 2）

### 2.1 いまのヒントの何が足りないか

いま KIE に渡るのは `region_px: {page, bbox}` だけである。モデルの側から見ると
「この矩形の中を優先せよ」としか言われておらず、**矩形の中身が項目の種類と合っている
かを判断する材料が無い**。sample8 では矩形の中に「大熊邸」（建物名）があり、項目は
customer_name。座標だけ見れば「宛先はここ」なので従った。

プロンプトには「ヒントは絶対条件ではない」と書いてあるが、**何をもって外れと判断
するかが書かれていない**ので、指示として機能していない。

### 2.2 決めたこと

| # | 決定 | 理由 |
|---|---|---|
| D7 | 領域に **`example_value`（テンプレート元でその位置にあった値）** を持たせる | 「前回ここには『株式会社千曲川ホーム』があった」があれば、「大熊邸」を見たときに種類が違うと判断できる。座標だけでは判断材料が無い |
| D8 | ヒントは矩形ではなく **矩形の中にある span の候補列** として渡す | モデルが実際に選ぶのは span である。矩形→span の解決をモデルに任せると、矩形に少しかかった span まで拾う。orchestrator 側で決定論的に解決し、候補として名指しする |
| D9 | **ヒントを渡す前に決定論で落とす**: 候補 span が 0 件／型付き項目で型に合う候補が無い | 「この帳票ではその位置に何も無い」「金額項目なのに数字が無い」は、モデルに聞くまでもなく間違ったヒント。落とした事実を metrics に残す |
| D10 | プロンプトに **「外れと判断する基準」** を明記し、項目ごとに **ヒントに従ったか** を返させる | 「絶対条件ではない」だけでは判断できない。従った／捨てたの申告は検証画面の参考表示と計測に使う |
| D11 | 検証画面に「ヒントに従った項目」を**参考表示**する（Phase 5 の位置バッジと同じ流儀。レビュー件数には影響しない） | 位置ガードが検知できない失敗を、人が見て気づける場所を作る。有効化で増えるレビューは 0 |
| D12 | 出荷は**再計測のゲート**を通してから。既定 on にする条件を先に決める | 前回と同じ。「良くなった気がする」で出さない |

### 2.3 保存契約: `RegionRect.example_value`

```python
class RegionRect(BaseModel):
    page: ...
    rect: ...
    label: Optional[str] = None
    # テンプレート元の帳票で、この領域にあった値（読取領域のみ。除外領域では未使用）。
    # KIE に「前回ここには何があったか」を伝えるためのもので、値の正規化はしない
    # （紙面の見た目に近いほど照合しやすい）。200 字で切る。
    example_value: Optional[str] = None
```

- fields JSONB の中なので**マイグレーション不要**。
- `RegionRect` は gateway の DTO からも参照されている（`SchemaFieldDto.region`）ので
  モデルに足せば往復する。**ただし必ず往復テストを足す**（pydantic v2 の既定
  `extra="ignore"` は DTO 側の漏れを黙って落とす。§4.2 で一度踏んでいる）。
- web の `RegionRect` 型に `example_value?: string | null` を足す。
- `isUntouched` の保全（触っていない矩形は `origin` をそのまま返す）は
  `example_value` ごと保全する。

**どこで値を決めるか。** テンプレート化画面の save() で、読取領域を持つ行について
`example_value = その行に表示されている今回の値`（`d.sample`）。検証画面で人が直した
値が `fields` に反映されていることが前提 ── **実装時に `data.fields` が corrections
適用後の値を返しているか確認すること**（`final_value` 列があるが、result DTO が
どちらを載せているかは要確認）。

新規項目（Part 1）は `sample` が無いので `example_value = null`。この場合ヒントは
候補 span だけで渡す（§2.4）。後述の §3.1（矩形の下の文字）を入れると、新規項目
にも例示値が付く。

**データの分類が変わることに注意。** これまで `field_schemas` は項目の定義だけを
持っていたが、`example_value` は**帳票の値（取引先名など）**である。RLS の中に
留まるので漏れはしないが、スキーマ管理画面にも表示されるようになる。隠さずに
出す（何がヒントに使われているかを人が見られる状態にする）。

### 2.4 ランタイム: 候補 span の解決と事前ガード

`_schema_for_prompt`（llm_nodes.py）を次のように変える。ヒント有効時のみ。

```python
# 領域を持つ field ごとに
px = _region_px(region, pages)               # 既存: 正規化 → 画素、ページ解決
if px is None: continue                       # 既存: 存在しないページは落とす
cands = [s for s in spans
         if s.page == px["page"] and _covered(s.bbox, [px["bbox"]], HINT_SPAN_RATIO)]
cands = cands[:HINT_MAX_CANDIDATES]           # 読み順の先頭から。大きすぎる矩形は弱いヒント
if not cands:
    dropped[name] = "no_spans_in_region"      # D9-a
    continue
if field_type in TYPED and not any(parses(field_type, s.text) for s in cands):
    dropped[name] = "no_typed_candidate"      # D9-b
    continue
stripped["region_hint"] = {
    "page": px["page"],
    "bbox": px["bbox"],
    "candidate_span_ids": [s.span_id for s in cands],
    "example_value": region.get("example_value"),
    # 例示値と一致する span がこの帳票にもある ＝ 同じ位置に同じ値。強い根拠
    "example_present": any(key(s.text) == key(ev) for s in cands) if ev else False,
}
```

- `_covered` は除外領域と同じ判定関数を使う（`EXCLUDE_SPAN_RATIO=0.5` と同じ 0.5 から
  始める）。判定の作りを 2 つ持たない。
- `HINT_MAX_CANDIDATES = 12`。超えた分は落とし、落とした事実を metrics に残す。
- `TYPED` は `money_jpy` / `date` / `number` 系。判定には決定論正規化のパーサを
  そのまま使う（新しく書かない）。
- `spans` は既に state にある（kie_extract は `state["spans"]` を受けている）ので、
  `_schema_for_prompt(schema, pages, spans)` と引数を足すだけ。
- **落とした・削ったは全て `metrics.region.hints` に書く**:
  `{"given": [...], "dropped": {name: reason}, "truncated": {name: n}}`。
  shadow の位置ガードと同じで、集計できないものは判断できない。

`region_px` キーは `region_hint` に置き換える。kie.py の `_has_region_hint` と
`_spans_for_prompt(with_bbox=...)` は `region_hint` を見るように直す。
**領域を持たない field には何も足さない**ので、`snapshots/kie_prompt_no_region.txt`
はバイト一致のまま。

### 2.5 プロンプト（`kie_region_hint.yaml`）

差し替え後の骨子:

```
# region_hint（読取領域のヒント）がある場合
region_hint は「同じ種類の帳票で、前回その項目がこの位置にあった」という情報である。
- candidate_span_ids: この帳票でその位置にある span。**まずここから探せ。**
- example_value: 前回その位置にあった値（無ければ null）。
- example_present: 同じ値がこの帳票の同じ位置にもある（true なら強い根拠）。

**ヒントを捨てる基準**（次のいずれかなら candidate を使わず、文脈と語彙で決めよ）:
- candidate の中身が項目の種類と合わない（会社名の項目なのに候補が住所・建物名・
  日付・数量など）
- example_value がある場合、候補の種類が example_value と合わない
  （会社名 vs 個人名、金額 vs 番号 など）
- 項目の見出し（「合計」「請求先」など）が candidate の近くに無く、別の場所に
  見出し付きで同じ種類の値がある

ヒントを捨てても value=null にしてはならない。捨てた場合は文脈から探せ。
出力の各 field に "hint": "followed" | "rejected" を付けよ（region_hint が無い
項目は null）。span_ids は実在する span を指すこと（指示 2 の根拠契約が優先）。
```

出力に `hint` を足すため、kie.py の item 解析で `item.get("hint")` を拾い、
`ExtractedField` には**足さず**（schemas パッケージの契約と DB 列を増やさない）、
kie_extract の戻り値に `hint_outcomes: dict[str, str]` として添える。ノードが
`metrics.region.hints.outcomes` に書く。

### 2.6 検証画面の参考表示（D11）

既存の「📐 領域外で検出 N 項目（参考）」と同じ場所・同じ流儀で、
`metrics.region.hints.outcomes` から「ヒントに従った項目」に小さなマークを出す。
文言は断定しない（「位置ヒントを使用」）。`title` に example_value を添えると、
レビュアが「前回は会社名だったのに今回は建物名」と気づける。

**レビュー件数・確信度・run status には一切触らない**（Phase 5 の表示と同じ
テストで固定する）。

### 2.7 出荷ゲート（D12）

`golden/src/newfan_golden/region_ab.py` で S1・S2 を再計測する。フィクスチャは
2026-09-07 と同じ（`region_ab_s1.jsonl` 21 枚、`region_ab_s2.jsonl` 5 枚）。
領域は `region_from_gold.py` で起こし、**`example_value` はテンプレート元の正解値**
を入れる（`build_region_fixtures.py` に 1 行足す）。

既定 on にする条件（**すべて**満たすこと）:

| # | 条件 | 根拠 |
|---|---|---|
| G1 | S1 の McNemar が「介入が有意に良い」（p < 0.05）のまま | 効き目を失っていない |
| G2 | **S2 で介入が対照を下回る帳票がゼロ**（帳票ごとの試行合計） | 前回の sample8（12/21 → 7/21）を再発させない。これが本設計の目的そのもの |
| G3 | sample8 の customer_name が対照以上（対照 3/3 に対し介入 ≥ 3/3 か、`hint: rejected` が 3/3） | 「1 行ずれ」の直接の再現ケース |
| G4 | `metrics.region.hints.dropped` が S2 の別レイアウト側（sample8 の customer_name）で理由付きで記録されている、または `rejected` が申告されている | 検知できない失敗を無くしたことの確認 |
| G5 | 領域を持たないスキーマのプロンプトがバイト一致（既存スナップショット） | 領域を使っていないテナントの挙動不変 |

通ったら `REGION_KIE_HINTS` の既定を on にし、環境変数はキルスイッチとして残す。
通らなければ off のまま、結果を実測記録（第 3 回）に残す。

## 3. 推奨の追加増分（別コミット・別判断）

### 3.1 矩形の下の文字を見せる（span の永続化と取得 API）

新規項目に領域を引いたとき、**「この枠には何が書いてあるか」がその場で見えない**。
いまは保存→再抽出（30 秒〜）で初めて分かる。span を run ごとに永続化し、
`GET /documents/{id}/spans?page=n` で返せば:

- 引いた矩形の中の文字を画面に出せる（「枠に含まれる文字: 2024/07/31」）
- 新規項目にも `example_value` を付けられる（§2.3 の穴が埋まる）
- Phase 5 の位置ガードの検討にも使える

必要なもの: `run_spans(run_id, page_no, spans JSONB)` テーブル（migration 0008、RLS +
FORCE）、`save_result` で state の spans を書く、gateway に viewer 可の GET。
1 ページ数百 span × 100 バイト ≒ 数十 KB／ページなので JSONB で足りる。

structure-svc に都度問い合わせる案は採らない（ページあたり数秒〜数十秒。矩形を引く
たびに待たせるのは操作にならない）。

### 3.2 ヒント元の記録（`origin: "ghost" | "manual"`）

領域が AI の位置（ゴーストクリック）由来か手描きかを保存すると、計測で
「手描きの領域だけ集計する」ができる。挙動には影響しない。**やるなら今**
（後から付けると既存の領域が全部 unknown になる）。

## 4. やらないこと

1. **編集モードでの項目削除** — D4。スキーマ管理画面のまま。
2. **明細（表）への読取領域** — 従来どおり非対応（行数が可変）。`columns` 持ちには
   `region_hint` を付けない（既存の分岐を維持）。
3. **ヒント付きと無しの二重抽出で照合** — 失敗の検知としては最も確実だが LLM 費用が
   倍になる。D9〜D11 で足りるかをゲートで見てから。
4. **住所項目だけヒントを外す** — 前回の計測で住所は一度も改善しなかったが、同じ
   データで決めると過適合。第 3 回の計測で再度見る。
5. **`example_value` の自動更新** — 再抽出の結果でスキーマの例示値を書き換えるのは
   「スキーマが勝手に変わる」ので採らない。人が編集モードで保存したときだけ更新。
6. **複数ファイルの同時アップロード・一括再処理** — 工程の後半だが本設計の外。
   別途（どちらも小さい）。

## 5. コミットの切り方

| # | 内容 | 単独で出せるか |
