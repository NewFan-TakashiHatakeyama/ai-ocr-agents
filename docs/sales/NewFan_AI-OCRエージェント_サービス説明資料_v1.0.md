# 第1部 現場担当者向け説明会（30分）

時間配分: §1 4分／§2 5分（デモ込み）／§3 5分（デモ込み）／§4 6分（**最重要**・デモ込み）／§5 3分／§6 2分／§7 体験ワーク3分／§8 1分＋質疑予備1分。

## 1. いまの困りごと → AI-OCR エージェントとは（4分）

**問題**: 紙・PDF の帳票（請求書・発注書・見積書・納品書）を、人が目で読んで基幹システムに打ち直している。従来の AI-OCR を入れても解決しきらない理由は3つ。

1. **テンプレート地獄** — 「取引先ごとに読み取り枠（座標）を登録する」方式のため、取引先が増えるたび・先方がフォーマットを変えるたびに登録作業が発生し、気づかないうちに読み取りが壊れる。
2. **結局、全件を目視突合している** — OCR が「読めた」と言っても信用できないので、結局1枚ずつ元帳票と見比べる。OCR を入れた後も工数が減らない。
3. **同じ間違いを毎月直している** — 「1 を 7 と読む」「あの取引先の社名表記だけいつも崩れる」。直した知識が誰の頭の中にも残るだけで、システムには一切還元されない。翌月また同じ場所を直す。

**解決**: NewFan AI-OCR エージェントは、**テンプレート（座標）を登録しない AI-OCR** です。登録するのは「請求書から何を取りたいか」という**項目名の一覧だけ**。あとは AI が帳票を読み、**どこから取ったか（根拠）を必ず示し**、人が直した内容を**覚えて次回から自動で当てにいきます**。

そして、読み取った後の「基幹システムへの転記」まで、**ノードをつないだ絵**で自動化できます — 画面操作を録画する従来型 RPA と違い、**画面レイアウトが変わっても壊れません**。

- **トーク**: 「今日お伝えしたいのは2つだけです。**登録するのは項目名だけ**。そして**一度直せば、次から直さなくていい**。この2つです」

**提供形態のご案内（この時点で1行触れる）**: 本サービスは **SaaS（マルチテナント）** で提供します。加えて、**お客様専用環境での提供や、業種特化・自社帳票特化のカスタマイズ実装 OCR** も個社別にご提供可能です（詳細は第2部 §10）。

## 2. できること①: テンプレート登録なしで読む — 登録するのは「項目名」だけ（5分・デモ込み）

**問題**: 「新しい取引先の請求書が来た。OCR に覚えさせるのに半日かかる」「先方がフォーマットを変えたら読めなくなった」。

**解決**: 帳票種別（請求書・発注書・見積書…）ごとに**項目の一覧（スキーマ）**を1回だけ定義します。座標も、罫線の位置も、サンプル帳票の枚数も要りません。**同じ「請求書」であれば、レイアウトが違う取引先でも同じスキーマで読めます。**

### 操作手順（そのままデモ手順）

**手順1** — 帳票をアップロードする。ドラッグ＆ドロップ、またはチャット画面へのファイル添付。

![アップロード（SCR-02）](images/02_ドキュメント一覧_アップロード.png)

**手順2** — 「抽出を開始」を押す。このとき、**システムがファイルを見て帳票種別を推定**し、使うスキーマを既定で選んでくれます（「推定: 見積書／信頼度 100%」のように表示）。違っていればその場で別のスキーマに変更できます。

![抽出開始と帳票種別の推定](images/03_抽出開始_分類サジェスト.png)

- **画面のポイント**: ① 推定された帳票種別と信頼度が明示される ② 人が上書きできる ③ 上書きした選択が優先される（人の指定が常に最優先）。

**手順3** — 数十秒で結果が出る。**取れた値ごとに、帳票画像のどこから取ったかが枠（bbox）で示されます。**

![検証画面（SCR-03）](images/04_検証画面_全体.png)

- **トーク**: 「テンプレートを作っていないのに読めています。**この製品には『座標を登録する』という作業がそもそも存在しません**」
- **発表者ノート**: 「テンプレートレス」を「何も登録しなくていい」と言い換えないこと。**項目定義（スキーマ）は必要**で、しかも「項目が取れない」相談の大半はスキーマに項目が無いことが原因（実証済み・付録A）。ここは正直に説明したほうが導入後の期待値ずれが起きない。

**項目を増やすのも1分** — 「担当者名と振込先も欲しい」と思ったら、スキーマ管理画面で項目を足すか、**チャットに『請求書スキーマに支払方法を追加して』と話しかけるだけ**。AI が変更内容を提案 → 人が承認 → 新しい版として保存されます（版管理されるので、いつでも前の版に戻せます）。

![チャットからのスキーマ変更（SCR-01）](images/05_チャット_スキーマ変更承認.png)

- **発表者ノート**: 実証済みの事実として使える数字 — **4項目しか定義していなかった請求書スキーマを15項目に拡張したところ、15項目すべてが根拠付きで抽出成功した**（実 LLM・実帳票での確認）。「取れないのはモデルの限界ではなく定義漏れ」という説明の裏付けになる。

## 3. できること②: 直す作業そのものを短くする（5分・デモ込み）

**問題**: 「OCR の結果を全件、元の紙と見比べている。これなら最初から手入力と変わらない」。

**解決**: 検証画面（SCR-03）は「**どこを見ればいいか**」を機械が指定します。全件を見るのではなく、**機械が自信のない箇所だけ**を見る運用に変わります。

![検証画面・要確認フィールド](images/06_検証画面_要確認フィールド.png)

- **確信度で色分け** — 各項目に確信度バーが付き、赤（<0.6）／黄（<0.8）／緑（≥0.8）／青（検算合格済み）で表示。**要確認の項目がパネル最上部に集められます**。
- **クリックで元の場所に飛ぶ** — 項目行をクリックすると帳票画像側の該当箇所がハイライトされ、そこまでスクロールします。紙をめくる必要がありません。
- **文字単位の差分ポップオーバー** — 「1 か 7 か」で迷う箇所は、その文字を**拡大表示**し、①OCR の原値 ②AI の補正案 ③手入力 の3つを並べて見せます。**採択はワンクリック（キー `1` / `2` / `e`）**。
- **計算が合っているかを機械が検算** — 明細合計＝小計、小計＋消費税＝合計、数量×単価＝金額、適格請求書登録番号（`T`＋13桁）の**法人番号チェックディジット**、銀行コード桁数、請求日≤支払期日、同一請求の重複検知。**検算に通った金額項目は自動的に「確認済み」へ格上げ**され、人が見る対象から外れます。
- **キーボードだけで完結** — `n`/`p` で要確認項目を巡回、`Enter` で承認、`e` で編集、`Ctrl+Enter` で確定。マウスに持ち替えません。
- **編集は自動保存** — 500ms のデバウンスで自動保存されるので「保存し忘れて消えた」がありません。

![文字差分ポップオーバー](images/07_検証画面_文字差分ポップオーバー.png)

- **トーク**: 「見るのは**赤と黄だけ**です。緑と青は機械が根拠と検算で裏を取っています。**1↔7 の誤読は、金額の検算でほぼ確実に落ちます**」
- **発表者ノート**: 「精度○%」「工数○%削減」の数値は**自社実測が取れるまで言わない**（付録A）。この節は「見る対象が減る仕組み」の説明に徹する。

**明細表（テーブル）も同じ考え方** — 明細行は表エディタで検証します。セルを選ぶと帳票画像側の該当セルが光り、行ごとに「数量×単価＝金額」、フッタで「明細合計⇔小計・税・合計」をリアルタイム検算します。

## 4. できること③: **一度直せば、二度と直さない**（6分・デモ込み）★本日の主役

**問題**: これが現場の最大の不満です。

> 「あの取引先の請求書、毎月かならず**同じ場所**を同じように直している。先月も、先々月も。私が直したことは、どこにも残らない」

従来の OCR には「学習」がありません。あるとしても「テンプレートを直す＝また座標を触る」だけです。

**解決**: NewFan AI-OCR エージェントは、**人が直した内容を組織の資産として蓄積し、AI が次回から自動で当てにいきます。** しかも「なんとなく似ているから当てる」のではなく、**再現できることを機械が検証してから**恒久ルールに昇格させます。

### 学習の3段階（この3段が本製品の核心）

**第1段: 修正メモリ（その場で効く）**
あなたが検証画面で直した1件は、`どの帳票種別 × どの取引先 × どの項目 × どんな原値` という文脈のキーとともに保存されます。次に**似た文脈**の帳票が来たとき、AI はこの過去の修正例を参照しながら読みます。1件直しただけでも、次から効きます。

**第2段: ルール化（同じ直しが5件たまったら）**
同種の修正が **5件** たまると、システムが自動的に「これはルールにできないか？」を検討します。取り出されるルールは4種類の**決定論ルール**（毎回まったく同じ結果になる、AI 推論を使わない変換）と、1種類の **LLM 最適化**です。

| ルール種別 | 内容 | 例 |
|---|---|---|
| `regex_replace` | パターン置換 | 伝票番号の先頭に混入する記号を除去 |
| `vocab_map` | 語彙の写像（表記ゆれの名寄せ） | 「サンプル（株）」「サンプル社」→「株式会社サンプル」 |
| `format` | 書式の強制 | 伝票番号は `^7\d{5}$` |
| `checksum` | チェックディジット検証 | 適格請求書登録番号 |
| `llm_hint` | 決定論化できない知識を自然言語で AI に渡す | 「この取引先は明細の最終行が値引き行なので合計に含めない」 |

**第3段: 自動検証ゲート（間違ったルールを本番に出さない）★ここが差別化点**
抽出されたルールは、いきなり有効にはなりません。**そのテナントの過去の確定済み帳票をホールドアウトとして機械が再適用**し、

- **過去の修正を 90% 以上再現できること**
- **すでに正しかった値を壊す誤適用が 0 件であること**

の**両方**を満たしたときだけ `draft` → `active` に昇格します。検証レポート（何件に当たり、何件を再現し、何件壊したか）は画面で確認でき、管理者が人の判断で有効化／退役させることもできます。

![ルール管理と検証レポート（SCR-05）](images/08_ルール管理_検証レポート.png)

- **画面のポイント**: ① ルール種別のピル表示 ② 検証レポート（再現率・回帰件数） ③ **基準を満たさないルールは「有効化」ボタンが押せない**（ゲート）。
- **トーク**: 「学習する AI-OCR は他社にもありますが、**『学習した内容が本当に正しいかを、過去データで機械が検算してから本番に出す』**——ここが違います。**間違った学習が本番を壊すことを、仕組みで防いでいます**」

### AI が勝手に書き換えないための2重の縛り

「AI が学習して自動で直す」と聞くと、**勝手に値を変えられる**のが怖いはずです。本製品はここを構造的に縛っています。

- **縛り①（混同文字表）** — AI による自動置換が許されるのは、**視覚的に混同しうる文字の組み合わせ**（1↔7、0↔O、日↔曰 など、あらかじめ定義された表）に該当する場合、**または**このテナントの過去の修正例に一致する場合**だけ**です。それ以外の「AI がそう思った」変更は**自動適用されず、必ず人の確認に回ります**。
- **縛り②（根拠必須）** — すべての抽出値は、帳票画像上の**実在する読み取り領域（span）に紐付いていること**が必須です。紐付けられない値は確信度 0 として強制的に人の確認へ回ります。**AI が根拠なしに値を作ることはできません。**

- **トーク**: 「AI が勝手に賢くなって勝手に書き換える、ということは起きません。**AI は「見えている文字の読み違い」しか直せない**設計です」

### この機能が効いてくる形（説明会での言い方）

- 月初1週目: 取引先 A の請求書で「1→7」を3回直した。→ **修正メモリに入り、AI が参照し始める。**
- 月初2週目: 同じ直しが5件を超えた。→ **ルール候補が自動抽出され、過去データで検証 → 基準を満たせば有効化。**
- 翌月: **同じ箇所は直さなくてよくなっている。**

- **発表者ノート**: 「◯ヶ月で人の確認がゼロになる」等の**時間軸を約束しない**（未実測・付録A）。「同じ直しを繰り返さない仕組みがある」「効き具合はダッシュボードで見える」までに留める。

## 5. できること④: 誤魔化さない — 分からないときは「分かりません」と言う（3分）

**問題**: 生成 AI の幻覚（それらしい嘘）。「AI が入れた数字が実は帳票のどこにも書いていなかった」は、経理業務では事故になります。

**解決**: 本製品は「**自信がないなら人に回す**」を既定動作にしています。

- **根拠が取れない値は確定させない**（前節の「縛り②」）。
- **確信度が閾値を下回る項目は必ず人の確認へ**。閾値は項目の重要度で3段階（**重要項目 0.90 / 標準 0.80 / 備考など 0.60**。テナントごとに調整可能で、「金額は必ず人が見る」といった**無条件レビュー指定**もできます）。
- **読みにくいページに対する画像 AI（VL）の読み取り結果は、自動確定を禁止**。必ず人の確認に回ります。
- **値の由来が全部見える** — 各項目に「OCR 原値／AI 補正／ルール適用／人手」のバッジが付き、ホバーすると**なぜそう直したかの理由と、参照した過去修正例の ID** まで表示されます。

![値の由来バッジ](images/09_検証画面_由来バッジ.png)

- **トーク**: 「監査で『この数字の根拠は？』と聞かれたとき、**帳票画像のこの位置から、この経路で入った**と1画面で示せます」

## 6. 職種別ユースケース（2分・スライド1枚）

「自分の業務で何に使えるか」を職種の言葉で示す（体験ワークのお題カタログを兼ねる）。

- **経理（買掛）**: 取引先から届く請求書 PDF → 適格請求書登録番号のチェックディジット検証・税率別（10%／軽減8%）の税額検算・重複請求の検知まで自動 → 会計システムへ自動転記。**「登録番号が形式だけ正しくて実在しない」帳票を機械が弾きます。**
- **受発注事務**: メール／共有フォルダに届く注文書を自動で取り込み → 帳票種別を自動判定（**請求書ワークフローに発注書が混ざったら止める**）→ 受注データとして基幹 DB へ UPSERT。
- **物流・現場事務**: スマホ撮影した納品書・受領書を取り込み → 明細表を行単位で検算 → 要確認だけを事務所で確認。
- **情シス・業務改善**: 「読む」だけでなく「読んだ後の転記」まで**ノードをつないだ絵**で組める。**画面操作を録画する RPA と違い、先方のフォーマット変更や画面改修で壊れません**（第2部 §3）。

## 7. 体験ワーク（3分）

参加者自身に1枚読ませる:

1. 手元の帳票（機密を含まないもの）をドラッグ＆ドロップ
2. 推定された帳票種別を確認して「抽出を開始」
3. 結果が出たら **`n` キーで要確認項目を巡回**し、1つ直して `Ctrl+Enter` で確定
4. **直した内容が「あなたのテナントの修正メモリ」に入ったことを、由来バッジで確認する**

**うまく使うコツ**（スライド1枚）: ① 欲しい項目が出ないときは、まず**スキーマの項目定義**を疑う（モデルの限界ではなく定義漏れが大半） ② 直すときは「正しい値」を入れる（後で機械が検証に使う教師データになります） ③ 迷ったら承認せず、要確認のまま残す。

## 8. 使い始め方と FAQ（1分＋質疑）

- **アカウント**: 管理者から招待。ロールは 一般ユーザー（検証・確定）／管理者（スキーマ・ルール・ワークフロー・接続）。
- **対応形式（現時点）**: PDF / PNG / JPEG / TIFF（複数ページ可）。**Word・Excel・PowerPoint は現時点で未対応**（設計上は PDF 変換経由で対応予定・付録A）。制限は既定で 50MB/ファイル、300ページ/ドキュメント。

**FAQ 想定問答**:

- **Q. 直した内容は他のお客様（他テナント）にも共有されますか？** → いいえ。修正メモリ・ルールは**テナント単位で完全に分離**されており、他社に出ることはありません。また、修正内容をベクトル化する処理は**自社環境内のローカルモデル**で行うため、**修正データを外部の埋め込み API へ送りません**。
- **Q. AI に読ませたら、うちの帳票が AI の学習に使われますか？** → 基盤モデルの追加学習には使いません。学習するのは**お客様テナント内の修正メモリとルール**だけです。
- **Q. 手書き文字は読めますか？** → 印字帳票を主対象としています。手書きは帳票・筆跡により差が大きいため、**実帳票での事前検証（PoC）を前提**にご案内します。
- **Q. 読み取り精度は何%ですか？** → **お客様の実帳票で測る数字です。**当社標準のゴールデンセットでの回帰試験は継続実施していますが、「一般論の精度%」はご提示しません。PoC で対象帳票の実測をお出しします。
- **Q. 間違って確定してしまったら？** → 確定操作・修正はすべて監査ログに残り、誰がいつどの値をどう変えたかを追跡できます。

# 第2部 管理者向け説明会（約45分＋質疑15分）

時間配分: §1 3分／§2 4分／**§3 ワークフロー 10分**／**§4 学習ループの運用 8分**／§5 3分／§6 4分／§7 3分／§8 4分／§9 2分／§10 提供形態 3分／§11 FAQ 1分。押した場合に飛ばす節は §5・§9。

## 1. 全体像（1枚・3分）

処理の流れは **取込 → 前処理・ページ化 → レイアウト解析＋OCR → 品質ゲート（必要なら画像 AI へ）→ 過去修正の参照 → 項目抽出（KIE）→ 決定論正規化 → 確信度算出 → LLM 補正（低確信のみ）→ 決定論検算 → 確信度ゲート → 人の確認（HITL）→ 学習 → 確定・出力**。

![抽出グラフ全体像](images/10_全体像_抽出グラフ.png)

**設計の骨格として押さえていただきたい3点**:

1. **LLM は「主役」ではなく「限定的な補助」** — 項目抽出（KIE）と、**低確信の項目に限った**補正だけに使います。正規化・検算・重複検知は**すべて決定論処理**（AI 推論を使わない、毎回同じ結果になる処理）です。→ 監査可能性とコストの両方に効きます。
2. **抽出グラフの内部構成はユーザーが変更できない**（意図的な制約）。品質保証と監査の境界を固定するためで、お客様が組めるのは後述の**粗粒度ワークフロー**です。
3. **すべての値に根拠（帳票上の位置）が紐付く** — 紐付かない値は自動確定できません。

**セキュリティ審査で効く1行**: 全業務テーブルに **Row Level Security** を適用したマルチテナント分離。修正メモリのベクトルインデックスも**テナント別**。接続情報のパスワード・トークンは **DB に保存せず AWS Secrets Manager 参照**のみを持ち、参照先はテナント帰属を検証した名前空間（`ai-ocr/<env>/conn/<tenant_id>/`）に限定されます。

## 2. 帳票の「型」づくり — スキーマ管理（4分）

**問題**: 従来型 AI-OCR の導入コストの大半は「テンプレート整備」。取引先 300 社なら 300 枚分のレイアウト登録が必要で、フォーマット変更のたびに保守が発生する。

**解決**: 本製品に**テンプレート（座標登録）という概念はありません**。代わりに帳票種別（`doc_type`）単位の**項目定義（スキーマ）**を持ちます。

![スキーマ管理（SCR-06）](images/11_スキーマ管理_版タブ.png)

- **定義するもの**: 項目名・表示ラベル・型（文字列／日付／金額／数値／税率／登録番号／口座）・必須か・**critical（重要項目＝レビュー閾値を最も厳しくする）**か。
- **版管理**: 保存すると新しい版（v1, v2, …）が作られ、**実行中のワークフローは開始時点の版を参照し続けます**。版を戻せます。
- **作成経路は2つ**: ① スキーマ管理画面で直接編集 ② **チャットに自然言語で依頼**（「請求書スキーマに支払方法を追加して」→ AI が変更案を提示 → **承認カードで人が承認** → 同一の版管理を通って新版作成）。**AI の提案が人の承認なしに反映されることはありません。**
- **重複防止**: 既存 `doc_type` と同名での新規作成はブロック（暗黙の版バンプによる事故を防止）。

- **トーク**: 「導入初期にお願いするのは『**帳票の種類ごとに、欲しい項目を並べる**』だけです。取引先ごとの作業はありません」
- **発表者ノート**: 実証済みの説明弾 — 「項目が取れない」の第一容疑はスキーマ定義（4項目→15項目に拡張したら15項目すべて取得成功）。**運用チームには「まずスキーマを疑え」を徹底**していただく。

## 3. ワークフロー — 絵で組む、壊れない RPA（10分・4枚）★本日の主役その1

**問題**: OCR は「読む」までしかやりません。読んだ後の「基幹システムへの転記」は、結局のところ ①人が打つ ②個別に作り込む ③画面操作型 RPA で自動化する、のいずれか。**③は画面レイアウトが1ピクセル変わると壊れ、壊れたことに誰も気づかない**まま業務が止まります。

**解決**: 本製品は「**どこから取り込み → どう読み → どう分岐し → どう変換して → どこへ届けるか**」を、**ノードをつないだ図**として定義します。画面座標にも UI にも依存しないので、**先方の画面改修やレイアウト変更では壊れません**。

![ワークフローエディタ（SCR-07）](images/12_ワークフロー_エディタ全体.png)

- **画面のポイント**: ① 左のパレットからノードをドラッグ＆ドロップ ② ノード同士を線でつなぐだけ ③ 右パネルで各ノードの設定（**すべて日本語のフォーム**。JSON を書く必要はありません）。ミニマップ・カテゴリ色分け・種別アイコン付き。

### 3.2 「壊れない」ための3つの仕掛け（ここが従来 RPA との差）

**① 保存時・有効化時の自動点検（lint）** — 図が業務として成立しているかを機械が検査し、問題のあるノードを画面上で赤くハイライトします。

- DAG になっているか／トリガーが1つ以上あるか／到達できないノードが無いか
- **DB・ファイル出力の上流に必ず「AI-OCR 抽出」があるか**
- **条件分岐に else があるか**（分岐漏れで黙って消える経路を作らせない）
- **人の確認ゲートを通らずに出力へ到達する経路がないか**（要確認帳票が黙って基幹システムへ流れる事故の防止・警告）
- 同一接続に対する重複トリガー（1ファイルから実行が二重生成される構成）はエラー

![構成点検（lint）の指摘表示](images/13_ワークフロー_lint指摘.png)

**② 有効化の前に「本番に何が起きるか」を見る（dry-run）** — 直近の確定済み帳票を入力に全ノードを実行し、**出力だけは実行せず「生成される SQL／送信ペイロードのプレビュー」を返します**。

- **プレビューと実行は同一のコード**が生成します（「プレビューでは通ったのに本番で違う SQL が出た」が起きない設計）。
- **有効化は dry-run 成功が前提条件**です。点検も通っていない図は本番になりません。

![dry-run 出力プレビュー](images/14_ワークフロー_dryrun_プレビュー.png)

**③ 有効化＝版の固定** — 有効化した時点の図が版として固定され、実行中のワークフローは開始時点の版を参照し続けます。編集途中の図が実行中の業務に混ざりません。

- **トーク**: 「**点検 → 出力を確認 → 有効にする**。この3ステップがツールバーに並んでいます。**点検に通らない図、出力を確認していない図は、そもそも有効にできません。**」

### 3.3 基幹 DB への書き込みを情シスが許可できる形にする

「AI が基幹 DB に書く」は、情シスにとって最大の懸念です。本製品は**能力そのものを構造的に絞って**います。

| 制約 | 内容 |
|---|---|
| **任意 SQL 不可** | 実行される SQL は**プリペアドステートメントの機械生成のみ**。ユーザーが SQL 文字列を書く場所はありません |
| **INSERT / UPSERT のみ** | **UPDATE・DELETE は実行できません**（機能として存在しない） |
| **許可テーブル制** | 書き込み先は接続ごとの許可テーブル一覧に**完全一致**したものだけ |
| **行数上限** | 1 実行あたり既定 1,000 行 |
| **キー列必須** | INSERT は書込キーによる重複防止。**UPSERT はキー列の指定が必須**（無指定で業務キー重複を黙殺し、無音のデータ欠落を起こさせない） |
| **接続情報** | パスワード・トークンは DB に持たず Secrets Manager 参照のみ。参照先名前空間はテナント帰属を検証 |
| **推奨運用** | お客様側 DB には **INSERT/UPSERT 権限のみの専用ユーザー**を作っていただく（導入手順書に明記） |
| **失敗時ポリシー** | `retry` / `skip_and_notify` / `halt_notify`（既定 = **止めて通知**） |

- **トーク**: 「『AI に DB を触らせる』のではありません。**AI にできるのは、許可されたテーブルに、決められた形の行を追加することだけ**です。消すことも、書き換えることもできません」
- **実測（そのまま話せる数字）**: S3 に帳票を配置 → **約2秒で自動取込** → 抽出 → 人の確認待ちへ → 確定操作から **1秒未満**で基幹 DB（`erp_demo.invoices`）へ実 UPSERT。Google Drive／Microsoft 365 のフォルダ監視は、**ファイル配置から15秒以内**に検知（compose 実測・実 OCR／実 LLM）。

### 3.4 監視取込の安全設計（重複取込・取りこぼしの防止）

- **冪等性**: ファイルのパス＋コンテンツハッシュ／ETag を処理済みカーソルとして管理し、**同一ファイルは既定でスキップ**（明示的な再処理 API のみ許可）。
- **常駐ゼロのポーリング**: フォルダ監視はワーカー主ループ内のインターバル処理として実装（常駐プロセスを増やさない）。1 tick あたりの処理件数に上限があり、**1テナントの大量投入が他テナントの処理を止めません**。
- **同期結果の可視化**: 接続一覧に「最終同期（✓N分前／✗失敗＋理由）」を表示。同期失敗は3回で打ち切り（恒久失敗メッセージがキューに滞留し続けるのを防止）。
- **サービス停止中のイベント**: SQS に滞留し、再開後に自動で消化されます（実測: 停止中に配置 → 再開後 86 秒で drain）。

## 4. 学習ループの運用 — 「同じミスを二度と繰り返さない」を管理する（8分・4枚）★本日の主役その2

**問題**: 「AI が学習します」と言われても、管理者としては ①**何を学習したのか分からない** ②**間違った学習が本番を壊すのが怖い** ③**止められない**、の3点で承認できない。

**解決**: 本製品の学習は、**すべて可視・検証済み・人が止められる**形にしてあります。

### 4.1 学習ループの全体像

![学習ループ（1枚図）](images/15_学習ループ_全体図.png)

```
人が検証画面で修正
   ↓（1件から）
修正メモリに登録（テナント別・文脈キー付き・ローカル埋め込み）
   ↓（同種5件たまったら自動起動）
ルール候補の抽出（regex_replace / vocab_map / format / checksum / llm_hint）
   ↓（過去の確定済み帳票で機械が検算）
自動検証ゲート：再現率 90%以上 かつ 誤適用 0件
   ↓（通過したものだけ）
active（以後は決定論処理として毎回適用・AI 推論なし）
   ↓（効かなくなったら）
retired（人が退役させる／画面から）
```

### 4.2 各段の管理ポイント

**修正メモリ**

- キーは `帳票種別 × 取引先 × 項目 × 原値 × 周辺文脈`。次回の抽出時に**類似上位5件・類似度0.75以上**が AI へ few-shot として渡ります。
- **埋め込み（ベクトル化）はローカルモデルで実行**します（`multilingual-e5-small`）。**お客様の修正データを外部の埋め込み API へ送信しません**（設計判断として明文化）。
- 正本は PostgreSQL の修正ログ。ベクトルインデックスは**いつでも DB から再構築できる派生物**として扱います（破損時の復旧手順が単純）。

**ルール自動検証（有効化ゲート）**

![ルール検証レポート詳細](images/16_ルール管理_有効化ゲート.png)

- 基準: **過去修正の再現率 ≥ 90%**、かつ**確定済み正解値への誤適用 0 件**。
- **基準を満たさないルールは、画面上で「有効化」ボタンが押せません。**
- 検証レポート（対象件数・再現件数・回帰件数・ルール定義 JSON）を画面で確認でき、**管理者による人手 override も可能**（override 自体が監査に残ります）。
- 過剰一般化の抑止: 根拠3件未満のパターンは決定論ルールにせず、**`llm_hint`（自然言語のヒント）として出力**する規約。

**LLM 最適化（`llm_hint`）— 決定論化できない業務知識を AI に渡す**

- 「この取引先は明細の最終行が値引き行」「押印欄の数字は取らない」のような、**正規表現では書けない業務知識**を**日本語の文章のまま**登録できます。有効化すると、その帳票種別の抽出プロンプトに**ルールヒントとして自動注入**されます。
- **人が手で書いた `llm_hint` は再現率検証の対象外**（決定論変換ではないため機械検算になじまない）で、検証レポート無しに有効化できます。
- ただし **AI（エージェント）が自動生成した `llm_hint` は従来どおり検証ゲートを通します** — 「検証されていないルールが1クリックで本番へ注入される」経路を作らないための、意図的な非対称です。
- 入力制限: ヒント本文 2,000 文字／説明 200 文字、未登録の帳票種別には作れません。

![LLM 最適化の登録フォーム](images/17_ルール管理_LLM最適化登録.png)

- **トーク**: 「『AI にコツを教える』が、**管理画面のフォームから日本語でできます**。しかも**人が書いたものと AI が作ったものを区別して扱い**、AI 由来は必ず検証を通します」

**学習の効きを数字で見る**

- ダッシュボード（SCR-04）に「学習の効き」ブロックがあり、有効ルール数・修正メモリ件数・処理内訳（自動確定／要確認／失敗）を表示します。
- **フィールド精度**は「確定した Run のうち、人が一切修正しなかった項目の割合」として機械算出しています（週次の人手監査の代替指標）。
- **LLM コスト**は Run ごとの実使用量差分を永続化し、直近30日合計を表示します（実 AWS 環境で実測値の表示を確認済み）。

![ダッシュボード（SCR-04）](images/18_ダッシュボード_KPIと学習の効き.png)

- **発表者ノート**: ダッシュボードの「フィールド精度」は**無修正率**であって外部基準の正解率ではない。**「精度 100%」と読み替えて話さない**（付録A）。

## 5. 帳票の自動仕分け（3分）

**問題**: 「請求書フォルダに発注書が紛れ込み、請求書として基幹システムに入った」——これは OCR の精度問題ではなく、**仕分けの問題**です。

**解決**: 帳票種別の判定を**2箇所**に配置しています。

1. **抽出前のサジェスト（人向け）** — アップロード時にファイル名と本文からキーワードスコアで種別を推定し、**推定種別と信頼度を出したうえでスキーマを既定選択**。人が上書きできます。`doc_type` が明示指定されている場合は**その指定が最優先**。
2. **ワークフローの分類ゲート（機械向け）** — 「帳票分類」ノードが、内容の信号（ファイル名＋抽出結果）から種別を判定し、**信頼度 0.75 以上で許可リスト外の種別だった場合は実行を停止**します。信号が無い／確信が持てない場合は従来どおりスキーマの種別を踏襲します（非破壊）。

- **発表者ノート**: 分類器は**キーワードスコア方式**（LLM 分類ではない＝決定論・同じ入力なら同じ結果）。敵対的レビューで潰した既知の落とし穴3点（包含語の二重加点／英単語の部分一致による埋没ヒット／全角英字の正規化漏れ）は修正済み。**「AI が完全に仕分けます」とは言わない** — 「許可リスト外を止めるゲート」として説明する。

| `gdrive` | Google Drive フォルダ監視 | 実装済み（**実クレデンシャルでの OAuth E2E は未了**・付録A） |

## 7. 品質・確信度・ゲート設計（3分）

管理者が「どこまで自動化するか」を決めるためのダイヤルは以下です。

| パラメータ | 既定 | 意味 |
|---|---|---|
| `conf.threshold.critical` | 0.90 | **重要項目**（金額・登録番号など）のレビュー閾値 |
| `conf.threshold.standard` | 0.80 | 標準項目 |
| `conf.threshold.low_impact` | 0.60 | 備考など |
| `conf.always_review_fields` | テナント設定 | **確信度に関わらず必ず人が見る項目**の指定 |
| `memory.knn_topk` / `sim_threshold` | 5 / 0.75 | 過去修正の参照件数・類似度下限 |
| `rules.min_evidence` | 5 | ルール抽出を起動する同種修正数 |
| `rules.validation_pass` | 0.90 / 回帰0件 | ルール自動有効化の基準 |

**確信度の作り方（説明できるようにしておく）**: `確信度 = min(OCR の文字確信度, 根拠の強さ)`。根拠の強さは **1.00 = 帳票の文字列と完全一致 / 0.85 = 型変換のみで導出（和暦→西暦など） / 0.70 = 画像 AI 由来・部分一致 / 0.00 = 根拠なし（強制レビュー）**。**検算に合格した項目は 0.98 へ格上げ**されます。

**完全自動化（HITL スキップ）について**: 既定 OFF。`auto_confirm` を有効にする場合でも、**critical 項目を含む帳票は必ず人の確認ゲートを通します**（テナント設定で緩和可能ですが、有効化時に警告表示＋監査ログ記録）。

# 付録C: 用語

| 用語 | 意味 |
|---|---|
| **スキーマ** | 帳票種別ごとの「取りたい項目の定義」。テンプレート（座標登録）ではない。版管理される |
| **テンプレートレス** | 取引先ごとのレイアウト登録（座標指定）を必要としない方式。項目定義は必要 |
| **HITL** | Human In The Loop。機械が自信を持てない箇所だけを人が確認する運用 |
| **確信度（confidence）** | その値がどれだけ確からしいかの指標。OCR の文字確信度と根拠の強さの小さい方 |
| **grounding（根拠）** | 抽出値が帳票画像上のどの読み取り領域から来たかの紐付け。根拠なしの値は自動確定不可 |
| **修正メモリ** | 人が直した内容をテナント別に蓄積し、次回の抽出で参照する仕組み |
| **ルール** | 修正メモリから抽出され、機械検証を通って恒久適用される変換規則。決定論4種＋LLM最適化1種 |
| **決定論（deterministic）** | AI 推論を使わず、同じ入力に対して常に同じ結果を返す処理。正規化・検算・分類ゲートが該当 |
| **auto-elevation** | 検算に合格した項目の確信度を自動的に引き上げ、人の確認対象から外す仕組み |
| **dry-run** | ワークフローを出力なしで実行し、生成される SQL／ペイロードをプレビューすること。有効化の前提条件 |
| **STP 率** | Straight Through Processing 率。人が一切触らずに完了した帳票の割合（**現在未実測**） |
