# 現場担当者向け説明会（30分）

時間配分: §1 3分／§2 4分（デモ込み）／§3 5分（デモ込み）／**§4 7分（最重要・デモ込み）**／**§5 5分**／§6 2分／§7 職種別 1分／§8 体験ワーク2分／§9 まとめ1分＋質疑予備。押した場合に飛ばす節は §6・§7（FAQ は資料配布で代替）。

## 1. いまの困りごと → AI-OCR エージェントとは（3分）

**問題**: 紙・PDF の帳票（請求書・発注書・見積書・納品書）を、人が目で読んで基幹システムに打ち直している。従来の AI-OCR を入れても解決しきらない理由は3つ。

1. **テンプレート地獄** — 取引先ごとに読み取り枠（座標）を登録する方式のため、取引先が増えるたび・先方がフォーマットを変えるたびに登録作業が発生し、気づかないうちに読み取りが壊れる。
2. **結局、全件を目視突合している** — OCR が「読めた」と言っても信用できないので、1枚ずつ元帳票と見比べる。OCR を入れた後も工数が減らない。
3. **同じ間違いを毎月直している** — 「1 を 7 と読む」「あの取引先の社名表記だけいつも崩れる」。直した知識は誰かの頭の中に残るだけで、システムには還元されない。翌月また同じ場所を直す。

**解決**: NewFan AI-OCR エージェントは、**テンプレート（座標）を登録しない AI-OCR** です。登録するのは「請求書から何を取りたいか」という**項目名の一覧だけ**。AI が帳票を読み、**どこから取ったか（根拠）を必ず示し**、人が直した内容を**覚えて次回から自動で当てにいきます**。さらに、読み取った後の「基幹システムへの転記」まで、**ノードをつないだ絵**で自動化できます。

![サービス全体像（1枚図）](images/01_全体像_処理の流れ.png)

- **トーク**: 「今日お伝えしたいのは2つだけです。**登録するのは項目名だけ**。そして**一度直せば、次から直さなくていい**。この2つです」
- **提供形態（この時点で1行だけ）**: SaaS で提供します。**個社別の専用環境・カスタマイズ実装 OCR も可能**です（補足章 §C-6）。

## 2. できること①: テンプレート登録なしで読む — 登録するのは「項目名」だけ（4分・デモ込み）

**問題**: 「新しい取引先の請求書が来た。OCR に覚えさせるのに半日かかる」「先方がフォーマットを変えたら読めなくなった」。

**解決**: 帳票種別（請求書・発注書・見積書…）ごとに**項目の一覧（スキーマ）**を1回だけ定義します。座標も、罫線の位置も、サンプル帳票の枚数も要りません。**同じ「請求書」なら、レイアウトが違う取引先でも同じスキーマで読めます。**

### 操作手順（そのままデモ手順）

**手順1** — 帳票をアップロードする。一覧画面へのドラッグ＆ドロップ、またはチャット画面へのファイル添付。

![アップロード（SCR-02）](images/02_ドキュメント一覧_アップロード.png)

**手順2** — 「抽出を開始」を押す。このとき**システムがファイル名等の信号から帳票種別を推定**し、使うスキーマを既定で選んでくれます（「推定: 見積書／信頼度 100%」のように表示）。違っていればその場で別スキーマに変更でき、**人の指定が常に最優先**されます。

![抽出開始と帳票種別の推定](images/03_抽出開始_分類サジェスト.png)

**手順3** — 結果が出る。**取れた値ごとに、帳票画像のどこから取ったかが枠（bbox）で示されます。**

![検証画面（SCR-03）](images/04_検証画面_全体.png)

- **トーク**: 「テンプレートを作っていないのに読めています。**この製品には『座標を登録する』という作業がそもそも存在しません**」
- **発表者ノート**: 所要時間を聞かれたら — 実測があるのは **OCR・レイアウト解析で A4 1ページ 12〜16 秒**（構成による）。項目抽出（LLM）の時間が加わるため、**「1〜2分以内」等のエンドツーエンドの約束はしない**（未実測）。デモでは実際に待って見せるのが最も誠実。
- **発表者ノート**: 「テンプレートレス」を「何も登録しなくていい」と言い換えない。**項目定義（スキーマ）は必要**で、「項目が取れない」相談の大半はスキーマの定義漏れが原因（実証済み: 4項目定義→4件抽出、15項目に拡張→**15件すべて根拠付きで抽出成功**。実 LLM・実帳票）。

**項目を増やすのも1分** — 「担当者名と振込先も欲しい」と思ったら、スキーマ管理画面で項目を足すか、**チャットに『請求書スキーマに支払方法を追加して』と話しかけるだけ**。AI が変更内容を提案 → **人が承認カードで承認** → 新しい版として保存（版管理・いつでも前の版に戻せる）。**AI の提案が人の承認なしに反映されることはありません。**

![チャットからのスキーマ変更（SCR-01）](images/05_チャット_スキーマ変更承認.png)

## 3. できること②: 全件突合をやめる — 見るのは機械が指した所だけ（5分・デモ込み）

**問題**: 「OCR の結果を全件、元の紙と見比べている。これなら手入力と変わらない」。

**解決**: 検証画面は「**どこを見ればいいか**」を機械が指定します。全件を見るのではなく、**機械が自信のない箇所だけ**を見る運用に変わります。

![検証画面・要確認フィールド](images/06_検証画面_要確認フィールド.png)

- **確信度で色分け** — 各項目に確信度バーが付き、赤（<0.6）／黄（<0.8）／緑（≥0.8）／青（検算合格）で表示。**要確認の項目がパネル最上部に集まります**。
- **クリックで元の場所に飛ぶ** — 項目行をクリックすると帳票画像側の該当箇所がハイライトされ、そこへスクロール。紙をめくりません。
- **文字単位の差分ポップオーバー** — 「1 か 7 か」で迷う箇所は、その文字を**拡大表示**し、①OCR の原値 ②AI の補正案 ③手入力 の3つを並べて見せます。根拠（混同ペア・検算結果・過去修正例）も同時表示。**採択はワンクリック（キー `1` / `2` / `e`）**。
- **計算が合っているかを機械が検算** — 明細合計＝小計、小計＋消費税＝合計、税率別（10%／軽減8%）の税額、数量×単価＝金額、適格請求書登録番号（`T`＋13桁）の**検査数字（チェックディジット）の整合**、銀行コード・口座の桁数、請求日≤支払期日。**検算に通った金額項目は自動的に「確認済み」へ格上げ**され、人が見る対象から外れます — **1↔7 の誤読は金額の検算でほぼ確実に落ちる**ためです。
- **キーボードだけで完結** — `n`/`p` で要確認項目を巡回、`Enter` で承認、`e` で編集、`Ctrl+Enter` で確定。マウスに持ち替えません。
- **編集は自動保存** — 500ms のデバウンスで自動保存。「保存し忘れて消えた」がありません。

![文字差分ポップオーバー](images/07_検証画面_文字差分ポップオーバー.png)

- **トーク**: 「見るのは**赤と黄だけ**。緑と青は機械が根拠と検算で裏を取っています」
- **発表者ノート**: 検算の説明で言ってよいのは「**検査数字の整合を検証**」まで。**「実在しない事業者を弾く」とは言わない**（国税庁データベースとの実在照合は行っていない）。同一請求の**重複検知（V-DUP）は検証ロジック実装済みだが現行ビルドでは未接続** — 現行機能として話さない（付録A）。
- **発表者ノート**: 「精度○%」「工数○%削減」の数値は**自社実測が取れるまで言わない**（付録A）。この節は「見る対象が減る仕組み」の説明に徹する。

**明細表（テーブル）** — 明細行も行×列の構造ごと抽出され、確定データとして出力されます。**セル単位の編集グリッド・行ごとのリアルタイム検算 UI は設計済み・実装中**です。現時点のデモでは、明細の検算結果（V-SUM／V-QTY）が項目側の確信度に反映されるところまでを見せる（付録A）。

## 4. できること③: **一度直せば、二度と直さない**（7分・デモ込み）★本日の主役

**問題**: これが現場の最大の不満です。

> 「あの取引先の請求書、毎月かならず**同じ場所**を同じように直している。先月も、先々月も。私が直したことは、どこにも残らない」

従来の OCR には「学習」がありません。あるとしても「テンプレートを直す＝また座標を触る」だけです。

**解決**: NewFan AI-OCR エージェントは、**人が直した内容を組織の資産として蓄積し、AI が次回から自動で当てにいきます。** しかも「なんとなく似ているから当てる」のではなく、**再現できることを機械が検証してから**恒久ルールに昇格させます。

### 学習の3段階（この3段が本製品の核心・スライド1枚目）

![学習ループ（1枚図）](images/08_学習ループ_全体図.png)

**第1段: 修正メモリ（1件から、その場で効く）**
あなたが検証画面で直した1件は、`どの帳票種別 × どの取引先 × どの項目 × どんな原値 × 周辺の文脈` というキーとともに保存されます。次に**似た文脈**の帳票が来たとき、AI はこの過去の修正例（類似上位5件・類似度0.75以上）を参照しながら読みます。**1件直しただけでも、次から効き始めます。**

**第2段: ルール化（同じ直しが5件たまったら自動起動）**
同種の修正が **5件** たまると、システムが「これはルールにできないか？」を自動で検討します。取り出されるのは4種類の**決定論ルール**（AI 推論を使わず、毎回まったく同じ結果になる変換）と、1種類の **LLM 最適化**です。

| ルール種別 | 内容 | 例 |
|---|---|---|
| `regex_replace` | パターン置換 | 伝票番号の先頭に混入する記号を除去 |
| `vocab_map` | 語彙の写像（表記ゆれの名寄せ） | 「サンプル（株）」「サンプル社」→「株式会社サンプル」 |
| `format` | 書式の強制 | 伝票番号は `^7\d{5}$` |
| `checksum` | 検査数字の検証 | 適格請求書登録番号 |
| `llm_hint` | 決定論化できない業務知識を日本語のまま AI に渡す | 「この取引先は明細の最終行が値引き行なので合計に含めない」 |

**第3段: 自動検証ゲート（間違ったルールを本番に出さない）★ここが差別化点・スライド2枚目**
抽出されたルールは、いきなり有効にはなりません。**そのテナントの過去の確定済み帳票に機械が再適用**し、

- **過去の修正を 90% 以上再現できること**
- **すでに正しかった値を壊す誤適用が 0 件であること**

の**両方**を満たしたときだけ有効化されます。検証レポート（何件に当たり、何件を再現し、何件壊したか）は画面で確認でき、**基準を満たさないルールは「有効化」ボタンそのものが押せません**。効かなくなったルールは画面から退役でき、有効化・退役はすべて監査に残ります。

![ルール管理と検証レポート（SCR-05）](images/09_ルール管理_検証レポート.png)

- **画面のポイント**: ① ルール種別のピル表示 ② 検証レポート（再現率・回帰件数） ③ 基準未達のルールは有効化ボタンが非活性。
- **トーク**: 「学習する AI-OCR は他社にもあります。違いは、**学習した内容が本当に正しいかを、過去データで機械が検算してから本番に出す**こと。**間違った学習が本番を壊す事故を、仕組みで防いでいます**」

### 「コツを教える」もできる — LLM 最適化（スライド2枚目に同居可）

「この取引先は明細の最終行が値引き行」「押印欄の数字は取らない」のような、**正規表現では書けない業務知識**を、**管理画面のフォームから日本語の文章のまま**登録できます。有効化すると、その帳票種別の抽出 AI へ**ヒントとして自動注入**されます。

- **人が書いたヒント**は再現率検証の対象外（決定論変換ではないため機械検算になじまない）で、そのまま有効化できます。
- **AI が自動生成したヒント**は従来どおり検証ゲートを通します — 「検証されていない学習が1クリックで本番へ入る」経路を作らない、意図的な非対称です。

![LLM 最適化の登録フォーム](images/10_ルール管理_LLM最適化登録.png)

### AI が勝手に書き換えないための2重の縛り（スライド3枚目）

「AI が学習して自動で直す」と聞くと、**勝手に値を変えられる**のが怖いはずです。ここを構造的に縛っています。

- **縛り①（混同文字表）** — AI による自動置換が許されるのは、**視覚的に混同しうる文字の組み合わせ**（1↔7↔I、0↔O↔〇、8↔B、カ↔力、ロ↔口、未↔末 など、あらかじめ定義された表）に該当する場合、**または**このテナントの過去の修正例に一致する場合**だけ**。それ以外の「AI がそう思った」変更は**自動適用されず、必ず人の確認に回ります**。桁数を増減させる修正は確信度の低い文字に限定され、視覚的根拠の記載が必須です。
- **縛り②（根拠必須）** — すべての抽出値は、帳票画像上の**実在する読み取り領域に紐付いていること**が必須。紐付けられない値は確信度 0 として強制的に人の確認へ。**AI が根拠なしに値を作ることはできません。**

- **トーク**: 「AI が勝手に賢くなって勝手に書き換える、ということは起きません。**AI に許されているのは『見えている文字の読み違いを直すこと』だけ**です」

### 効いてくる形（説明会での言い方）

- 月初1週目: 取引先 A の請求書で「1→7」を3回直した → **修正メモリに入り、AI が参照し始める**。
- 月初2週目: 同じ直しが5件を超えた → **ルール候補が自動抽出され、過去データで検証 → 基準を満たせば有効化**。
- 翌月: **同じ箇所は直さなくてよくなっている**。学習の効き（有効ルール数・修正メモリ件数・無修正率）はダッシュボードで確認できます。

- **発表者ノート**: 「◯ヶ月で確認ゼロになる」等の**時間軸を約束しない**（未実測）。「同じ直しを繰り返さない仕組みがあり、効き具合が画面で見える」までに留める。ダッシュボードの「フィールド精度」は**人が修正しなかった項目の割合（無修正率）**であって外部基準の正解率ではない — 読み替えて話さない。

## 5. できること④: 読んだ後の転記も、絵で組める — 壊れない自動化（5分）★本日の主役その2

**問題**: OCR は「読む」まで。読んだ後の基幹システムへの転記は、①人が打つ ②個別開発 ③画面操作型 RPA、のいずれかで、**③は画面レイアウトが変わると壊れ、壊れたことに気づかないまま業務が止まります**。

**解決**: 「**どこから取り込み → どう読み → どう分岐し → どう変換して → どこへ届けるか**」を、**ノードをつないだ図**として定義します。画面座標にも UI にも依存しないため、**先方の画面改修やフォーマット変更の影響を受けません**。

![ワークフローエディタ（SCR-07）](images/11_ワークフロー_エディタ全体.png)

- **画面のポイント**: ① 左のパレットからノードをドラッグ＆ドロップ ② 線でつなぐだけ ③ 設定は**すべて日本語のフォーム**（JSON・コードを書く場所はありません）。

**組める部品（16種）**: 取込＝S3／Google Drive／Microsoft 365／Box のフォルダ監視・手動・スケジュール（cron）、処理＝**帳票分類**（請求書の流れに発注書が混ざったら止めるゲート）・**AI-OCR 抽出**、分岐＝条件分岐（金額・確信度・帳票種別などで振り分け）・**人の確認ゲート**、変換＝項目名の付け替え・日付/金額の書式・マスキング、出力＝**基幹 DB へ INSERT/UPSERT**・Webhook・ファイル（JSON/CSV）・通知（Slack 互換 Webhook）。

**現場の方に覚えてほしいのは1つの型**:

> フォルダに置く → 自動で読まれる → **自信のないものだけ、あなたのレビューキューに届く** → あなたが確定した瞬間、基幹システムに入る

- **実測（そのまま話せる数字）**: S3 に帳票を配置 → **約2秒で自動取込**。Google Drive／Microsoft 365 のフォルダは**配置から15秒以内に検知**。あなたが確定操作をしてから**1秒未満**で基幹 DB へ実書込み（いずれも実環境実測）。

**「壊れない」ための3つの仕掛け（管理者が有効化する前に必ず通る関門）**:

1. **自動点検（lint）** — 図が業務として成立しているか機械が検査。**条件分岐の else 漏れ**（黙って消える経路）、**人の確認ゲートを通らず出力へ届く経路**（要確認帳票が黙って基幹へ流れる事故）等を検出し、該当ノードを赤くハイライト。
2. **出力プレビュー（dry-run）** — 有効化の前に、直近の確定済み帳票で全ノードを試し、**実行される SQL／送信ペイロードそのもの**を確認できます。**プレビューと本番実行は同一のコードが生成**するため、「プレビューでは通ったのに本番は違った」が起きません。**有効化は dry-run 成功が前提条件**です。
3. **能力の構造的制限** — DB への書き込みは **INSERT / UPSERT のみ（UPDATE・DELETE は機能として存在しない）**、書込み先は許可テーブルに完全一致したもののみ、任意 SQL 不可、1回の実行で最大1,000行。**AI が皆さんのデータを消したり書き換えたりすることは、構造的にできません。**

![点検と出力プレビュー](images/12_ワークフロー_lint_dryrun.png)

- **トーク**: 「**点検 → 出力を確認 → 有効にする**。この3ステップを通らない図は本番になりません。録画型 RPA の『いつの間にか壊れて止まっていた』は、この製品では起きようがない設計です」
- **発表者ノート**: ワークフローの構築・有効化は管理者権限。現場向け説明では「あなたのキューに要確認だけが届く」体験を主語にする。**メール添付トリガーは未実装**（画面に出るが有効化できない。メール→S3 保存→S3 監視が代替）— デモで触らない（付録A）。同一ファイルの二重取込はコンテンツハッシュで自動スキップ（同じファイルを2回置いても二重計上されない）。

## 6. 誤魔化さない AI — 分からないときは「分かりません」と言う（2分）

**問題**: 生成 AI の幻覚（それらしい嘘）。「AI が入れた数字が帳票のどこにも書いていなかった」は経理業務では事故になります。

**解決**: 「**自信がないなら人に回す**」が既定動作です。

- **根拠が取れない値は確定させない**（§4 縛り②）。
- **確信度が閾値未満の項目は必ず人の確認へ**。閾値は項目の重要度で3段階（重要 0.90／標準 0.80／備考など 0.60。「金額は必ず人が見る」といった無条件レビュー指定も可能）。
- **読みにくいページを画像 AI（VL）で補った結果は、自動確定を禁止**。必ず人の確認に回ります。
- **値の由来が全部見える** — 各項目に「OCR 原値／AI 補正／ルール適用／人手」のバッジが付き、ホバーで**補正理由と参照した過去修正例の ID** まで表示。

![値の由来バッジ](images/13_検証画面_由来バッジ.png)

- **トーク**: 「監査で『この数字の根拠は？』と聞かれたら、**帳票画像のこの位置から、この経路で入った**と1画面で示せます」

## 7. 職種別ユースケース（1分・スライド1枚）

- **経理（買掛）**: 取引先の請求書 PDF → 登録番号の検査数字・税率別の税額検算まで自動 → 会計システムへ自動転記。見るのは要確認だけ。
- **受発注事務**: 共有フォルダ（Drive／SharePoint／Box）に届く注文書を自動取込 → **請求書の流れに発注書が混ざったら分類ゲートが停止** → 受注データとして基幹 DB へ。
- **物流・現場事務**: スキャンした納品書・受領書を取り込み → 要確認だけを事務所でまとめて確認。
- **業務改善担当**: 「読む」から「転記」までを絵で組める。画面録画型 RPA の保守地獄からの脱出。

※発表者ノート: **スマホ撮影帳票は現行構成では品質担保外**（歪み補正が未稼働）— ユースケースとして積極訴求しない。聞かれたら「スキャン画像を推奨。撮影画像は PoC で実測のうえ判断」と答える。

## 10. 現場向け FAQ（想定問答・配布用）

- **Q. 1枚何秒で読めますか？** → OCR・レイアウト解析は A4 1ページ 12〜16 秒（実測）。項目抽出の AI 時間が加わります。正確な合計時間は御社帳票での PoC で実測してお出しします。
- **Q. 私が直した内容は他社にも共有される？** → いいえ。修正メモリ・ルールは**テナント（会社）単位で完全分離**。修正内容のベクトル化も**自社環境内のローカルモデル**で行い、外部の AI サービスへ修正データを送りません。
- **Q. うちの帳票が AI の学習に使われる？** → 基盤モデルの追加学習には使いません。学習は**御社テナント内の修正メモリとルール**だけです。
- **Q. 手書きは読める？** → 印字帳票が主対象。手書きは筆跡差が大きく、**実帳票での事前検証（PoC）前提**でご案内します。
- **Q. Excel や Word の帳票は？** → 現時点は PDF / PNG / JPEG / TIFF（複数ページ可・50MB／300ページまで）。Office 形式は PDF 化対応を予定（付録A）。
- **Q. 精度は何%？** → **御社の実帳票で測る数字**です。一般論の精度%は提示しません。PoC で対象帳票の実測をお出しします。
- **Q. 間違って確定してしまったら？** → 確定・修正はすべて監査ログに残り、誰がいつどの値をどう変えたかを追跡できます。

# 補足: 管理者向け情報（情シス・業務改善・内部統制の方へ）

現場向け説明会の後、管理者に個別説明する際の要点集。詳細質問は個別打合せへ誘導する。

## C-1. アーキテクチャ1枚

処理の流れ: 取込 → 前処理・ページ化 → レイアウト解析＋OCR → 品質ゲート → 過去修正の参照 → 項目抽出（KIE）→ **決定論正規化** → 確信度算出 → LLM 補正（**低確信のみ・混同文字表制約**）→ **決定論検算** → 確信度ゲート → 人の確認 → 学習 → 確定・出力。

![抽出グラフ全体像](images/14_全体像_抽出グラフ.png)

- **LLM の役割は限定的**: 項目抽出と低確信項目の補正のみ。正規化・検算・分類ゲートは**決定論**（同じ入力→常に同じ結果）。監査可能性と LLM コストの両方に効く（LLM コストは「低確信フィールド数×補正1回」に限定され、Run ごとの実使用量がダッシュボードに出る）。
- **抽出パイプラインの内部はユーザーが変更できない**（品質保証・監査境界の固定。組めるのは粗粒度ワークフローのみ）。

## C-2. セキュリティ・テナント分離・監査

- 全業務テーブルに **Row Level Security**。修正メモリのベクトルインデックスもテナント別。埋め込みは**ローカルモデル**（multilingual-e5）— 修正データを外部埋め込み API へ送らない（設計判断として明文化）。
- 認証は JWT＋API キー、ロールベース（admin／一般）。管理画面（スキーマ・ルール・ワークフロー・接続・ダッシュボード）は admin のみ。
- 接続のパスワード・トークン・署名鍵は **DB に保存せず Secrets Manager 参照**のみ。参照先はテナント帰属を検証した名前空間に限定。実行タスクの IAM も同名前空間に限定。
- 監査: 値の修正・確定・スキーマ版作成・ルール有効化/退役/override・ワークフロー変更/有効化/dry-run・接続操作を、**実施者（human/agent）を区別して**記録。**「全操作の完全な記録」「監査の完全性を保証」とは言わない**（表現ルール）。
- Webhook 出力は HMAC-SHA256 署名・5回指数リトライ。送信先は SSRF ガード（プライベートレンジ遮断）。

## C-3. 基幹 DB 書込みの構造的制約（DD-12）

任意 SQL 不可（プリペアド機械生成のみ）／**INSERT・UPSERT のみ、UPDATE・DELETE は機能として不存在**／許可テーブル完全一致制／1実行1,000行上限／UPSERT はキー列必須（業務キー重複の無音欠落防止）／失敗時ポリシーは retry・skip_and_notify・halt_notify（既定＝止めて通知）／お客様側 DB には INSERT/UPSERT 権限のみの専用ユーザーを推奨（導入手順書に明記）。

## C-4. 自動化の統制ダイヤル

| パラメータ | 既定 | 意味 |
|---|---|---|
| レビュー閾値 | critical 0.90 / 標準 0.80 / 低影響 0.60 | 項目重要度別の人手確認ライン |
| 無条件レビュー項目 | テナント設定 | 確信度に関わらず必ず人が見る |
| 完全自動化（HITL スキップ） | **既定 OFF** | 有効化しても critical 項目を含む帳票は必ず人の確認を通す（緩和は警告＋監査記録付き） |
| ルール自動有効化基準 | 再現率≥90% かつ 回帰0件 | 学習ゲート |
| ルール抽出の起動 | 同種修正5件 | |
| 修正メモリ参照 | 上位5件・類似度≥0.75 | |

確信度の定義: `min(OCR文字確信度, 根拠の強さ)`。根拠の強さ＝1.00（帳票文字列と完全一致）／0.85（型変換のみで導出）／0.70（画像 AI 由来・部分一致）／0.00（根拠なし→強制レビュー）。検算合格で 0.98 へ自動格上げ。

## C-5. 性能・インフラ（実測値のみで話す）

- OCR・レイアウト解析: A4 1ページ **4vCPU=16.4 秒／8vCPU=11.6 秒**（実測・ウォーム）。精度は構成によらず同一。1ページ単価が vCPU 数によらずほぼ一定のため、**タスク数の水平スケールが線形に効く**。
- OCR モデル v5→v6 更改で平均確信度 **0.9127→0.9689**、94行中36行改善（「单俩」→「単価」等）。合計・消費税行の取りこぼしは旧モデル起因と実測で特定・解消済み。
- **GPU 不要の構成が既定**（Fargate CPU）。難読帳票が要件に届かない場合のみ画像 AI（VL）を GPU 構成で段階追加。
- 障害時: 原本は元ストレージに残り当社は変更しない。ジョブは指数リトライ（既定3回）→恒久失敗は DLQ 隔離。停止中のイベントはキュー滞留→再開後に自動消化（実測: 停止中配置→再開後86秒で消化）。**「自動緊急停止」とは言わない**（手動手順）。

## C-6. 提供形態 — SaaS 標準＋個社別対応

| 提供形態 | 内容 | 向いているお客様 |
|---|---|---|
| **① SaaS 標準（推奨・最短導入）** | 当社運用のマルチテナント環境。RLS 分離。修正メモリ・ルール・スキーマはテナント内に閉じる | まず効果を確認したい／標準帳票が中心 |
| **② 専用環境提供** | お客様専用テナント／専用インフラ。保持期間・ネットワーク要件・接続先制約に個別対応 | セキュリティ要件が厳しい／自社網内の基幹 DB へ直接書込みたい |
| **③ カスタマイズ実装 OCR（個社別開発）** | 自社帳票・業界特有帳票への専用実装: 業務ルールの**専用バリデータ追加**（標準の検算群に追加実装）／社内コード体系・取引先マスタ名寄せの**正規化器追加**／EDI・業務パッケージへの**専用コネクタ実装**／認識モデルの帳票特化チューニング（適用可否は事前検証）／**オンプレミス・閉域構成**（CPU のみの軽量構成・外部 API 不使用構成が設計上のオプション） | 標準で吸収しきれない業務ルールがある／データを外に出せない |

**進め方**: ①帳票サンプルの適合性評価 → ②標準／作り込みの切り分け → ③**まず標準 SaaS で PoC（実測値を取る）** → ④必要な作り込みのみ個別見積り。**いきなり全部を作り込まない**。

- **発表者ノート**: 費用は営業窓口から個別案内（本資料で扱わない。利用量計量・上限機能は現状無く「従量課金」の説明もしない）。「どんな帳票でも読める」とは言わない — 「サンプルをお預かりして評価」まで。

# 付録A: 表現ルールと「設計 vs 現行実装」差分メモ

## A-1. 設計上も言ってはいけない（確定した表現ルール）

一般論の精度数値（帳票精度・STP 率は**未実測**。PoC 実測でのみ語る） ／ エンドツーエンドの処理時間の約束（実測は OCR 部のみ） ／ 「登録番号の**実在**確認」（検査数字の整合まで。国税庁 DB 照合はしない） ／ 「重複請求を検知します」（現行未接続・下記A-2） ／ 「何でも読める」「どんな帳票でも対応」 ／ 「テンプレート不要」を「何も登録不要」と言い換えること（スキーマ定義は必要） ／ 「Word・Excel も読めます」（未実装） ／ 「手書きも読めます」（要事前検証） ／ 「スマホ撮影でも大丈夫」（歪み補正が現行未稼働） ／ 「メール添付から自動取込」（トリガー未実装・S3 経由が代替） ／ 「AI が完全に仕分けます」（分類は決定論キーワードゲート） ／ 「全操作を完全に監査記録」「監査の完全性を保証」 ／ ダッシュボードの「フィールド精度」を正解率と読み替えること（実体は**無修正率**） ／ 「1万枚を◯時間で」を実績として（SLO＝目標） ／ 自動緊急停止 ／ 利用量の計量・上限 ／ 「Slack/Teams ネイティブ連携」（Slack 互換 incoming webhook が実体）

## A-3. 限定付きで言える表現（確定ルール）

学習 →「**修正メモリは1件から効く。恒久ルール化は再現率90%・回帰0件を機械検証してから**」 ／ 検算 →「登録番号は**検査数字の整合**を検証」 ／ 精度 →「御社帳票の PoC 実測でご提示。当社標準セットの回帰試験は継続実施」 ／ 処理時間 →「OCR・レイアウト解析は A4 1ページ 12〜16 秒（実測）。合計時間は PoC で実測」 ／ DB 連携 →「INSERT/UPSERT のみ・許可テーブル限定・任意 SQL 不可」 ／ 分類 →「許可リスト外の帳票種別を**止めるゲート**（ファイル名信号・決定論）」 ／ 個社別対応 →「サンプル評価のうえ標準／作り込みを切り分け」 ／ オンプレ →「CPU のみの軽量構成が設計上のオプション（個社別対応）」

## A-4. v1.0 からの主な修正（敵対的レビュー 2026-08-21 反映）

① V-DUP を現行機能から差分メモへ移動 ② 表エディタ記述を設計扱いへ格下げ ③ 「実在しない事業者を弾く」→「検査数字の整合を検証」へ修正 ④ 分類ゲート信号を「ファイル名＋抽出結果」→「ファイル名信号のみ」へ修正（抽出値は構造的に偏るため信号から排除済みの実装に整合） ⑤ 混同文字表の例を設計書付録Aの実在ペアへ差し替え ⑥ 「数十秒で結果」の時間約束を削除 ⑦ スマホ撮影ユースケースを非訴求化 ⑧ 2部構成を現場担当者向け単部＋管理者補足へ再編（学習ループの二重説明を統合） ⑨ まとめ・今日からのアクション（才流メソッド必須要素）を追加 ⑩ 現場向け FAQ を拡充。

# 付録C: 用語

| 用語 | 意味 |
|---|---|
| **スキーマ** | 帳票種別ごとの「取りたい項目の定義」。テンプレート（座標登録）ではない。版管理される |
| **テンプレートレス** | 取引先ごとのレイアウト登録（座標指定）を必要としない方式。項目定義は必要 |
| **HITL** | Human In The Loop。機械が自信を持てない箇所だけを人が確認する運用 |
| **確信度（confidence）** | 値の確からしさ。OCR の文字確信度と根拠の強さの小さい方 |
| **根拠（grounding）** | 抽出値が帳票画像上のどの読み取り領域から来たかの紐付け。根拠なしの値は自動確定不可 |
| **修正メモリ** | 人が直した内容をテナント別に蓄積し、次回の抽出で参照する仕組み。1件から効く |
| **ルール** | 修正メモリから抽出され、機械検証（再現率90%・回帰0件）を通って恒久適用される変換規則。決定論4種＋LLM最適化1種 |
| **決定論（deterministic）** | AI 推論を使わず、同じ入力に常に同じ結果を返す処理。正規化・検算・分類ゲートが該当 |
| **auto-elevation** | 検算に合格した項目の確信度を自動で引き上げ、人の確認対象から外す仕組み |
| **dry-run** | ワークフローを出力なしで実行し、生成される SQL／ペイロードをプレビューすること。有効化の前提条件 |
| **STP 率** | Straight Through Processing 率。人が一切触らず完了した帳票の割合（**現在未実測**） |
