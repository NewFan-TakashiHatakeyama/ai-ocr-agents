# 現場担当者向け説明会（30分）

時間配分: §1 3分／§2 5分（デモ込み）／§3 5分（デモ込み）／**§4 7分（最重要・デモ込み）**／**§5 5分**／§6 2分／§7 1分／§8 体験ワーク1分／§9 まとめ1分。押した場合に飛ばす節は §6・§7。

## 1. いまの困りごと → AI-OCR エージェントとは（3分）

**問題**: 紙・PDF の帳票（請求書・発注書・見積書・納品書）を、人が目で読んで基幹システムに打ち直している。従来の AI-OCR を入れても解決しきらない理由は3つ。

1. **テンプレート地獄** — 取引先ごとに読み取り枠（座標）を登録する方式のため、取引先が増えるたび・先方がフォーマットを変えるたびに登録作業が発生する。
2. **結局、全件を目視突合している** — OCR が「読めた」と言っても信用できないので、1枚ずつ元帳票と見比べる。OCR を入れた後も工数が減らない。
3. **同じ間違いを毎月直している** — 「1 を 7 と読む」「あの取引先の社名表記だけ崩れる」。直した知識はどこにも残らず、翌月また同じ場所を直す。

**解決**: NewFan AI-OCR エージェントは、**テンプレート（座標）を登録しない AI-OCR**。登録するのは「何を取りたいか」という**項目名の一覧だけ**。AI が帳票を読み、**どこから取ったか（根拠）を必ず示し**、人が直した内容を**覚えて次回から自動で当てにいく**。さらに読み取った後の「基幹システムへの転記」まで、**ノードをつないだ絵**で自動化できる。

- **トーク**: 「今日お伝えしたいのは2つだけです。**登録するのは項目名だけ**。そして**一度直せば、次から直さなくていい**。この2つです」
- **提供形態（1行だけ）**: SaaS で提供。**個社別の専用環境・カスタマイズ実装 OCR も可能**（補足章 C-6）。

## 2. できること①: テンプレート登録なしで読む（5分・デモ込み）

**問題**: 「新しい取引先の請求書が来た。OCR に覚えさせるのに半日かかる」「先方がフォーマットを変えたら読めなくなった」。

**解決**: スキーマ（項目定義）が無くても、まず取り込めば **AI が帳票から項目を自動発見して抽出**する。結果を見ながら「残す項目」を選んで**テンプレート化**すれば、帳票種別ごとのスキーマが 1 回で出来上がる（座標も罫線位置もサンプル枚数も不要）。同じ「請求書」なら、レイアウトが違う取引先でも同じスキーマで読める。

**解決**: 検証画面は「**どこを見ればいいか**」を機械が指定する。全件を見るのではなく、**機械が自信のない箇所だけ**を見る運用に変わる。

## 4. できること③: **一度直せば、二度と直さない**（7分・デモ込み）★本日の主役

**問題**: 現場の最大の不満。

> 「あの取引先の請求書、毎月かならず**同じ場所**を同じように直している。私が直したことは、どこにも残らない」

**解決**: 人が直した内容を**組織の資産として蓄積**し、AI が次回から自動で当てにいく。しかも「なんとなく似ているから当てる」のではなく、**再現できることを機械が検証してから**恒久ルールに昇格させる。

### 学習の3段階（スライド1枚目）

**第1段: 修正メモリ（1件から、その場で効く）**
検証画面で直した1件は、`帳票種別 × 取引先 × 項目 × 原値 × 周辺文脈` のキーとともに保存される。次に似た文脈の帳票が来たとき、AI は過去の修正例（類似上位5件・類似度0.75以上）を参照しながら読む。§3 の画面で根拠に出ていた「類似修正 cor_01H8MQ」がまさにこれ — **過去の修正が、今日の帳票の補正候補の根拠として引用されている**。

**第2段: ルール化（同じ直しが5件たまったら自動起動）**
同種の修正が5件たまると、システムが「ルールにできないか」を自動で検討する。取り出されるのは4種の**決定論ルール**と1種の **LLM 最適化**:

| ルール種別 | 内容 | 例 |
|---|---|---|
| `regex_replace` | パターン置換 | 伝票番号の先頭に混入する記号を除去 |
| `vocab_map` | 語彙の写像（表記ゆれの名寄せ） | 「サンフル商事」→「サンプル商事」 |
| `format` | 書式の強制 | 伝票番号は先頭「7」の6桁 |
| `checksum` | 検査数字の検証 | 適格請求書登録番号 |
| `llm_hint` | 決定論化できない業務知識を日本語のまま AI に渡す | 「合計金額は『御請求金額』の値を優先し、内訳行の小計と混同しないこと」 |

**第3段: 自動検証ゲート（間違ったルールを本番に出さない）★差別化点**
抽出されたルールはいきなり有効にならない。**そのテナントの過去の確定済み帳票に機械が再適用**し、**過去修正の再現率 90% 以上・すでに正しかった値への誤適用 0 件**の両方を満たしたときだけ有効化される。

実機のルール管理画面 — llm_hint 2件（有効1・承認待ち1）が登録され、ルールの中身（JSON）と有効化条件が画面に明記されている:

![ルール管理](images/12_ルール管理.png)

- **画面のポイント**: ① ルールごとに種別・対象（invoice・total_amount）・状態（有効／承認待ち）・検証レポート列 ② 選択中ルールの定義がそのまま読める — 「合計金額は『御請求金額』の値を優先し、内訳行の小計と混同しないこと」という**日本語の業務知識**が AI への指示として登録されている ③ 画面下部に「**有効化条件: 再現率≥90% かつ 回帰0件**」「有効化/退役は監査記録」と明記。
- **トーク**: 「学習する AI-OCR は他社にもあります。違いは、**学習した内容が本当に正しいかを過去データで機械が検算してから本番に出す**こと。間違った学習が本番を壊す事故を、仕組みで防いでいます」

### 「コツを教える」もできる — LLM 最適化（スライド2枚目）

正規表現では書けない業務知識を、**管理画面のフォームから日本語の文章のまま**登録できる。実機で入力中の画面:

![LLM最適化の登録フォーム](images/13_LLM最適化フォーム.png)

- **画面のポイント**: ① 対象の帳票種別・対象項目（空欄=全項目）を選ぶだけ ② 指示は自然言語 — 「この取引先の請求書は『御請求金額』欄が2箇所ある。上段の枠内の金額を合計金額として採用すること。」 ③ 作成すると**承認待ち**に入る（勝手に本番へ入らない）。
- **人が書いたヒント**は再現率検証の対象外でそのまま有効化できる。**AI が自動生成したヒントは検証ゲートを必ず通す** — 「検証されていない学習が1クリックで本番へ入る」経路を作らない意図的な非対称。

### AI が勝手に書き換えないための2重の縛り（スライド3枚目）

- **縛り①（混同文字表）** — AI の自動置換が許されるのは、**視覚的に混同しうる文字の組み合わせ**（1↔7↔I、0↔O↔〇、8↔B、カ↔力、ロ↔口、未↔末 など事前定義の表）に該当する場合、**または**過去の修正例に一致する場合**だけ**。§3 の画面の根拠表示「混同ペア I↔1」はこの縛りが実際に働いている証拠。それ以外の変更は自動適用されず必ず人の確認へ。
- **縛り②（根拠必須）** — すべての抽出値は帳票画像上の**実在する読み取り領域に紐付く**ことが必須。紐付かない値は確信度 0 で強制的に人の確認へ。**AI が根拠なしに値を作ることはできない。**

## 5. できること④: 読んだ後の転記も、絵で組める — 壊れない自動化（5分）★主役その2

**問題**: OCR は「読む」まで。読んだ後の転記は、人が打つか、画面操作型 RPA で自動化するか。**RPA は画面レイアウトが変わると壊れ、壊れたことに気づかない**。

**解決**: 「どこから取り込み → どう読み → どう分岐し → どう変換して → どこへ届けるか」を、**ノードをつないだ図**として定義する。画面座標にも UI にも依存しないため、画面改修やフォーマット変更の影響を受けない。

実機のワークフローエディタ — 稼働中（active v3）の「ローカル基幹DB格納」。手動実行→AI-OCR 抽出→HITL ゲート→フィールド変換→DB 格納 の5ノード。右パネルは「DB 格納」ノードの設定フォーム:

![ワークフローエディタ](images/15_ワークフローエディタ.png)

### 「壊れない」ための3つの仕掛け

**① 自動点検（lint）** — 業務として成立しない図を機械が検出し、該当ノードを赤くハイライトする。実機で意図的に壊れた図（抽出ノード無しで DB 格納・未テストの接続）を点検した画面:

![点検エラーの検出](images/16_ワークフロー_点検エラー.png)

- **画面のポイント**: ① 「エラー: sink.db_write の上流に AI-OCR 抽出（process.extract）がありません」— **読んでいないデータを基幹に流す構成は組めない** ② 「エラー: 接続が存在しないか疎通テスト未実施です」— 未確認の接続先には流せない ③ 問題ノードが赤枠でハイライト、右下に「エラー2件/警告0件」。**エラーがある図は有効化できない。**

**② 出力プレビュー（dry-run）** — 有効化の前に「本番で何が起きるか」を実データで確認できる。実機の出力プレビュー — DB 格納ノードが `erp_demo.invoices` へ書き込む**列と値の対応表**、さらに「SQL を表示（上級者向け）」まで:

![出力プレビュー](images/17_ワークフロー_出力プレビュー.png)

- **画面のポイント**: ① 「実行はせず、DB 格納・Webhook が書き込む・送信する内容を確認できます」 ② invoice_no ← 抽出値「invoice_no」、amount ← 抽出値「total_amount」、source_system ← 固定値 — **転記のマッピングが目で確認できる** ③ プレビューと本番実行は**同一のコード**が SQL を生成（「プレビューでは通ったのに本番で違う」が起きない）。

**③ 能力の構造的制限** — DB への書き込みは **INSERT/UPSERT のみ（UPDATE・DELETE は機能として存在しない）**、書き込み先は許可テーブル完全一致のみ、任意 SQL 不可、1実行1,000行上限。**AI が基幹のデータを消したり書き換えたりすることは、構造的にできない。**

実機の接続管理 — Google Drive・Box・Microsoft 365・基幹 DB（PostgreSQL）が並び、**最終同期の成否**（✓1分以内／✗失敗（3日前）＋理由）まで表示。失敗した接続はエラー内容付きで赤表示され、「今すぐ同期」で手動リトライできる:

- **発表者ノート**: ワークフローの構築・有効化は管理者権限。現場向けには「要確認だけが自分のキューに届く」体験を主語に。メール添付トリガーは未実装（画面に「未実装」表示・有効化不可）。

## 6. 誤魔化さない AI — 分からないときは「分かりません」と言う（2分）

**問題**: 生成 AI の幻覚。「AI が入れた数字が帳票のどこにも無かった」は経理では事故になる。

**解決**: 「自信がないなら人に回す」が既定動作。

- **根拠が取れない値は確定させない**（§4 縛り②）。
- **確信度が閾値未満は必ず人の確認へ**（重要項目 0.90／標準 0.80／備考など 0.60。無条件レビュー指定も可能）。
- **読みにくいページは正直に申告する** — 品質の低いページを画像 AI（VL）で補った場合、実機ではページに**警告バナー**が出る:

![VL補完の警告バナー](images/07_検証画面_VL補完バナー.png)

- **画面のポイント**: ① ページタブに「p.2 VL」バッジ ② バナー「このページは **VL補完**（構造/OCR品質が低いため画像モデルで抽出）。由来 VL の値は grounding 上限 0.7・**特に確認が必要です**」 ③ VL 由来の値は**自動確定が禁止**され、必ず人の確認に回る。
- **トーク**: 「読みにくいページを『読めたことにする』のではなく、**読みにくかったと申告して人を呼ぶ**。監査で『この数字の根拠は？』と聞かれたら、帳票画像のこの位置から、この経路で入ったと1画面で示せます」

# 処理の中身 — 1枚の帳票に何が起きているか（技術に興味のある方向け・5分版）

「AI に丸投げ」ではなく、**決定論処理（毎回同じ結果になる処理）で LLM を挟み撃ちにする**パイプライン。§2 の実抽出で実際に走った処理をそのまま説明する。

```
① 取込        ファイル検証（形式/サイズ/ページ数）→ ページ分割・PNG化
② 構造解析     PP-StructureV3 + PP-OCRv6（実測: A4 1ページ 12〜16秒）
              → 読み取り領域(span)・レイアウト・明細表の行×列構造を一括取得
③ 低確信の再読 確信度の低い文字領域だけを切り出して OCR に再問合せ（DD-02）
④ 品質ゲート   ページ品質が基準未満 → 画像AI(VL)補完 or 人の確認へ直行（§6のバナー）
⑤ 過去修正の参照 修正メモリを類似検索（上位5件・類似度0.75以上）→ AIへ渡す
⑥ 項目抽出(KIE) LLM がスキーマの項目を抽出。全項目に読み取り領域IDの紐付けを強制
⑦ 決定論正規化  全半角/和暦→西暦/△▲/桁区切り → テナントの有効ルールを適用
⑧ 確信度算出   min(OCR文字確信度, 根拠の強さ)。根拠なし=0（強制レビュー）
⑨ LLM補正     低確信の項目だけ。混同文字表 or 過去修正例に合致する提案のみ
⑩ 決定論検算   V-SUM/V-TAX/V-QTY/登録番号検査数字/銀行桁数/日付整合
              合格項目は確信度を自動引き上げ（人の確認対象から外す）
⑪ 確信度ゲート  閾値（重要0.90/標準0.80/低0.60）＋無条件レビュー指定で要確認を決定
⑫ 人の確認(HITL) 要確認だけレビューキューへ。確定で ⑬ へ
⑬ 学習        修正を修正メモリへ登録。同種5件でルール抽出→自動検証→有効化
⑭ 確定・出力   DB保存 → ワークフローの下流（DB格納/Webhook/CSV/通知）へ
```

- **LLM を使うのは ⑥ と ⑨ だけ**。しかも ⑨ は低確信項目に限定されるため、LLM コストは「低確信フィールド数 × 補正1回」に収まる（ダッシュボードに Run ごとの実測コスト表示）。
- ②③⑦⑧⑩⑪ はすべて決定論 — 同じ帳票を2回入れれば同じ結果になる。監査説明可能性の土台。
- §3 の「¥I36,998 → 136,998」の提案は、⑨（混同ペア I↔1）＋⑩（明細合計と一致 V-SUM）＋⑤（類似修正 cor_01H8MQ）の**3つの証拠の合流**として画面に表示されていた。

# 補足: 管理者向け情報（情シス・業務改善・内部統制の方へ）

## C-1. スキーマ管理（帳票の「型」）

![スキーマ管理](images/09_スキーマ管理.png)

- 帳票種別ごとに項目名・ラベル・型（string／date／money_jpy／jp_invoice_reg_no 等）・必須・**critical**（レビュー閾値を最も厳しくする）をトグルで定義。実機は invoice v6（17項目）・purchase_order v1・quotation v1 の3種が稼働。
- 保存は常に**新版作成**（v6→v7）。実行中のワークフローは開始時点の版を参照し続ける。
- 新規作成モードでは**既存種別との重複を禁止**（暗黙の版バンプ事故を防止）:

![スキーマ新規作成](images/10_スキーマ新規作成.png)

- チャット経由の変更（§2）も**同一の版管理**を通る。AI 提案は人の承認が必須。

## C-2. セキュリティ・テナント分離・監査

- 全業務テーブルに **Row Level Security**。修正メモリのベクトルインデックスもテナント別。埋め込みはローカルモデル（multilingual-e5）— 修正データを外部埋め込み API へ送らない。
- 認証は JWT＋API キー、ロールベース（admin／一般）。管理画面は admin のみ（非 admin は 403）。
- 接続のパスワード・トークン・署名鍵は **DB に保存せず Secrets Manager 参照**（テナント帰属を検証した名前空間限定。接続管理画面にも「秘密は config に書かず secret_ref で渡します」と明記）。
- 監査: 値の修正・確定・スキーマ版作成・ルール有効化/退役/override・ワークフロー変更/有効化/dry-run・接続操作を実施者（human/agent）区別で記録。**「全操作の完全な記録」とは言わない**（表現ルール）。
- Webhook 出力は HMAC-SHA256 署名・5回指数リトライ・SSRF ガード。

## C-3. 基幹 DB 書込みの構造的制約

任意 SQL 不可（プリペアド機械生成のみ）／INSERT・UPSERT のみ／許可テーブル完全一致制／1実行1,000行上限／UPSERT はキー列必須／失敗時ポリシー既定「停止して通知」／顧客側 DB には INSERT/UPSERT 権限のみの専用ユーザーを推奨。§5 の実機画面（設定フォーム・出力プレビュー・SQL 表示）がそのまま監査説明資料になる。

## C-4. 自動化の統制ダイヤル

| パラメータ | 既定 | 意味 |
|---|---|---|
| レビュー閾値 | critical 0.90 / 標準 0.80 / 低影響 0.60 | 項目重要度別の人手確認ライン |
| 無条件レビュー項目 | テナント設定 | 確信度に関わらず必ず人が見る |
| 完全自動化（HITL スキップ） | **既定 OFF** | 有効化しても critical 含む帳票は必ず人の確認（緩和は警告＋監査記録） |
| ルール自動有効化 | 再現率≥90% かつ 回帰0件 | 学習ゲート |
| ルール抽出の起動 | 同種修正5件 | |
| 修正メモリ参照 | 上位5件・類似度≥0.75 | |

確信度 = `min(OCR文字確信度, 根拠の強さ)`。根拠の強さ: 1.00＝帳票文字列と完全一致／0.85＝型変換のみで導出／0.70＝画像AI由来・部分一致／0.00＝根拠なし（強制レビュー）。検算合格で自動引き上げ。

## C-5. 性能・インフラ（実測値のみで話す）

- OCR・レイアウト解析: A4 1ページ **4vCPU=16.4秒／8vCPU=11.6秒**（実測・ウォーム）。精度は構成によらず同一。1ページ単価が vCPU 数によらずほぼ一定 → **タスク数の水平スケールが線形に効く**。
- OCR モデル v5→v6 更改で平均確信度 **0.9127→0.9689**、94行中36行改善。合計・消費税行の取りこぼしは旧モデル起因と実測で特定・解消済み。
- **GPU 不要の構成が既定**（Fargate CPU）。難読帳票が要件未達の場合のみ画像 AI（VL）を GPU 構成で段階追加。
- 障害時: 原本は元ストレージに残り当社は変更しない。ジョブは指数リトライ（既定3回）→恒久失敗は DLQ 隔離。停止中のイベントはキュー滞留→再開後に自動消化（実測: 86秒で消化）。「自動緊急停止」とは言わない（手動手順）。

## C-6. 提供形態 — SaaS 標準＋個社別対応

| 提供形態 | 内容 | 向いているお客様 |
|---|---|---|
| **① SaaS 標準（推奨・最短導入）** | 当社運用のマルチテナント環境。RLS 分離。修正メモリ・ルール・スキーマはテナント内に閉じる | まず効果を確認したい／標準帳票が中心 |
| **② 専用環境提供** | お客様専用テナント／専用インフラ。保持期間・ネットワーク要件・接続先制約に個別対応 | セキュリティ要件が厳しい／自社網内の基幹 DB へ直接書き込みたい |
| **③ カスタマイズ実装 OCR（個社別開発）** | 業務ルールの**専用バリデータ追加**（標準の検算群に追加）／社内コード体系・取引先マスタ名寄せの**正規化器追加**／EDI・業務パッケージへの**専用コネクタ実装**／認識モデルの帳票特化チューニング（適用可否は事前検証）／**オンプレミス・閉域構成**（CPU のみの軽量構成が設計上のオプション） | 標準で吸収しきれない業務ルールがある／データを外に出せない |

**進め方**: ①帳票サンプルの適合性評価 → ②標準／作り込みの切り分け → ③**まず標準 SaaS で PoC（実測値を取る）** → ④必要な作り込みのみ個別見積り。

- **発表者ノート**: 費用は営業窓口から個別案内（利用量計量・上限機能は現状無く「従量課金」の説明もしない）。「どんな帳票でも読める」とは言わない。

# 付録A: 表現ルールと「設計 vs 現行実装」差分メモ

## A-1. 言ってはいけない（確定した表現ルール）

一般論の精度数値（帳票精度・STP 率の一般値は**未実測** — 実機ダッシュボードの STP 26.7%/精度 100% は**ローカル検証データ16件の値**であり営業数値に使わない） ／ エンドツーエンドの処理時間の約束（実測は OCR 部のみ） ／ 「登録番号の実在確認」（検査数字の整合まで） ／ 「重複請求を検知します」（V-DUP 未接続） ／ 「何でも読める」 ／ 「テンプレート不要」を「何も登録不要・スキーマも永久に不要」と言い換えること（初回はスキーマ無しで自動発見できるが、安定運用・検算・型正規化はスキーマ化後に効く） ／ 「Word・Excel も読めます」（未実装） ／ 「手書きも読めます」（要事前検証） ／ 「スマホ撮影でも大丈夫」（歪み補正が未稼働） ／ 「メール添付から自動取込」（未実装・画面にも「未実装」表示） ／ 「AI が完全に仕分けます」（分類は決定論キーワードゲート） ／ 「全操作を完全に監査記録」 ／ ダッシュボードの「フィールド精度」を正解率と読み替えること（無修正率） ／ 「1万枚を◯時間で」を実績として ／ 自動緊急停止 ／ 利用量の計量・上限 ／ 「Slack/Teams ネイティブ連携」（Slack 互換 incoming webhook が実体）

## A-3. 限定付きで言える表現（確定ルール）

学習 →「修正メモリは1件から効く。恒久ルール化は再現率90%・回帰0件を機械検証してから」 ／ 検算 →「登録番号は検査数字の整合を検証」 ／ 精度 →「御社帳票の PoC 実測でご提示」 ／ 処理時間 →「OCR・レイアウト解析は A4 1ページ 12〜16 秒（実測）。合計は PoC で実測」 ／ DB 連携 →「INSERT/UPSERT のみ・許可テーブル限定・任意 SQL 不可」 ／ 分類 →「許可リスト外の帳票種別を止めるゲート（決定論）」 ／ 個社別対応 →「サンプル評価のうえ標準／作り込みを切り分け」 ／ オンプレ →「CPU のみの軽量構成が設計上のオプション（個社別対応）」

# 付録C: 用語

| 用語 | 意味 |
|---|---|
| **スキーマ** | 帳票種別ごとの「取りたい項目の定義」。テンプレート（座標登録）ではない。版管理される。初回はスキーマ無しの自動発見抽出から**テンプレート化**で作れる（ADR-0006） |
| **テンプレートレス** | 取引先ごとのレイアウト登録（座標指定）を必要としない方式。項目定義は必要 |
| **HITL** | Human In The Loop。機械が自信を持てない箇所だけを人が確認する運用 |
| **確信度（confidence）** | 値の確からしさ。OCR の文字確信度と根拠の強さの小さい方 |
| **根拠（grounding）** | 抽出値が帳票画像上のどの読み取り領域から来たかの紐付け。根拠なしの値は自動確定不可 |
| **修正メモリ** | 人が直した内容をテナント別に蓄積し、次回の抽出で参照する仕組み。1件から効く |
| **ルール** | 修正メモリから抽出され、機械検証（再現率90%・回帰0件）を通って恒久適用される変換規則。決定論4種＋LLM最適化1種 |
| **決定論（deterministic）** | AI 推論を使わず、同じ入力に常に同じ結果を返す処理。正規化・検算・分類ゲートが該当 |
| **auto-elevation** | 検算に合格した項目の確信度を自動で引き上げ、人の確認対象から外す仕組み |
| **dry-run** | ワークフローを出力なしで実行し、生成される SQL／ペイロードをプレビューすること。有効化の前提条件 |
| **VL補完** | 品質の低いページを画像モデルで補う経路。由来 VL の値は自動確定禁止（要人手確認） |
| **STP 率** | 人が一切触らずに完了した帳票の割合 |
